# 회의실 예약 시스템 설계서

> 문서 상태: 구현 기준안  
> 최종 수정일: 2026-08-12  
> 기준 시간대: Asia/Seoul  
> 대상 DB: Supabase PostgreSQL 15+

## 1. 개요

### 1.1 시스템 목적

사무실 내 회의실 6개(대회의실 1개, 소회의실 5개)의 예약 현황을 조회하고, 단건 예약의 생성·취소·시간 변경과 정기예약의 신청·승인·반려를 제공하는 웹 시스템이다.

### 1.2 설계 원칙

- 모든 예약자는 로그인한 회원이어야 한다.
- 일반 사용자는 본인 예약과 본인 정기예약 신청만 변경할 수 있다.
- 관리자는 전체 예약 조회, 정기예약 승인·반려, 회의실 및 사용자 관리 권한을 가진다.
- 예약 취소는 물리 삭제하지 않고 상태를 변경하여 이력을 보존한다.
- 시간 충돌은 애플리케이션 검증과 PostgreSQL 제약으로 이중 방어한다.
- 날짜와 업무시간 판단은 `Asia/Seoul`을 기준으로 한다.
- 개인정보와 비밀번호는 필요한 범위에서만 수집·보관하며 화면에 과도하게 노출하지 않는다.

### 1.3 사용자 유형

| 유형 | 주요 권한 | 인증 |
|---|---|---|
| 일반 사용자 | 예약현황 조회, 본인 예약 생성·취소·시간변경, 정기예약 신청 | 로그인 필수 |
| 관리자 | 일반 사용자 권한 + 정기예약 승인·반려, 회의실 추가·수정·삭제, 사용자 관리 | 로그인 필수, `ADMIN` 역할 필요 |

> 기존 초안의 “일반 사용자 로그인 불필요” 정책은 현재 DB 및 UI의 회원 모델과 충돌하므로 폐기한다.

## 2. 업무 정책

### 2.1 운영시간과 예약 단위

- 기본 운영시간: 09:00~19:00
- 예약 단위: 30분
- 단건 예약 최대 시간: 기본 4시간
- 과거 시각에는 새 예약을 만들 수 없다.
- 종료시각은 시작시각보다 늦어야 한다.
- 운영시간, 최대 예약 시간, 예약 가능 미래 범위는 환경설정으로 분리할 수 있다.
- 휴일·주말 제한은 초기 버전에서는 적용하지 않으며, 도입 시 별도 영업일 정책으로 관리한다.

### 2.2 예약 충돌 기준

같은 회의실의 `CONFIRMED` 예약에 대해 다음 조건이 참이면 충돌이다.

```text
신규 시작 < 기존 종료 AND 신규 종료 > 기존 시작
```

종료시각과 다음 예약의 시작시각이 같은 경우는 충돌하지 않는다. 충돌 검사는 화면 표시가 아니라 서버의 최신 데이터와 DB 제약을 기준으로 한다.

### 2.3 회의실 비활성화

- 비활성 회의실에는 새 예약과 정기예약을 신청할 수 없다.
- 비활성화 시 기존 확정 예약은 자동 취소하지 않는다.
- 관리자는 비활성화 전에 향후 예약 목록을 확인하고 별도로 조치한다.

### 2.4 회의실 추가·삭제

회의실 추가·삭제는 관리자만 수행할 수 있다.

추가 규칙:

- 회의실명은 필수이며 중복될 수 없다.
- 유형은 `LARGE` 또는 `SMALL`이어야 한다.
- 수용 인원은 1명 이상이어야 한다.
- 위치와 장비 정보는 선택 입력이다.
- 생성된 회의실은 기본적으로 활성 상태가 된다.
- 서버와 DB가 이름 중복 및 입력값을 모두 검증한다.

삭제 규칙:

- 예약 또는 정기예약 이력이 전혀 없는 회의실만 물리 삭제할 수 있다.
- 이력이 있는 회의실의 삭제 요청은 물리 삭제하지 않고 `is_active = false`, `deleted_at = now()`로 보관 처리한다.
- 향후 `CONFIRMED` 예약이나 `PENDING` 정기예약 신청이 있으면 즉시 보관 처리할 수 없다. 관리자가 해당 건을 취소·반려한 후 다시 요청해야 한다.
- 보관된 회의실은 일반 조회와 신규 예약 대상에서 제외하고 관리자 화면에서만 조회한다.
- 회의실 삭제·보관 처리와 복원은 관리자 감사 로그에 기록한다.
- 보관된 회의실은 관리자가 복원할 수 있으며, 동일 이름의 활성 회의실이 있으면 복원할 수 없다.

### 2.5 예약 정보 공개 범위

- 전체 예약현황에는 회의실, 시간, 사용목적을 표시한다.
- 예약자 회사명·이름·연락처는 일반 사용자에게 공개하지 않는다.
- 본인과 관리자만 예약자 상세정보를 볼 수 있다.
- 사용목적에는 민감정보를 입력하지 않도록 안내한다.

## 3. 주요 기능

### 3.1 예약현황 조회

- 기본 화면은 일간 타임테이블로 제공하고 일간·주간·월간 보기를 전환할 수 있다.
- 가로축은 회의실, 세로축은 30분 단위 시간으로 구성한다.
- 날짜 이동, 오늘 이동, 회의실명 검색, 대·소회의실 필터를 제공한다.
- 정기예약에서 생성된 예약은 별도 패턴으로 표시한다.
- 주간 보기는 7일간 날짜별 예약 목록, 월간 보기는 달력의 날짜별 예약 건수와 예약 목록을 표시한다.
- 모든 보기에서 예약을 선택하면 회의실, 일시, 예약자, 목적, 예약 유형, 참석자 목록을 상세 화면으로 확인한다.
- 조회 API는 날짜 범위와 회의실 조건을 필수로 받아 무제한 조회를 방지한다.

### 3.2 단건 예약 생성

필수 입력값은 회의실, 시작일시, 종료일시, 사용목적이다. 회사명과 사용자명은 로그인한 사용자 정보에서 가져오며 요청 본문 값을 신뢰하지 않는다. 참석자는 프로젝트의 활성 사용자 중 복수 선택할 수 있으며 예약자 자신은 참석자 목록에서 제외한다.

서버 검증 순서:

1. 로그인 및 사용자 활성 상태 확인
2. 회의실 존재 및 활성 상태 확인
3. `Asia/Seoul` 기준 과거 여부, 운영시간, 30분 단위, 최대 예약시간 검증
4. 애플리케이션 레벨 충돌 사전 확인
5. 트랜잭션에서 예약 INSERT
6. DB `EXCLUDE` 제약 위반 시 `409 CONFLICT`로 변환
7. 생성 이력 기록 후 커밋

참석자 등록 규칙:

- 참석자는 프로젝트의 활성 회원만 등록할 수 있다.
- 중복 참석자는 한 명으로 정규화한다.
- 예약자와 참석자는 별도 역할로 관리하며 예약자는 참석자 수에 포함하지 않는다.
- 예약 취소 시 참석자 연결 정보는 예약 이력과 함께 보존한다.
- 참석자 목록은 로그인 사용자에게만 공개한다.

### 3.3 예약 취소

- 본인 또는 관리자만 취소할 수 있다.
- `reservations.status`를 `CANCELLED`로 변경하고 행은 삭제하지 않는다.
- 이미 취소된 예약에 대한 재요청은 성공으로 처리하는 멱등 동작을 권장한다.
- 취소 행위는 변경 이력에 기록한다.
- 정기예약 파생 건 하나의 취소는 해당 인스턴스에만 적용한다.

### 3.4 예약시간 변경

- 본인 또는 관리자만 변경할 수 있다.
- 단축과 연장 모두 최종 시간 범위 전체를 서버에서 다시 검증한다.
- 충돌 검사에서는 변경 대상 예약 자체를 제외한다.
- 예약 변경과 변경 이력 기록은 하나의 트랜잭션으로 처리한다.
- 취소된 예약은 변경할 수 없다.

### 3.5 정기예약 신청

지원 패턴:

| 유형 | `pattern_detail` 예시 | 정책 |
|---|---|---|
| 매일 | `{}` | 적용 기간의 매일 |
| 매주 | `{"days_of_week":[1,3,5]}` | ISO 요일 1=월요일, 7=일요일 |
| 매월 | `{"day_of_month":15}` | 해당 일자가 없는 달은 건너뜀 |

검증 규칙:

- 시작일은 종료일보다 늦을 수 없다.
- 반복 시간은 운영시간과 예약 단위를 만족해야 한다.
- 기본 최대 적용 기간은 1년이다.
- 신청 시 예상 발생 건수와 충돌 목록을 계산해 사용자와 관리자에게 보여준다.
- 신청 단계에서는 실제 `reservations` 행을 만들지 않는다.

### 3.6 정기예약 승인·반려

승인은 다음을 하나의 원자적 트랜잭션으로 처리한다.

1. 신청 행을 `SELECT ... FOR UPDATE`로 잠근다.
2. 상태가 `PENDING`인지 확인한다.
3. 관리자 권한과 대상 회의실 활성 상태를 다시 확인한다.
4. 반복 규칙에 따라 발생 일시를 계산한다.
5. 모든 발생 건의 충돌을 다시 검사한다.
6. 충돌이 없으면 개별 `reservations` 행과 생성 로그를 일괄 생성한다.
7. 신청을 `APPROVED`로 변경하고 승인자·승인시각을 기록한다.
8. 전체 처리가 성공한 경우에만 커밋한다.

초기 버전의 승인 정책은 **하나라도 충돌하면 전체 승인 실패**로 한다. 관리자는 충돌 목록을 확인한 후 기간이나 요일을 조정하도록 신청자에게 반려한다. 부분 승인과 예외일 관리는 후속 기능으로 둔다.

반려 시에는 `REJECTED`, 반려 사유, 처리자, 처리시각을 기록한다. 반려 사유는 필수다.

승인된 정기예약의 전체 취소·규칙 변경은 초기 버전 범위에서 제외하며, 생성된 각 인스턴스의 개별 취소만 허용한다.

## 4. 데이터 모델

### 4.1 `rooms`

| 필드 | 타입 | 설명 |
|---|---|---|
| `room_id` | UUID PK | 회의실 ID |
| `name` | VARCHAR UNIQUE | 회의실명 |
| `room_type` | ENUM | `LARGE`, `SMALL` |
| `capacity` | INT | 1명 이상 |
| `floor` | VARCHAR | 위치 |
| `equipment` | TEXT[] | 보유 장비 |
| `is_active` | BOOLEAN | 신규 예약 가능 여부 |
| `deleted_at` | TIMESTAMPTZ NULL | 보관 처리 시각, NULL이면 정상 |
| `created_at` | TIMESTAMPTZ | 생성시각 |

`name`의 UNIQUE 정책은 보관된 회의실 이름의 재사용 여부를 명확히 해야 한다. 초기 버전은 감사 추적의 혼동을 막기 위해 보관 여부와 관계없이 이름 재사용을 금지한다.

### 4.2 `users`

일반 사용자와 관리자를 하나의 테이블에서 관리한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `user_id` | UUID PK | 내부 사용자 ID |
| `login_id` | VARCHAR UNIQUE | 로그인 ID |
| `password_hash` | TEXT | Argon2id 또는 bcrypt 해시, 평문 저장 금지 |
| `company_name` | VARCHAR | 회사명 |
| `name` | VARCHAR | 사용자명 |
| `contact` | VARCHAR NULL | 선택 연락처 |
| `role` | ENUM | `USER`, `ADMIN` |
| `status` | ENUM | `ACTIVE`, `INACTIVE` |
| `created_at` | TIMESTAMPTZ | 생성시각 |

로그인 ID 정책은 UI와 DB에서 동일하게 적용한다.

- 영문과 숫자를 모두 포함한 6자 이상, 또는 숫자 6자리
- 초기 계정도 이 규칙을 따라야 하며 `admin`, `hyunwoo`와 같은 기존 목 계정은 운영 데이터로 사용할 수 없다.

비밀번호 초기화 시 임시 비밀번호를 화면에 고정 문자열로 노출하지 않는다. 일회용 임시 비밀번호를 생성하고 최초 로그인 때 변경을 강제한다.

### 4.3 `reservations`

| 필드 | 타입 | 설명 |
|---|---|---|
| `reservation_id` | UUID PK | 예약 ID |
| `room_id` | UUID FK | 회의실 |
| `start_datetime` | TIMESTAMPTZ | 시작시각 |
| `end_datetime` | TIMESTAMPTZ | 종료시각 |
| `user_id` | UUID FK | 예약자 |
| `purpose` | TEXT | 사용목적 |
| `status` | ENUM | `CONFIRMED`, `CANCELLED` |
| `recurring_id` | UUID FK NULL | 정기예약 원본 ID |
| `created_at` | TIMESTAMPTZ | 생성시각 |
| `updated_at` | TIMESTAMPTZ | 수정시각 |

동일 정기예약이 재처리되어 중복 인스턴스를 만들지 않도록 `(recurring_id, start_datetime)` 부분 UNIQUE 제약을 추가한다.

### 4.4 `recurring_reservations`

| 필드 | 타입 | 설명 |
|---|---|---|
| `recurring_id` | UUID PK | 신청 ID |
| `room_id` | UUID FK | 회의실 |
| `pattern_type` | ENUM | `DAILY`, `WEEKLY`, `MONTHLY` |
| `pattern_detail` | JSONB | 반복 상세 |
| `start_time`, `end_time` | TIME | 반복 시간 |
| `period_start`, `period_end` | DATE | 적용 기간 |
| `purpose` | TEXT | 사용목적 |
| `applicant_id` | UUID FK | 신청자 |
| `approval_status` | ENUM | `PENDING`, `APPROVED`, `REJECTED` |
| `approved_by` | UUID FK NULL | 승인·반려 처리 관리자 |
| `approved_at` | TIMESTAMPTZ NULL | 처리시각 |
| `reject_reason` | TEXT NULL | 반려 사유 |
| `created_at` | TIMESTAMPTZ | 신청시각 |

상태 정합성 CHECK 제약을 둔다.

- `PENDING`: `approved_by`, `approved_at`, `reject_reason` 모두 NULL
- `APPROVED`: `approved_by`, `approved_at` 필수, `reject_reason` NULL
- `REJECTED`: `approved_by`, `approved_at`, `reject_reason` 필수

### 4.5 `reservation_change_logs`

| 필드 | 타입 | 설명 |
|---|---|---|
| `log_id` | UUID PK | 로그 ID |
| `reservation_id` | UUID FK | 대상 예약 |
| `action` | ENUM | `CREATE`, `CANCEL`, `EXTEND`, `SHORTEN` |
| `before_start`, `before_end` | TIMESTAMPTZ NULL | 변경 전 |
| `after_start`, `after_end` | TIMESTAMPTZ NULL | 변경 후 |
| `actor_id` | UUID FK | 수행 사용자 |
| `created_at` | TIMESTAMPTZ | 수행시각 |

감사 추적을 위해 `actor_name` 문자열 대신 `actor_id`를 사용한다. 사용자 이름의 당시 값 보존이 필요하면 별도 `actor_name_snapshot`을 함께 둔다.

### 4.6 `meeting_reservation_attendees`

| 필드 | 타입 | 설명 |
|---|---|---|
| `reservation_id` | UUID FK | 대상 예약 |
| `user_id` | UUID FK | 참석자 |
| `created_at` | TIMESTAMPTZ | 등록시각 |

`(reservation_id, user_id)`를 복합 기본키로 사용하여 중복 참석자 등록을 차단한다.

### 4.7 `admin_audit_logs`

회의실과 사용자 마스터 변경을 기록한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `audit_id` | UUID PK | 감사 로그 ID |
| `actor_id` | UUID FK | 수행 관리자 |
| `resource_type` | VARCHAR | 예: `ROOM`, `USER` |
| `resource_id` | UUID | 대상 ID |
| `action` | VARCHAR | `CREATE`, `UPDATE`, `ARCHIVE`, `RESTORE`, `DELETE` 등 |
| `before_data` | JSONB NULL | 변경 전 값 |
| `after_data` | JSONB NULL | 변경 후 값 |
| `created_at` | TIMESTAMPTZ | 수행시각 |

## 5. 상태 흐름

### 5.1 단건 예약

```text
CONFIRMED ──시간 변경──> CONFIRMED
     └──────취소──────> CANCELLED
```

`CANCELLED`에서 `CONFIRMED`로 복구하는 기능은 제공하지 않는다.

### 5.2 정기예약

```text
PENDING ──승인 트랜잭션 성공──> APPROVED
   └──────반려 사유 입력──────> REJECTED
```

처리 완료 상태를 다시 `PENDING`으로 되돌리지 않는다. 변경이 필요하면 새 신청을 생성한다.

## 6. 권한과 보안

### 6.1 인증 방식

- Next.js 서버와 Auth.js Credentials Provider를 사용한다.
- 로그인 ID와 비밀번호 검증은 서버에서만 수행한다.
- 비밀번호 해시와 DB 비밀키는 브라우저에 전달하지 않는다.
- 세션에는 최소 식별자만 저장하고, 민감 작업 시 DB에서 최신 사용자 상태와 역할을 다시 확인한다.
- 비활성 사용자는 새 세션 발급과 예약 변경을 차단한다.
- 관리자 역할은 사용자가 수정 가능한 메타데이터나 클라이언트 요청값으로 판정하지 않는다.

### 6.2 Supabase 접근 경계

초기 버전은 브라우저가 Supabase Data API에 직접 접근하지 않고 Next.js 서버 API만 사용한다.

- 가능하면 Data API를 비활성화한다.
- Data API를 유지해야 하면 `anon`, `authenticated`의 테이블 권한을 명시적으로 회수한다.
- `public` 등 노출 스키마의 모든 테이블에는 RLS를 활성화하고 기본 거부 상태를 유지한다.
- 서버 전용 비밀키나 `service_role` 키를 `NEXT_PUBLIC_` 환경변수에 두지 않는다.
- 뷰를 노출해야 하면 PostgreSQL 15+의 `security_invoker = true`를 사용한다.
- 특권 함수는 노출 스키마에 두지 않고 실행 권한을 명시적으로 제한한다.

향후 Supabase Auth 또는 브라우저 직접 접근으로 전환한다면 소유권 정책은 `(select auth.uid()) = user_id` 형태로 정의하고, UPDATE 정책에는 `USING`과 `WITH CHECK`를 모두 둔다. 해당 전환은 현재 자체 `users.user_id`와 Supabase Auth UID의 매핑 설계를 포함한 별도 마이그레이션으로 수행한다.

## 8. DB 무결성과 트랜잭션

### 8.1 중복 예약 방지

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE reservations
ADD CONSTRAINT no_overlapping_reservations
EXCLUDE USING GIST (
  room_id WITH =,
  tstzrange(start_datetime, end_datetime, '[)') WITH &&
) WHERE (status = 'CONFIRMED');
```

`[)` 범위를 사용하여 시작은 포함하고 종료는 제외한다.

### 8.2 날짜 조회

세션 시간대에 의존하는 `start_datetime::date` 비교를 피하고, 서버에서 서울 기준 하루의 시작·끝을 UTC 범위로 변환해 조회한다.

```sql
WHERE start_datetime < :to_utc
  AND end_datetime > :from_utc
```

이 방식은 자정을 넘는 예약을 향후 허용할 경우에도 올바르게 겹침을 조회한다.

### 8.3 이력 기록

- 예약 변경과 로그 INSERT는 동일 트랜잭션에서 수행한다.
- 애플리케이션을 우회한 변경까지 반드시 기록해야 한다면 DB 트리거를 사용한다.
- 트리거를 사용할 경우 요청 수행자 ID를 안전하게 전달하는 방식과 실패 정책을 별도 검증한다.

## 11. 비기능 요구사항

- 예약 생성·변경·승인 API는 원자적으로 처리한다.
- 동일 요청 재전송에 대비해 승인·취소는 멱등성을 보장한다.
- 예약현황 조회는 날짜 범위 인덱스를 사용하고 페이지 또는 범위를 제한한다.
- 개인정보가 포함된 응답에는 공유 캐시를 사용하지 않는다.
- 관리자 작업은 수행자와 시각을 감사 로그에 남긴다.
- 운영 DB 백업과 복구 절차를 마련하고 정기적으로 복구를 시험한다.
- 오류 메시지는 내부 스키마나 SQL을 노출하지 않는다.

## 12. 테스트 기준

최소한 다음 자동화 테스트를 포함한다.

- 경계가 맞닿은 예약은 성공하고 1분이라도 겹치는 예약은 실패
- 동시에 같은 슬롯을 요청하면 하나만 성공
- 취소된 슬롯은 다시 예약 가능
- 다른 사용자의 예약 변경·취소는 403
- 비활성 회의실 예약은 실패
- 과거, 운영시간 외, 30분 단위 위반, 최대시간 초과 예약은 실패
- 정기예약 반복 날짜 계산: 월말, 윤년, 존재하지 않는 매월 일자
- 정기예약 승인 중 하나라도 충돌하면 아무 인스턴스도 생성되지 않음
- 동일 승인 요청 재전송 시 중복 인스턴스가 생성되지 않음
- 서울 날짜 경계와 UTC 변환
- 일반 사용자의 관리자 API 접근 차단
- Supabase 노출 스키마에 대한 익명·인증 역할의 직접 접근 차단
- 사용 이력이 없는 회의실은 물리 삭제되고 관련 감사 로그가 기록됨
- 사용 이력이 있는 회의실은 보관 처리되고 기존 예약 조회 결과의 참조가 유지됨
- 향후 확정 예약 또는 승인 대기 신청이 있는 회의실의 삭제 요청 차단
- 보관 회의실이 일반 예약 목록에서 제외되고 관리자가 복원 가능
