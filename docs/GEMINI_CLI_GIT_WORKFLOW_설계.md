# Gemini CLI Git 위임 워크플로우 — 설계안 (구현 보류)

> 상태: **설계 단계**. 아직 `.github/workflows`에 반영하지 않았습니다. 승인 후 구현합니다.

## ① 현황 구조 분석

- 저장소(`mohenz/pmotools`)에는 현재 `.github/workflows`가 없어 GitHub Actions 기반 자동화가 전무한 상태입니다.
- git commit/push/pull은 현재 사람 또는 Claude Code 세션이 직접 수행하고 있습니다.
- 앱 코드에는 이미 `@google/genai` 의존성이 있어 Gemini API 자체는 프로젝트에 낯설지 않으나, git 작업을 위임하는 CLI 자동화는 신규 영역입니다.
- 브랜치 보호 규칙(필수 리뷰, 상태 체크 등) 현황은 저장소 설정에서 별도 확인이 필요합니다(현재 세션 권한으로는 미확인).

## ② 이해관계자 권력 구조

| 이해관계자 | 권한/역할 | 이 워크플로우에서의 관계 |
| --- | --- | --- |
| Repo Owner/Maintainer | Secret 관리, 브랜치 보호 설정 | 최종 승인자, GEMINI_API_KEY 발급·등록 책임 |
| 개발자 | PR 리뷰, merge 승인 | Gemini CLI가 낸 PR의 게이트키퍼 |
| Gemini CLI(비인간 행위자) | 위임받은 범위 내 코드 수정·commit·push | 권한은 워크플로우가 부여한 범위로 엄격히 제한 |
| GitHub Actions(플랫폼) | 실행 격리, 토큰 스코프 제공 | 신뢰 경계(trust boundary) |

## ③ 제약 조건

- **Budget**: Gemini API 호출 비용 — 사용 빈도 미확정, 초기엔 사용량 모니터링 필요(정량 데이터 없음).
- **Schedule**: 특정 마감 없음, 온디맨드 성격.
- **Political/Governance (조직/정치 리스크)**: AI 에이전트에게 push 권한을 부여하는 것 자체가 SI/계열사 환경에서는 "AI 생성 변경의 책임 소재" 이슈로 이어질 수 있음. 내부 보안·감사 정책과의 정렬 확인 필요.
- **Technical**: Gemini CLI 인증 방식(API Key vs OAuth), CI 비대화형 실행 옵션(`--yolo` 등 승인 프롬프트 생략 옵션) 필요. 모델 출력이 불안정할 경우 커밋 메시지 생성 실패 대비 fallback 필요.

## ④ 시나리오 (3안)

| # | 시나리오 | 설명 |
| --- | --- | --- |
| A | **수동 트리거** (`workflow_dispatch`) | 담당자가 Actions 탭에서 작업 지시를 입력해 수동 실행. Gemini CLI는 `gemini/*` 브랜치에서만 작업 후 PR 생성. |
| B | **PR 코멘트 트리거** | PR에 `/gemini fix` 같은 코멘트를 달면 자동 실행. 리뷰 루프에 통합되지만 코멘트 권한자 판별(스푸핑 방지) 로직 필요. |
| C | **완전 자동** (스케줄/커밋 훅) | 사람 개입 없이 주기적/이벤트 기반으로 상시 실행. |

## ⑤ Impact Matrix

| 시나리오 | 자동화 수준 | 통제 리스크 | 구현 난이도 | 감사 대응 용이성 | 권장도 |
| --- | --- | --- | --- | --- | --- |
| A. 수동 트리거 | 낮음 | 낮음 | 낮음 | 높음 | ★★★ |
| B. PR 코멘트 | 중간 | 중간 (권한자 검증 필요) | 중간 | 중간 | ★★ |
| C. 완전 자동 | 높음 | 높음 (통제 부재) | 높음 | 낮음 | ★ |

## ⑥ Recommended Option

**A안(수동 트리거) + PR 기반 반영**을 권장합니다.

- 근거 1: 도입 초기 AI 에이전트의 산출물 신뢰도가 검증되지 않았으므로, "사람이 트리거 → 사람이 병합 승인"하는 이중 게이트가 사고 발생 시 책임 소재를 명확히 함.
- 근거 2: 보호 브랜치(main)에는 어떤 시나리오에서도 직접 push를 허용하지 않고 PR 경유만 허용 — 이는 A/B/C 공통 원칙으로 유지.
- 근거 3: A안은 구현·검증 난이도가 가장 낮아 파일럿 검증 후 B안으로 단계적 확장이 가능한 구조(확장성 확보).

## ⑦ 즉시 실행 Step

1. Repo Owner가 `GEMINI_API_KEY` Secret 등록 담당자 지정
2. `main` 브랜치 보호 규칙 현황 확인 (PR 필수 여부)
3. A안 워크플로우 초안 구현 승인 여부 결정 (승인 시 바로 구현 가능한 초안 보유 중)
4. 낮은 리스크 작업(예: 오탈자 수정, 문서 정리) 1건으로 파일럿 실행
5. 파일럿 결과 리뷰 후 정식 채택/미채택 및 B안 확장 여부 결정
