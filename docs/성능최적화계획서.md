# PMO CONTROL 성능 최적화 계획서

- 대상 프로젝트: `projectmgmt`
- 작성일: 2026-08-13
- 기준 환경: Next.js 15.5.22, React 19, Auth.js 5, Prisma 7, PostgreSQL 18
- 로컬 실행: `http://localhost:3020`

## 1. 목적

사이트 전반의 느린 반응 원인을 측정 결과에 근거해 구분하고, 개발 환경과 운영 환경 모두에서 체감 성능을 개선한다. 인증 보안 수준이나 데이터 정합성을 낮추는 방식은 사용하지 않는다.

## 2. 현재 측정 결과

| 대상 | 측정 결과 | 비고 |
|---|---:|---|
| `/portfolio` 최초 요청 | 약 11.98초 | 라우트 컴파일 7.8초 포함 |
| `/portfolio` 컴파일 후 서버 응답 | 약 2.05초 | 브라우저 완료 체감 약 2.63초 |
| `/login` 최초 요청 | 약 9.33초 | 개발 모드 컴파일 포함 |
| `/login` 컴파일 후 | 약 0.29~0.33초 | 반복 요청 기준 |
| 로그인 인증 처리 | 약 0.77~1.34초 | bcrypt cost 12 포함 |
| `/api/auth/session` | 약 0.13~0.56초 | 화면 전환 중 반복 호출 관찰 |
| Prisma 단일 조회 | 최초 465ms, 이후 3~9ms | 연결 초기화 이후 정상 |

| 프로덕션 로그인 화면 | 약 0.25~0.53초 | Vercel 배포 환경 |

브라우저 콘솔 오류와 PostgreSQL 장기 실행 쿼리는 발견되지 않았다. 로컬 PostgreSQL은 `localhost:55432`에서 정상 응답했다.

## 3. 원인 분석

### 3.1 Next.js 개발 모드 컴파일

현재 `next dev`로 실행되며, 처음 방문하는 라우트는 요청 시점에 컴파일된다. 최초 화면 지연의 가장 큰 원인이다. 개발 서버 Node 프로세스는 진단 당시 약 1.4GB의 메모리를 사용했다.

### 3.2 읽지 않은 쪽지 요청 중복 (코드 확인 완료)

`app/layout.tsx:27,30`에서 `<AppNavigation area="sidebar">`와 `<AppNavigation area="workspace">`를 형제로 렌더링한다. `components/AppNavigation.tsx:14-17`의 `useEffect(() => { ... fetch("/api/v1/messages/unread-count") ... }, [session?.user, pathname])`가 두 인스턴스에 각각 독립적으로 존재해 서로의 호출을 인지하지 못한다. 즉 라우트가 바뀔 때마다 최소 2회의 병렬 fetch가 발생하며, 각 fetch는 `app/api/v1/messages/unread-count/route.ts`에서 `getLocalContext()`(JWT 디코딩) → `unreadMessageCount()`(DB 조회)를 각각 수행한다. 두 인스턴스 사이에 캐시나 dedup 로직이 전혀 없다.

### 3.3 Auth.js 세션 확인 반복 (코드 확인 완료)

`components/AuthSessionProvider.tsx`는 `<SessionProvider>`에 `session` prop을 전달하지 않는다. 서버에서 확인한 초기 세션을 넘기지 않으므로 클라이언트 마운트 시 `/api/auth/session`을 무조건 fetch한다. `useSession()`은 `UserMenu.tsx`, `AppNavigation.tsx`(2곳)에서 호출되며 이들은 동일 Context를 구독하므로 각자 추가 fetch를 만들지는 않지만, next-auth `SessionProvider`의 기본값(`refetchOnWindowFocus: true`)이 켜져 있어 창 포커스가 돌아올 때마다 세션 재검증이 발생한다. JWT 전략이라 DB 조회는 없지만 요청 자체의 누적 횟수가 체감 지연에 영향을 준다.

### 3.4 동적 서버 렌더링과 다중 쿼리 (코드 확인 완료, 범위 확장)

`grep` 결과 `export const dynamic = "force-dynamic"`이 포트폴리오뿐 아니라 `/`, `/items`, `/calendar`, `/meetrooms`, `/weekly-reports`, `/weekly-progress`, `/staff-changes`, `/settings/*`, `/activity-logs` 등 총 21개 라우트에 적용되어 있다. 즉 앱 내 거의 모든 화면이 정적 최적화 없이 매 요청마다 전체 서버 렌더링을 수행한다. 포트폴리오 화면(`app/portfolio/page.tsx`)은 `getPortfolioDashboard()`에서 `Promise.all`로 6개 쿼리(주차 조회, 보고 건수, 평균 공정률, 지연 건수, 인력 증감 집계, 열린 이슈 수)를 병렬 실행하고 `listWeeklyProgress()`가 `include`로 주차·그룹 조인을 추가로 실행한다. 웜 상태 DB 처리시간은 짧아 현재의 핵심 병목은 아니지만, 21개 라우트 전체가 캐시 없이 서버 렌더링 + 인증 처리 비용을 매번 합산한다는 점에서 6단계(캐시 최적화) 대상 범위가 문서 초안보다 넓다.

### 3.5 로그인 비밀번호 검증

로그인 시 bcrypt cost 12로 비밀번호를 검증하므로 약 1초가 소요될 수 있다. 이는 보안을 위한 의도적인 비용이며 강도를 낮추지 않는다.

### 3.6 미들웨어와 페이지의 JWT 이중 디코딩 (신규 발견)

`middleware.ts`는 `auth()`로 모든 요청을 감싸며 matcher가 `_next/static`, `_next/image`, `favicon.ico`만 제외하므로(`/((?!_next/static|_next/image|favicon.ico).*)`) 정적 자산을 제외한 모든 페이지·API 요청에서 JWT를 디코딩한다. 그런데 서버 컴포넌트/라우트 핸들러 쪽에서도 `getLocalContext()`(`lib/server/context.ts:7`)가 `auth()`를 다시 호출한다. 예를 들어 `/api/v1/messages/unread-count` 요청 1건은 미들웨어에서 1회, 라우트 핸들러 내부에서 1회, 총 2회 JWT 디코딩을 수행한다. 개별 비용은 작지만 21개 force-dynamic 라우트 전체와 3.2의 반복 호출에 곱해져 누적된다. 4단계(초기 세션 서버 주입) 작업 시 미들웨어와 페이지의 인증 책임 분리를 함께 정리할 필요가 있다.

### 3.7 쓰기 경로의 감사로그 N+1 조회 (신규 발견, 범위 외 참고사항)

`lib/server/db-pg.ts:35-57`의 `writeAuditLog()`는 호출될 때마다 내부적으로 `actorNameOf(actorId)`를 먼저 `await`하는데, 이는 `prisma.user.findUnique()`로 별도 DB 왕복을 수행한 뒤에야 `auditLog.create()`를 실행한다. `saveReport`, `createProgress`, `updateProgress`, `saveStaffChange` 등 거의 모든 쓰기 API가 이 경로를 거치므로, 각 등록·수정 요청마다 감사로그 저장을 위한 순차 조회 1회가 추가된다. 현재 측정표(2장)는 읽기/페이지 로드 경로 위주라 이 비용이 반영되어 있지 않다. 체감 지연의 주원인은 아니지만, 8단계 최종 검증에서 이슈 등록·수정, 주간실적, 인력변동 등 쓰기 동작의 응답시간도 별도로 측정해 반영할 것을 권장한다. actorName은 감사로그 스냅샷 목적상 필요하므로 제거 대상이 아니라 "actorId만 저장하고 조회 시점에 join"으로 바꿀지 여부는 사용자 판단이 필요하다.

## 4. 성능 목표

| 지표 | 현재 | 목표 |
|---|---:|---:|
| 개발 모드 최초 화면 | 4~12초 | 2~4초 이하 |
| 컴파일 후 화면 이동 | 약 2초 | 500ms 이하 |
| 로그인 처리 | 0.8~1.3초 | 1초 내외 유지 |
| unread-count 호출 | 화면당 다수 | 초기 화면당 1회 이하 |
| 세션 API 호출 | 화면 전환 중 반복 | 최초 0~1회, 일반 이동 시 제거 |
| 프로덕션 주요 화면 TTFB | 별도 기준 필요 | 500ms 이하 |

## 5. 단계별 최적화 계획

### 1단계: 성능 측정 기준 확립

- 대상 경로: `/`, `/portfolio`, `/calendar`, `/meetrooms`, `/items`, `/login`.
- 대상 API: `/api/auth/session`, `/api/v1/messages/unread-count`, `/api/health`.
- 최초 요청과 웜 요청을 분리한다.
- 서버 응답, 브라우저 화면 표시, DB 처리시간, API 호출 횟수를 기록한다.
- 개발 모드와 프로덕션 모드를 같은 데이터 조건에서 비교한다.

### 2단계: 개발 서버 Turbopack 전환 (완료, 2026-08-15)

- `dev`와 `local` 스크립트를 `next dev --turbopack --port 3020`으로 변경했다.
- 호환성 문제 대비용으로 기존 Webpack 명령을 `dev:webpack` 스크립트로 별도 유지했다.
- 검증 결과: 미들웨어 컴파일 1.7초, `/login` 최초 컴파일 8초(기존 Webpack 기준 9.33초와 유사한 수준, 뚜렷한 개선은 재측정 필요), 웜 요청 0.39~0.78초. Turbopack 자체로 인한 컴파일 오류나 호환성 문제는 발견되지 않았다.
- `npm.cmd run lint`(tsc --noEmit), `npm.cmd run test`(vitest, 26개 통과) 모두 정상 통과했다.
- `/api/health` 503 응답은 이번 검증 세션에서 로컬 PostgreSQL(`db:local:start`)을 기동하지 않아 발생한 것으로, Turbopack과 무관하다.
- 미완료 항목: 인증이 필요한 라우트(`/portfolio`, `/calendar` 등)의 최초 컴파일 시간과 실제 코드 변경에 대한 HMR 동작은 로그인 세션이 있는 상태에서 별도 검증이 필요하다.

### 3단계: unread-count 단일 조회 구조 도입 (완료, 2026-08-15)

- `components/UnreadMessageProvider.tsx` 신설: `app/layout.tsx`에서 `AuthSessionProvider` 안, `AppNavigation` 렌더링 이전에 한 번만 배치했다.
- `AppNavigation.tsx`는 자체 `useEffect`/`fetch`를 제거하고 `useUnreadMessageCount()`로 Context 값을 공유한다. 사이드바·워크스페이스 두 인스턴스가 이제 같은 값을 참조하며 각자 fetch하지 않는다.
- 마운트 시 1회 조회 후 경로 변경으로는 재조회하지 않으며, 60초 주기 폴링만 유지한다(문서 지정 범위인 30~60초 내 상한값 선택 — 불필요한 트래픽보다 지연 허용이 낫다고 판단).
- `screens/MessagesScreen.tsx`의 쪽지 열람(`MessageRow.view`)이 읽음 처리에 성공하면 `refresh()`를 호출해 즉시 무효화한다. 발신은 수신자의 카운트에만 영향을 주므로 발신자 쪽 무효화는 불필요.
- 효과: 화면 전환당 unread-count 호출이 최소 2회(병렬)에서 0회(세션당 최초 1회 + 60초 폴링)로 감소.

### 4단계: Auth.js 세션 요청 최소화 (완료, 2026-08-15)

- `app/layout.tsx`를 async 서버 컴포넌트로 전환해 `auth()`를 1회 호출하고 결과를 `AuthSessionProvider`에 전달한다.
- `AuthSessionProvider`가 `SessionProvider`에 `session` prop과 `refetchOnWindowFocus={false}`를 전달하도록 수정했다. 초기 세션이 서버에서 주입되므로 클라이언트 마운트 시의 `/api/auth/session` 요청과 포커스 복귀 시 재검증이 모두 제거된다.
- 미들웨어는 기존대로 전역 로그인 게이트 역할을 유지하고, `getLocalContext()` 기반 API 권한 검사(관리자 전용 API의 `assertAdmin` 등)는 그대로 유지했다 — 인증 경로를 줄이되 권한 검사 자체는 생략하지 않는다는 원칙(7장)을 지켰다.

### 5단계: 화면 전환 체감 개선 (완료, 2026-08-15)

- `/portfolio`, `/calendar`, `/meetrooms`, `/items`에 `loading.tsx`를 추가하고, `app/globals.css`에 `.skeleton` 셰이머 애니메이션과 `.skeleton-title`/`.skeleton-kpi`/`.skeleton-card`/`.skeleton-row` 유틸리티를 추가해 각 화면의 실제 레이아웃(카드 수, 그리드 구조)에 맞춘 스켈레톤을 구성했다.
- pending 표시 점검 결과 대부분의 제출 버튼은 이미 `disabled` + "저장 중…" 형태로 표준화되어 있었다. 예외 2건(`WorkForms.tsx`의 `WeekCreateForm`, `WeekStatusButton.tsx`)이 텍스트 전환 없이 `disabled`만 사용하고 있어 동일 패턴으로 맞췄다.
- `router.refresh()` 호출 13건을 전수 점검한 결과, 전부 성공한 뮤테이션 직후 같은 화면의 서버 데이터를 다시 읽어오는 정상적인 용도였다 — pathname 변경이나 포커스 등 불필요한 트리거로 호출되는 사례는 없어 별도 수정하지 않았다.
- 무거운 클라이언트 컴포넌트 동적 로딩을 검토했으나, `exceljs`(엑셀)와 `rrule`(반복 일정)은 이미 서버 전용 모듈(`lib/server/calendar-excel.ts`, `lib/server/calendar.ts`)에서만 사용되어 클라이언트 번들에 포함되지 않았고, `CalendarModal`/`MeetingRoomScreen` 등 클라이언트 컴포넌트도 소규모라 별도 동적 로딩 대상이 없었다. `npm.cmd run build` 결과 First Load JS가 103~123kB 수준으로 이미 가벼움을 확인했다.

### 6단계: 서버 조회 및 캐시 최적화 (완료, 2026-08-15)

- 포트폴리오 집계(`getPortfolioDashboard`)와 주간실적 목록(`listWeeklyProgress`)의 병합 가능성을 검토했으나, `docs/작업기록_20260809_Firestore잔재정리.md`에 기록된 과거 작업에서 이미 "전체 로드 후 JS 집계"를 "DB `count`/`aggregate`/`groupBy`"로 전환한 이력이 있었다. 이를 다시 합치면 전체 이력 데이터를 JS로 끌어와 평균을 계산하는 이전 방식으로 되돌아가 확장성이 나빠지므로 **병합하지 않기로 결정**했다(현행 유지가 맞는 판단).
- `unstable_cache` + `revalidateTag`로 다음 항목에 짧은 캐시를 적용하고, 관련 쓰기 API 성공 시 즉시 무효화하도록 배선했다.
  - `getCodeOptions`(공통코드/트랙) — 30초, 그룹·코드 생성/수정 4곳에서 무효화 (`lib/server/common-codes.ts`)
  - `getProjectInformation`(프로젝트 기본정보) — 30초, 저장 시 무효화 (`lib/server/project-information.ts`)
  - `listProjectWeeks`(프로젝트 주차) — 30초, 주차 등록/마감 시 무효화 (`lib/server/work-management.ts`)
  - `getPortfolioDashboard`(포트폴리오 KPI) — 15초, 주간보고 저장·주간실적 등록/수정·인력변동 저장(`work-management.ts`)과 이슈 등록·상태변경·보관(`items.ts`)에서 무효화. 순환 참조를 피하려고 태그 헬퍼를 `lib/server/cache-tags.ts`로 분리했다.
- 회의실 예약/가용성 조회와 권한 검사(`getMemberRole` 등)에는 원칙(7장)에 따라 캐시를 적용하지 않았다.
- `npm.cmd run lint`, `npm.cmd run test`, `npm.cmd run build` 모두 통과했으나, 시드 계정 비밀번호를 알 수 없어 브라우저 로그인 상태에서 "저장 직후 화면에 즉시 반영되는지"까지는 이번 세션에서 검증하지 못했다 — 8단계 최종 확인 항목으로 남긴다.

### 7단계: Prisma와 PostgreSQL 세부 점검 (완료, 2026-08-15)

- `prisma/schema.prisma`의 인덱스를 전수 점검했다. `Message(receiverId, isRead)`, `Item(projectId, status)`/`Item(projectId, archivedAt)`, `WeeklyProgress/WeeklyReport/StaffChange(weekId, ...)` 등 주요 조회 경로에 이미 인덱스가 있었다 — 8/9 작업 이력에서 선행 정리된 결과로 보인다.
- 개선 여지 1건 발견: `getPortfolioDashboard`의 `openIssues` 카운트가 `{projectId, archivedAt, status}` 3개 조건을 동시에 걸지만 인덱스는 2개(`[projectId,status]`, `[projectId,archivedAt]`)로 나뉘어 있어 복합 인덱스 하나만큼 효율적이지 않다. 다만 이는 **스키마 마이그레이션**이 필요한 변경이고, 현재 웜 상태 쿼리 시간(12~35ms)이 이미 빠르며 원칙(7장) "측정 결과 없이 범위를 확대하지 않는다"에 해당해 **이번 세션에서는 적용하지 않고 제안으로만 남긴다**. 필요하면 사용자 승인 후 별도 마이그레이션으로 진행.
- 중복/N+1 조회를 코드 전수 검색으로 확인했다. 진짜 순차 반복 쿼리는 2곳: `lib/server/meeting-rooms.ts`(반복 회의 생성 시 회차별 충돌검사)와 `lib/server/calendar-excel.ts`의 `applyImport`(엑셀 일정 일괄 반영). 둘 다 예약 충돌 검증이나 행별 감사로그 기록처럼 정합성 요건상 순차 처리가 불가피한 로직이라 원칙(7장)에 따라 수정하지 않았다.
- `listMessages`의 `include: { sender: true, receiver: true }`가 `name`/`userId` 두 필드만 쓰면서 `passwordHash` 등 전체 컬럼을 불러오고 있어 `select`로 축소했다(`lib/server/messages.ts`). 서버 밖으로 나가는 데이터는 원래도 없었지만 불필요한 컬럼 전송을 줄였다.
- `listItems`의 페이지네이션(`pageSize` 10~100 clamp, `page` 1~totalPages clamp, `skip = (page-1)*pageSize`)을 검증한 결과 경계 오류 없음을 확인했다.
- Prisma Client 싱글턴(`lib/server/db-pg.ts`)과 어댑터/커넥션 풀 구조는 변경하지 않았다.

## 7. 적용 원칙

- bcrypt cost를 낮춰 성능을 확보하지 않는다.
- 인증·권한 검사를 생략하거나 클라이언트에만 위임하지 않는다.
- 회의실 예약 충돌, 권한, 감사 로그의 정합성을 성능과 교환하지 않는다.
- 측정 결과 없이 캐시 범위를 확대하지 않는다.
- 각 단계는 독립적으로 검증하고 문제가 있으면 단계 단위로 되돌릴 수 있게 커밋한다.

## 8. 현재 결론

현재 체감 지연의 주원인은 PostgreSQL이나 bcrypt가 아니라 Next.js 개발 모드의 최초 컴파일과 중복 클라이언트 요청이다. 우선순위는 Turbopack 전환, unread-count 단일화, 초기 세션 서버 주입 순이다. DB 최적화는 이 세 작업 이후 재측정 결과에 따라 진행한다.

### 8.1 2026-08-15 진행 결과 요약

2~7단계 코드 작업을 모두 완료했다. `npm.cmd run lint`/`test`/`build`는 전부 통과했고, Turbopack 전환·unread-count 단일화·세션 초기 주입·loading.tsx·짧은 캐시(공통코드/프로젝트정보/주차/포트폴리오 KPI, 태그 기반 무효화 포함)를 코드에 반영했다. 다만 이번 세션은 시드 계정 비밀번호를 알 수 없어 **실제 브라우저 로그인 상태에서의 검증(권한별 화면 확인, 기능 회귀 테스트, 캐시 무효화가 저장 직후 화면에 반영되는지, 콘솔 오류 확인)은 수행하지 못했다.** 이는 원칙(7장)이 요구하는 "각 단계 독립 검증"의 마지막 조각이므로, 사용자가 실제 계정으로 로그인해 아래를 확인해 주길 권장한다.

- 공통코드/프로젝트 정보/프로젝트 주차를 수정한 직후 화면에 즉시 반영되는지(캐시 무효화 정상 동작 확인)
- 이슈 등록·상태변경, 주간실적/보고/인력변동 저장 후 `/portfolio` KPI가 갱신되는지
- 쪽지 읽음 처리 후 사이드바 배지 숫자가 즉시 줄어드는지
- 관리자/운영자/일반 권한별 화면 접근 제어에 이상이 없는지
- 브라우저 콘솔에 새로운 오류가 없는지

추가로 인덱스 개선 제안 1건(7단계, `Item(projectId, archivedAt, status)` 복합 인덱스)은 스키마 마이그레이션이 필요해 이번 세션에서는 적용하지 않았다 — 진행 여부는 별도 승인이 필요하다.
