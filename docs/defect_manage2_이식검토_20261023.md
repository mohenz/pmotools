### 1.3 API (`/api/*`)

- 결함: `GET /defects`(페이징·필터, pageSize 최대 200), `GET /defects/:id`, `GET /defects/summary`(통계용 전체), `GET /defects/export`, `GET /defects/action-recheck`(관리자·조치자), `POST /defects`, `PUT /defects/:id`, `DELETE /defects/:id`(관리자, 논리 삭제)
- 공통코드: `GET/POST/DELETE /common-codes`(쓰기는 관리자)
- 설정: `GET/PUT /settings/global`
- 오류 로그: `GET`(관리자)/`POST /error-logs`
- 인증·사용자: `POST /auth/login`, `/signup`, `/logout`, `GET /auth/me`, `GET/POST/PUT/DELETE /users`, `POST /users/reset-password`
- 변경 요청은 `Origin`·`Sec-Fetch-Site` 검사와 JSON 콘텐츠 타입을 요구한다.

### 1.4 기능

1. **인증·권한:** 역할 테스터·조치자·관리자. 가입 시 테스터·조치자만 선택. 최초 로그인 비밀번호 변경 강제.
2. **결함 등록·수정:** 제목 5자 이상, 화면 URL은 http/https만, 이미지는 png/jpeg/webp/gif data URL 또는 URL. 등록 시 상태는 `Open`, 등록자는 로그인 사용자 이름.
3. **권한 규칙(서버):** 테스터는 조치 정보(담당자, 상태, 결함식별, 조치내용·예정일·시작·종료)를 등록·변경할 수 없고, 심각도는 관리자나 등록자 본인만 변경할 수 있다. 삭제는 관리자만.
4. **목록:** 결함 ID, 테스트구분, 심각도, 상태(`조치 미완료` 프리셋 포함), 결함식별, 등록자, 기간 등 복합 필터. 10페이지 단위 페이징. 결함 번호 복사. CSV(UTF-8 BOM) 다운로드. 조치예정일 열.
5. **대시보드:** 등록자별·심각도별 표, 심각도별 조치 현황, 상태별 가로 스택 바, 조치 미완료 카드(클릭 시 목록 이동), 조치완료율. 요약 데이터는 1000건 단위로 끝까지 조회.
6. **조치자 현황:** 조치자별 상태별 건수, 완료 건수, 완료율, 미배정 행.
7. **조치 재확인:** 상태가 완료(`Closed`·`Resolved`·`Staging`)인데 결함식별·조치내용이 모두 빈 결함 목록.
8. **관리:** 공통코드(코드 추가·삭제), 활성 테스트구분 설정, 사용자 관리(역할·부서·상태·비밀번호 초기화), 저장 오류 로그 조회, 사용자 매뉴얼(앱 안 렌더링).
9. **외부 연동:** 테스트 대상 사이트에 위젯을 붙이면 버튼 하나로 화면을 캡처해 등록 팝업(전용 폼, 사이드바 없음)을 열고 URL·제목·UserAgent를 자동 전달한다. Chrome 확장은 현재 탭을 캡처해 `?mode=standalone#register` 탭을 연다. 두 방식 모두 등록 탭의 서버 인증 쿠키를 사용한다.

### 1.5 이식에 영향을 주는 특징

- 한 프로젝트만 전제한다(프로젝트 개념 없음).
- 결함과 사람의 관계가 **이름 문자열**(`creator`, `assignee`)이고, 같은 이름·미등록 이름 처리 규칙이 없다. 문서(`db_schema.md`)에도 "사용자명 기반 관계는 별도 승인된 데이터 매핑 전까지 유지"로 적혀 있다.
- ID가 `Date.now()`/난수 BIGINT다.
- 캡처 이미지가 base64로 `TEXT` 컬럼과 요청 본문(JSON 30MB 제한)에 들어간다.
- 상태는 영문 문자열이며 전이 규칙은 없고 권한 검사만 있다.
- 사용자·세션·로그인이 자체 구현이다.

## 3. 이식 방안

### 방안 A — pmotools에 새 모듈로 재구현 (권장)

- 새 모델(`Defect`, `DefectHistory`)과 `/mp-defects` 계열 화면·API를 만든다. 사용자·프로젝트·공통코드·증적 저장소·통계 화면 패턴을 재사용한다.
- 장점: 로그인·프로젝트 범위·디자인·권한이 하나로 통합되고, 결함–사람 관계가 사용자 id로 바뀐다. 이후 단위테스트 결함·WBS·요구사항과 연결하기 쉽다.
- 단점: 공수가 가장 크다. 프런트 전체를 다시 작성한다.

### 방안 B — 별도 서버로 두고 연결

- defect_manage2를 그대로 운영하고 메뉴에서 링크 또는 프록시로 연결한다.
- 장점: 가장 빠르다.
- 단점: 로그인·사용자 DB·디자인이 이중이 되고 프로젝트·사용자와 연결할 수 없다. SSO를 따로 구현해야 한다. 장기적으로는 비용이 더 든다.

### 방안 C — 단계적 병행 (A의 이행 방식)

- A로 구현하는 동안 외부 위젯·확장 프로그램은 기존 서버로 계속 받고, 데이터 이관과 검증이 끝난 시점에 위젯·확장의 호출 주소를 pmotools로 바꾼다.
- 병행 기간 동안 신규 결함이 두 곳에 생기지 않도록 기존 서버를 읽기 전용으로 바꾸는 시점을 정해야 한다.

권고: **A를 C 방식으로 진행.** B는 임시 연결이 필요할 때만 고려한다.

### 4.1 데이터 모델 매핑

### 4.2 역할 매핑 (안)

- 테스터 → 프로젝트 구성원(`MEMBER`)
- 조치자 → 프로젝트 구성원 중 조치 권한이 부여된 직무(직무 권한 모델에 `defect 조치` 권한을 추가할지 결정)
- 관리자 → `ADMIN`·`SUPER_ADMIN`(기존 단위테스트의 관리자 권한 확대 방침과 일치)

### 4.3 화면·API (안)

- `/mp-defects`: 목록(필터·페이징·결함번호 복사·엑셀), `/mp-defects/new`, 결함 상세·수정, 통계(대시보드), 조치자 현황, 조치 재확인.
- 메뉴: `AppNavigation`에 그룹 추가, 메뉴 노출 설정에 등록.
- API: `/api/v1/mp/defects/*`(기존 `/api/v1/mp/ut/*`의 라우팅·권한 패턴 사용).
- 통계: 이미 만든 `mp-ut/stats`의 표·막대 구성 패턴을 재사용.

### 4.4 캡처·외부 연동

- 이미지는 base64 JSON 대신 `multipart/form-data` 업로드로 받아 증적 저장소에 파일로 저장한다.
- Chrome 확장은 `manifest.json`의 호스트·열기 주소를 pmotools 주소와 등록 경로로 바꾼다. 현재 확장은 `http://127.0.0.1:3000/?mode=standalone#register`를 연다.
- 위젯은 외부 사이트에서 `window.open` + `postMessage`(`DEFECTFLOW_READY`/`DATA`/`CLOSE`)로 데이터를 넘기는 구조다. 새 구조에서는 **허용 출처 목록 검사**, 메시지 스키마 검증, 로그인 세션 확인(요청 위조 방지)을 새로 설계해야 한다.
- 배포 환경 제약: 증적 저장소는 서버 디스크 전제(`UT_EVIDENCE_ROOT`)라 Vercel 같은 서버리스에서는 쓸 수 없다. 운영 환경을 확인해야 한다.

### 8.3 테스트 단계를 공통코드로 관리

- 기존 방식을 따른다. 단위테스트의 케이스유형(`ut_case_type`), 반려 사유(`ut_reject_reason`) 등이 이미 프로젝트별 공통코드 그룹으로 관리된다(`lib/server/mp/ut/common.ts`).
- 새 그룹(예: `test_stage`)을 만들고 코드마다 이름, 순서, 사용 여부를 프로젝트 관리자가 화면에서 추가·변경·비활성화한다. 프로젝트별로 다른 단계 구성을 쓴다.
- 케이스와 결함은 단계 코드를 참조(`testStageCodeId`)한다. 단계가 바뀌어도 이미 쓰인 단계는 비활성으로만 바꿔 과거 데이터의 표시가 유지된다(공통코드 기존 동작과 동일).
- 새 프로젝트 생성 시 쓸 수 있는 **기본 템플릿 몇 가지**(예: 단위·통합·3자·오픈형)를 시드로 제공하는 것을 검토한다.
- 현재 코드의 걸림돌: 단위테스트 대상 판정이 `UT_TARGET_STAGE = "개발"`(최상위 WBS 이름) + `isUnitTestTarget`(불린 1개)에 묶여 있다. 통합1차·2차처럼 단계가 여러 개가 되면 **어떤 WBS Task가 어느 테스트 단계의 대상인지**를 따로 표현해야 한다(예: Task–단계 연결 테이블). 이는 미결 사항이다(8.6).
- 통계보기는 단계를 **동적 열/필터**로 받는다. 단계가 프로젝트마다 다르므로 화면에 단계 이름을 하드코딩하지 않는다.

### 8.4 결함 모델 — 독립 결함 모듈 (결정 4, 2026-10-24)

앞서 제시했던 두 안(`ut_defects` 확장 / 새 통합 테이블) 중 **새 독립 모듈**(두 번째 안의 방향)로 정해졌다.

- 새 결함 테이블(프로젝트 범위)과 이력 테이블, 독립 메뉴·화면(등록·목록·상세·조치)을 만든다. defect_manage2의 필드를 기반으로 한다: 제목, 재현 단계, 심각도, 우선순위, 상태, 결함식별, 환경, 화면 메뉴·화면명·URL, 증적(파일), 담당자·등록자(사용자 id), 조치 내용·예정일·시작일·종료일.
- 테스트와는 **선택적 연결 키**로만 이어진다(없어도 결함이 존재한다): 테스트 단계 코드(공통코드 `test_stage`), 테스트 케이스, 수행 차수, WBS Task, 요구사항. 연결은 id로 저장하고 표시 값은 서버가 id에서 읽는다.
- 상태 체계는 공통코드로 관리하는 방향이 자연스럽다(프로젝트마다 다를 수 있음). 미결(8.6).
- 기존 `ut_defects`는 **새 모듈로 전환**한다(결정 5). 새 테이블은 단위테스트 테이블 스키마를 확장하지 않고 독립으로 추가하며, 전환 단계에서 `ut_defects` 데이터를 새 테이블로 이전하고 단위테스트 화면이 새 모듈을 쓰도록 바꾼다(8.9).

### 8.5 진척율 통합 = 통계 (구성)

- 집계 기준: 단계 × 업무단위 × WBS(대상 Task) 축으로 케이스 작성률, 수행률, Pass율, QC·PL 확인 진행, 결함(상태·심각도), 미조치 결함을 보여 준다. 이미 만든 `통계보기`(`lib/server/mp/ut/stats.ts`)가 기반이다.
- 추가 후보: 단계별 비교 표, 단계 진행 요약(예: 통합1차 수행률), WBS Task별 테스트 진행 현황, 조치자별 현황·조치 재확인(defect_manage2 기능).
- WBS 진척·실적일·이정표는 **자동으로 바꾸지 않는다.** 이정표 화면의 "WBS 진척 대조"처럼 표시만 한다.

### 8.7 결함 등록 진입 경로와 테스트별 결함관리 (결정 4)

**진입 경로 1 — 단위테스트 정보 화면에서 진입**
- 케이스 정보 화면에서 "결함 등록"을 누르면 결함 등록 화면이 **진입 정보**와 함께 열린다: 케이스, (수행 차수), 화면 URL·화면ID·화면명, WBS Task, 테스트 단계, 작업자.
- 진입 정보는 URL 파라미터로 id만 넘기고, 서버가 id로 케이스·화면 정보를 읽어 채운다(클라이언트가 보낸 표시 값을 그대로 저장하지 않는다). 사용자는 항목을 수정할 수 있다.
- 이번에 케이스에 추가한 `화면 URL`(`screenUrl`)이 이 진입 정보의 일부다.

**진입 경로 2 — 테스트 화면에서 위젯·확장 프로그램으로 등록**
- 테스트 대상 사이트의 위젯이나 Chrome 확장이 현재 페이지의 URL, 제목, UserAgent, 캡처 이미지를 담아 결함 등록 화면을 연다(defect_manage2의 `postMessage` + 전용 창 방식과 같은 구조).
- pmotools 로그인 세션을 쓰므로 로그인되지 않았으면 로그인 후 입력 내용이 유지되어야 한다.
- 새로 설계할 보안: 허용 출처 목록, 메시지 스키마 검증, 캡처 이미지 크기·형식 제한(증적 저장소 재사용), 요청 위조 방지.
- 케이스 지정은 선택이다. 케이스 없이 등록(독립 결함)도 가능하고, 이후 결함 화면에서 케이스·단계를 연결할 수 있어야 한다.

**테스트별 결함관리 (축적된 정보 활용)**
- 결함에 쌓인 연결 키(단계, 케이스, WBS Task, 업무단위)를 기준으로 **테스트별 결함 현황**을 보여 준다: 단계별·케이스별·Task별 결함 건수, 심각도·상태 분포, 미조치 결함, 케이스당 결함 수(결함 밀도).
- 단위테스트 케이스 정보 화면에서는 그 케이스에 연결된 결함 목록·건수를 보여 주고 결함관리 화면으로 이동할 수 있게 한다.
- 통계는 기존 통계보기의 구성(KPI → 표)을 재사용해 만들고, WBS 진척은 바꾸지 않는다(결정 3).
- "각 테스트별 결함관리"는 **테스트별 결함 현황·통계**로 확인되었다(2026-10-24).

### 8.9 `ut_defects` 전환의 영향 (결정 5) — **철회됨(8.12 규칙 1)**

> 이 절은 결정 5를 가정한 영향 분석이다. 2026-10-24에 사용자가 "단위테스트 프로그램과 데이터는 변경하지 않는다"는 규칙을 정하면서 결정 5가 철회되어 **실행하지 않는다.** 기록으로만 남긴다.

코드 검색으로 확인한 범위다(구현 전 점검 대상이며 확정 설계가 아니다).

**영향을 받는 코드**
- 서버: `lib/server/mp/ut/defects.ts`(등록·수정·조치·검증·수행/결함 목록 14곳이 `utDefect`/`utDefectAction` 사용), `grid.ts`(케이스 화면의 결함 목록·조치·검증 권한, 처리 대기 "결함 조치·검증 대기"), `milestones.ts`(UT완료 조건 ③ "Open 결함 없음" 계산), `stats.ts`(결함 현황 표·"미조치 결함" 카드), `export.ts`(수행·결함 엑셀), `common.ts`(`ut_defect_type` 공통코드 그룹), API `app/api/v1/mp/ut/[...path]/route.ts`(`/defects`, `/executions/:id/defects`).
- 도메인: `lib/domain/ut.ts`(결함 상태·조치·검증 전이, `utCompletionConditions`의 결함 조건, 결함 표시 번호 `DF-`).
- 화면: `UtCaseScreen`(결함 섹션, 조치·검증 UI), `UtListScreen`·`UtMilestonesScreen`·`UtStatsScreen`(결함 관련 열·조건·표).
- DB: `ut_defects`, `ut_defect_actions`(INSERT 전용 트리거), 수행과의 재테스트 연결(`retestExecutionId`).
- 로컬 DB 기준 기존 결함은 4건이다. 운영 DB 건수는 확인하지 못했다.

**전환 순서(안)**
1. 새 결함 모듈(테이블·화면·API)을 먼저 만든다. 이 단계에서는 `ut_defects`를 건드리지 않는다.
2. 단위테스트 케이스 화면에 새 모듈로 진입하는 "결함 등록" 버튼을 추가하고, 기존 결함 UI와 잠시 병행한다.
3. `ut_defects` → 새 테이블 이전 스크립트를 만들고 건수·충돌을 보고한 뒤 승인 후 실행한다(백업 선행, 수행 이력 연결과 조치·검증 이력 보존).
4. 단위테스트 쪽의 결함 등록·조치·검증 UI와 서버 코드를 새 모듈 호출로 바꾸고, 통계·이정표 조건·엑셀의 결함 집계를 새 테이블로 교체한다.
5. 안정화 후 `ut_defects`/`ut_defect_actions`를 읽기 전용으로 남기거나 정리한다(DROP은 별도 승인).

**주의**
- `ut_defect_actions`는 DB 트리거로 INSERT 전용이다. 이력을 새 테이블로 옮길 때 원본은 수정하지 않고 복사한다.
- 이정표의 "UT완료 조건 ③"은 결함에 의존하므로, 전환 중 두 곳의 결함을 모두 세는 기간이 생기지 않게 교체 시점을 맞춘다.
- **수행 결과 등록은 결함과 독립이어야 한다(현재 동작 유지).** 현재 코드에서 수행 결과 등록(`registerUtExecution`)과 판정 검증(`validateExecution`)은 결함에 의존하지 않는다. 필수 조건은 Fail=실제결과, N/A=사유, Pass·Fail=증적 1건 이상(최대 3개)뿐이며, Fail 판정을 해도 결함 등록이 강제되지 않고 QC·PL 확인 규칙에도 결함이 쓰이지 않는다. 전환 후에도 새 결함 모듈이 수행 결과 등록·QC/PL 확인의 선행 조건이 되어서는 안 된다.
- **결함이 없을 때의 계산은 "충족"으로 동일하게 유지한다.** 목록의 완료여부(`PL확인완료` + 열린 결함 0건 → "완료"), 이정표의 UT완료 조건 ③(Pass + 막힌 Open 결함 없음), 통계의 결함 표는 결함이 0건이면 충족·0으로 나온다. 전환 후에도 새 모듈에 연결된 결함이 없으면 같은 결과가 나와야 한다. 새 모듈의 결함 조회에 실패하거나 지연되더라도 수행 결과 등록은 막히지 않아야 한다(결함 집계는 조회용에 머문다).
- 전환 후 검증 항목: 결함이 0건인 케이스에서 Pass·Fail·Blocked·N/A 각 판정 등록, QC·PL 확인, 완료여부 "완료" 계산, UT완료 조건 ③ 충족 여부.
- 단위테스트의 운영 배포(Vercel)가 현재 실패 상태이므로, 스키마 변경 전에 배포 문제를 먼저 해결해야 한다(8.6 C7).

### 8.10 결함 권한 설계 (결정 8, 2026-10-24)

**확정된 내용**
- 조치자 = 결함의 **담당자(assignee)**. 별도 "조치자 역할"은 두지 않는다.
- 담당자 기본값 = 결함이 연결된 케이스의 **작업자**(1차 작업자 = WBS Task 담당자 스냅샷, `ut_cases.workerUserId`/`workerName`). 이후 QC, PL, 업무그룹리더 등이 결함을 확인하고 직접 담당자를 지정·변경한다.
- 조회: 일반 사용자는 **본인이 등록했거나 본인이 담당인 결함만** 본다.

**pmotools에서 각 주체를 표현하는 방법(코드 확인)**
- QC·PL: 케이스별 지정(`ut_cases.qcUserId`, `plUserId`). 케이스에 연결된 결함은 그 케이스의 QC·PL을 쓴다.
- 업무그룹리더: 업무그룹의 리더(`groups.leaderId`). 결함에 **업무단위(그룹)** 값이 있어야 판정할 수 있다.
- PM/PMO: 직무(`jobTitle`)로 판정(`hasPmPmoAccess`). 관리자·슈퍼관리자: 역할(`ADMIN`, `SUPER_ADMIN`).

**확인이 필요한 세부 (권고 포함)**

| # | 확인 사항 | 권고 |
|---|---|---|
| 8-a | 담당자를 **지정·변경할 수 있는 주체**: QC, PL, 업무그룹리더 외에 PM/PMO·관리자를 포함할지 | PM/PMO·관리자도 포함(예외 처리 권한과 일치) |
| 8-b | **조회 범위가 넓은 주체**: QC·PL·업무그룹리더·PM/PMO·관리자는 어디까지 보는지 | 관리자·PM/PMO는 프로젝트 전체, 업무그룹리더는 본인 그룹의 결함, QC·PL은 본인이 QC·PL인 케이스의 결함 + 본인 등록·담당 결함 |
| 8-c | **케이스 없는 결함(독립 결함)**의 QC·PL·리더 판정: 케이스가 없으면 QC·PL이 없다 | 독립 결함에도 **업무단위(그룹)**를 두고, 그 그룹의 리더와 PM/PMO가 담당자를 지정. 업무단위가 없으면 PM/PMO·관리자가 지정 |
| 8-d | **조치 입력·상태 변경 권한**: 담당자 + 지정 권한자에게 허용할지 | 담당자와 지정 권한자(8-a 주체) 모두 가능 |
| 8-e | **미배정 결함**(담당자 없음: 위젯으로 들어온 독립 결함 등)을 누가 보고 처리하는지 | 지정 권한자의 "미배정 결함" 목록으로 보여 준다. 등록자도 본인 결함이라 보인다 |
| 8-f | **심각도 변경**, **삭제**, **코드(단계·상태) 관리** | 심각도: 등록자 본인 + 지정 권한자, 삭제·코드 관리: 관리자 |

**데이터 이슈 — 기본 담당자를 채우지 못할 수 있다**
- 로컬 DB에서 케이스 44건의 작업자 **사용자 id가 모두 비어 있다**(이름만 저장됨). WBS 담당자가 시스템 사용자와 연결되지 않고 엑셀 원본 이름만 있기 때문이다(`wbs_items.ownerUserId` 없음, `ownerNameRaw`만 있음).
- 이 상태에서는 "1차 작업자를 기본 담당자로 지정"을 구현해도 담당자가 비게 된다. 해결안: (1) WBS 담당자 이름 → 사용자 매핑을 별도로 정리(이름 일치 목록을 사람이 확인), (2) 매핑되지 않으면 미배정으로 두고 지정 권한자가 지정.
- 운영 DB의 같은 상태는 확인하지 못했다.

### 8.12 설계 규칙 (2026-10-24, 불변)

사용자가 구현과 이관 전반에 적용할 두 규칙을 정했다.

1. **pmotools의 단위테스트 프로그램과 데이터는 변경하지 않는다. 연계는 테이블 조인과 API로 구현한다.**
2. **defect_manage2의 현재 기능과 데이터는 변경하지 않는다.**

**이 규칙이 기존 결정에 준 영향**

| 기존 결정·항목 | 영향 | 처리 |
|---|---|---|
| 결정 5(A1) `ut_defects`를 새 모듈로 전환 | 단위테스트 코드·데이터 변경이라 규칙 1과 충돌 | **철회.** 단위테스트의 결함 기능은 그대로 두고 새 모듈과 병존 |
| 8.9 전환 영향 분석, Phase 7(전환) 6~10일 | 실행하지 않음 | 읽기 전용 연계(F-18) 2~3일로 교체 |
| 단위테스트 케이스 화면에 "결함 등록" 버튼·연결 결함 영역 | 단위테스트 화면 변경 | **만들지 않음.** 진입은 pmotools 확장 프로그램·위젯이 현재 URL(`?case=`)을 전달하고 서버가 조인으로 해석하는 방식, 그리고 결함 화면의 케이스 검색 연결로 대체 |
| 결함의 케이스 연결 키(`caseId`, `executionId`) | 외래 키·역관계를 추가하면 `UtCase` 등 모델 정의가 바뀜 | **외래 키 없는 소프트 참조**로 하고 조회 시 읽기 전용 조인 |
| A5 WBS Task–테스트 단계 연결 | 단위테스트 대상 판정(`isUnitTestTarget`, "개발" 하드코딩) 일반화는 단위테스트 변경 | 판정 일반화는 **하지 않음.** 연결은 결함관리 신규 테이블로만 구현 |
| 단위테스트 통계·이정표·엑셀의 결함 집계 교체 | 단위테스트 변경 | 교체하지 않음. 새 통계는 새 결함 테이블 기준. 단위 단계 합산은 선택(미결 R-01) |
| 이관(결함, 사용자, 공통코드 등) | 원본 변경 금지 | **읽기 전용 복사.** 읽기 전용 계정 또는 GET API, 이관 전후 원본 건수·체크섬 비교(미결 R-03) |
| defect_manage2 위젯·확장 프로그램 | 원본 파일 변경 금지 | pmotools용을 **새로 제작**. 기존 것은 그대로 기존 주소를 가리킴 |
| 이관 후 병행 | 두 시스템에 데이터가 따로 존재(단방향 복사) | 중복·불일치 처리 방침은 미결 R-02 |

**공수 영향:** 단위테스트 전환이 빠지고 읽기 전용 연계로 바뀌어 전체 추정이 약 27~38.5일로 줄었다(이전 32~48일). 근거는 [작업계획서](결함관리_개발_작업계획서.md) 3장이다.

**남은 확인 사항(사용자 확인 요청)**
- R-01: 단위 단계 결함(`ut_defects`)을 새 결함 통계에 읽기 전용으로 합산할지.
- R-02: 병행 중 defect_manage2와의 중복·불일치 처리 방침.
- R-03: defect_manage2 데이터를 읽는 방식(읽기 전용 DB 계정 / GET API).
- F-02를 확장 프로그램·위젯 방식으로 바꾼 것이 단위테스트 화면 진입 요구를 충족하는지.

### 8.13 사용자 확인 결과 (2026-10-24)

8.12의 확인 요청에 대한 답이다.

| 확인 사항 | 결과 | 영향 |
|---|---|---|
| 단위테스트 화면에서의 진입을 확장 프로그램·위젯 방식으로 바꾼 것 | **충분** | F-02 확정 |
| R-01: 단위 단계 결함(`ut_defects`) 합산 | **합산** | 새 결함 통계에 `ut_defects`를 읽기 전용 조인으로 합산. 출처 구분, 상태·심각도 매핑 필요(설계서 7장) |
| R-03: defect_manage2 데이터를 읽는 방식 | **해당 없음.** defect_manage2와 연결하는 것이 아니라 그 기능을 pmotools에 개발하는 것 | 읽기 방식 결정이 필요 없음 |
| R-02: 이관 후 중복·불일치 | **해당 없음.** 별도 시스템이며 통합이 아니고 연결성이 없음 | 데이터 이관 자체가 없음 |

**결과**
- **defect_manage2는 기능 참고 자료일 뿐**이다. 데이터 이관, 가져오기, 동기화, API 연결은 모두 하지 않는다. 사용자는 pmotools 사용자를 쓰고 결함은 새로 쌓는다.
- 이에 따라 이 문서 앞부분의 **데이터 이관 관련 내용은 더 이상 적용되지 않는다**: 5장의 이관 원본·사용자 매핑·이관 범위·병행 일정, 6장의 이름→사용자 id 매핑 위험, 4.6의 데이터 이관 절차, 8.6의 C1~C4. 분석 기록으로만 남긴다.
- 설계서·작업계획서에서 F-16(데이터 이관)과 이관 Phase를 삭제했다. 작업항목은 43개, 추정은 **약 25~36일**이다([작업계획서](결함관리_개발_작업계획서.md) 3장).
- 남은 미결: D-01~D-04(상태 전이 제약, 막힌 결함 기준, 번호 접두사, 증적 제한), B-08(화면경로 코드 준비 방식), C5(위젯·확장 도입 시점·허용 출처), C6(목표일), C7(Vercel 운영 배포 실패 원인 해결과 증적 저장 환경), W-01(작업자 사용자 id 매핑).

### 8.14 용어 정리와 번호 모양 (2026-10-24)

사용자 지적에 따라 용어와 결함 번호를 정리했다.

- **결함 번호 모양은 전체 테스트에 통일**한다: `DF-{yyMMdd}-{순번 4자리}`(단위테스트 결함과 같은 모양). 이전 안의 `DM-` 접두사는 폐기한다. 단위테스트의 순번은 변경할 수 없어 번호가 겹칠 수 있으므로 겹침 방지 방식(순번 구간 분리 또는 출처 구분)을 D-03으로 남겼다.
- **심각도**는 결함 자체의 영향도이고 **조치 상태**와는 별개의 속성이다. 둘을 섞어 쓰지 않는다.
- **"막힌 결함"은 사용자에게 친화적이지 않은 용어**라서 **"미조치 중대 결함"**(조치 상태가 미조치이면서 심각도가 기준 이상인 결함)으로 바꿨다. 기준 심각도는 설정으로 둔다(D-02).
- **"담당자"는 조치 담당자(조치자)**를 뜻하며, 케이스의 **수행자**(테스트를 한 사람)와 다르다. 조치 담당자의 기본값은 케이스의 **작업자**(해당 기능을 만든 개발 담당자)다.

### 8.15 결함번호 체번 체계 확정 (2026-10-24)

"모든 결함 번호는 결함번호 체번 체계를 기준으로 한다"는 사용자 지시에 따라 체번 체계를 표준으로 확정했다(설계서 3.4).

- 형식 `DF-{yyMMdd}-{순번 4자리}`, 프로젝트 안에서 유일.
- **순번 범위를 출처별로 배정**한다: 단위테스트 0001~4999, 결함관리 5001~9999(5000 예비). 단위테스트 프로그램은 변경하지 않고(규칙 1) 지금처럼 매겨도 체계를 어기지 않는다. 번호만 보고 출처를 알 수 있다.
- 이에 따라 8.14의 `D-03`(번호 겹침 방지 방식)은 해소되었다.

### 8.16 남은 결정 사항 확정 (2026-10-24)

| 결정 | 결과 |
|---|---|
| D-01 상태 변경 규칙 | 순서 제한 없이 권한 있는 사람이 변경, 모두 이력에 기록 |
| D-02 미조치 중대 결함 기준 | Critical·Major (설정으로 변경 가능) |
| D-04 첨부 한도 | 결함당 3개, 파일당 20MB, 단위테스트와 같은 형식 |
| B-08 화면경로 | **필수값이 아님.** 데이터 컬럼(`screenPath`)만 제공. 코드 목록·관리·엑셀 등록 없음 |
| 위젯·확장 프로그램 도메인 | **대상 도메인 관리 기능(F-19, DM-10)을 추가**해 관리. 초기 대상은 **cinetube**(로컬 `localhost:8080)와 **secret album**(설계 단계, 계획 포트 8090) |
| 조치 담당자 | 기본값은 **WBS Task의 작업자**. 변경: QC, PL, 운영자(`OPERATOR`), 그룹리더, PMO(와 관리자·슈퍼관리자) |
| 현업 사용 시작 목표일 | 관리하지 않음 |
| 운영 배포 실패 원인·운영 환경 확인 | 관리하지 않음. **배포는 GitHub 반영까지**이며 **Vercel 배포는 별도 진행하지 않음** |
| 설계서 승인 | **최종 검토 후 승인** |

**조치 담당자 기본값 점검(로컬 DB, 읽기 전용):** WBS 3,480건 중 작업자가 시스템 사용자와 연결된 것이 2,298건이다. 이름만 있는 560건은 이름이 4종이고 그중 1종만 사용자와 1:1로 일치한다. 나머지 이름은 사람 이름이 아니다('개발자', '전체'). 별도 이름 매핑 작업은 필요 없고, 연결되지 않은 Task의 결함은 조치 담당자를 미지정으로 둔다. 운영 DB의 상태는 확인하지 못했다.

**효과:** 설계서 11장의 미결 사항이 없어졌다. 작업항목에 대상 도메인 관리(P6-05)가 추가되어 Phase 6 추정이 늘었고(4.25~6.25일), 화면경로 코드 그룹이 빠져 공통코드 그룹은 5개가 되었다.

### 8.17 화면경로 방식 변경 (2026-10-24)

8.16의 "화면경로는 선택 컬럼만, 코드 목록·엑셀 없음" 결정을 사용자가 **세 가지 방식**으로 바꿨다.

1. **사용자 입력** — 화면경로를 직접 입력(필수 아님). 1차 범위
2. **결함 수집 시 URL 정보 획득·전달·저장** — 위젯·확장이 현재 URL을 가져와 등록 화면에 전달하고 `screenUrl`로 저장. 1차 범위
3. **이후 화면 목록 일괄 등록(엑셀 등록 포함)** — **1차 이후(후속, F-20, DM-11)**. 화면 목록 모델과 관리 화면, 엑셀 양식·검증·미리보기, 결함 등록 화면의 선택·URL 자동 매칭

작업계획서에는 후속 Phase(L-01~L-03, 약 3~4.5일)를 1차와 분리해 추가했다. 1차 공수(약 25.75~37.25일)에는 포함하지 않는다.

### 8.18 미결·후속 사항 전부 확정 (2026-10-24)

"미결 및 후속사항이 없도록 설계서에 모두 결정하자"는 요청에 따라 남은 항목을 설계서(Rev 0.9)에서 확정했다. 사용자가 최종 검토에서 바꿀 수 있다.

| 항목 | 확정 내용 |
|---|---|
| 화면 목록 일괄 등록(F-20) | 후속에서 **본 범위로 편입**(작업계획서 Phase 7, 약 3~4.5일). 엑셀 양식(화면경로 필수, URL·화면명·사용 여부 선택), 5MB·5,000행, 오류가 있으면 반영하지 않음, 같은 화면경로는 수정·없으면 등록·엑셀에 없는 항목은 변경 없음, 쓰기 권한은 운영자·PMO·관리자 |
| 수집 URL 자동 매칭 | URL 정규화(호스트 소문자, 쿼리·해시·끝 `/` 제거), `*` 패턴, 여러 개면 더 구체적인 것 우선, 없으면 비움, 자동 채움은 제안(입력값 덮어쓰지 않음) |
| 기본 코드 값 | 단계 4개(단위·통합·3자·오픈), 상태 6개(접수·조치중·재오픈·조치완료·반영대기·종결), 심각도 4개, 우선순위 4개(P1~P4), 결함식별 4개 |
| 중대 결함 기준 설정 | 신규 테이블 `defect_severity_settings`(심각도 코드별 중대 여부, 기본 Critical·Major) |
| 위젯·확장 메시지 규격 | `PMO_DEFECT_READY/DATA/CLOSE`, 본문 필드·20MB 캡처 제한, 허용 출처 검사 |
| 로그인 유지 | 로그인 화면으로 이동 후 같은 팝업으로 복귀(`returnTo`), 수집 데이터는 팝업의 `sessionStorage`에 임시 보관 |
| 저장 오류 로그(F-17) | 만들지 않음. 서버 로그와 화면 오류 메시지로 대체 |
| 단위테스트 결함 합산 매핑 | 상태: REGISTERED·REFIX→미조치, FIXED→조치완료, VERIFIED→종결. 심각도: 같은 이름으로 대응 |

설계서 11장은 "결정 현황"으로 바뀌었고 미결·후속 사항은 없다.

### 8.19 설계 승인 (2026-10-24)

사용자가 [결함관리 프로그램 설계서](결함관리%20프로그램%20설계서.md)(Rev 1.0)와 [작업계획서](결함관리_개발_작업계획서.md)를 **승인**했다. 단, **구현 단계에는 사용자가 지시할 때까지 진입하지 않는다.** 코드와 DB는 변경하지 않았고, 구현 착수 지시는 작업계획서 P0-16에서 대기 중이다.
