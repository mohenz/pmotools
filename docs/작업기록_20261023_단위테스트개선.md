### 2.1 케이스 검토·승인 폐지 (사용자 결정: 1번 — 스키마 변경 없이 `IN_EXECUTION`)
- 새 케이스는 등록 즉시 `IN_EXECUTION`(수행 대기)으로 저장한다. enum 값(`DRAFT`·`REVIEW_REQUESTED`·`REJECTED`)은 호환용으로 남긴다.
- 수정 가능 조건: `canEditCase(status, executionCount)` = `IN_EXECUTION`이고 수행 결과 0건. 작성자 또는 PM/PMO만.
- 삭제: `requestUtCaseReview`, `decideUtCaseReview`, `listUtReviewInbox`, API `/cases/:id/review`·`/decision`, 목록의 "검토상태" 열·필터, "검토 대기"·"작성중" 처리 대기 항목, `nextCaseReviewStatus`, `utReviewStatus`, `UT_REVIEW_STATUS_LABEL`.
- `canExecuteCase`는 `APPROVED`(폐지 전 승인 건)와 `IN_EXECUTION`을 수행 가능으로 본다.
- 개발완료 선언 조건: "PL 승인된 케이스 1건 이상" → "등록된 케이스 1건 이상". 이정표 화면의 "승인" 표기는 "등록".
- 위치: `lib/domain/ut.ts`, `lib/server/mp/ut/{cases,grid,milestones}.ts`, `app/api/v1/mp/ut/[...path]/route.ts`, `app/mp-ut/page.tsx`, `screens/mp/ut/{UtCaseScreen,UtListScreen,UtMilestonesScreen}.tsx`, `features/mp/ut/format.ts`.
- 설계서 `docs/단위테스트 수행관리 프로그램 설계서.md` 6장 머리에 변경 메모 추가.

### 2.10 작업자 컬럼 (DB 스키마 변경)
- 사용자 정의: **작업자 = 케이스 저장 시점의 WBS Task 담당자 스냅샷**. 작성자가 WBS ID를 선택해 저장할 때 서버가 읽어 같이 저장하며(클라이언트 값 사용 안 함), 이후 WBS 담당자가 바뀌어도 케이스 값은 그대로다. WBS 없이 등록한 케이스는 비어 있다.
- 스키마(`prisma/schema.prisma`): `UtCase.workerUserId String?`(User 관계 `UtCaseWorker`, `onDelete: SetNull`, 인덱스), `UtCase.workerName String @default("")`, `User.utWorkerCases` 역관계.
- 마이그레이션: `prisma/migrations/20261023100000_ut_case_worker/migration.sql` — 컬럼 2개 추가, FK, 인덱스. 비어도 되는 컬럼 추가뿐이라 다운타임·기존 행 영향 없음. 롤백은 두 컬럼 DROP.
- 코드: `createUtCase`가 `listUtWbsLeaves`로 찾은 WBS의 `ownerUserId`/`ownerName`을 저장. `getUtCaseEditor`는 `wbsOwnerName: c.workerName`, 목록은 `ownerName: c.workerName || null`. 신규 등록 화면은 선택한 WBS의 담당자를 미리 보여 준다(`UtTreeNode.ownerName`).
- 기존 케이스 값은 비어 있으므로 아래 4장의 백필이 필요하다(임시 대체 처리는 만들었다가 백필 후 삭제했다 — 지금 코드에는 없다).

### 2.11 작성현황·수행결과 통계 화면 (신규)
- 메뉴: 왼쪽 메뉴 단위테스트 그룹의 "통계보기"(`/mp-ut/stats`). 하위 프로젝트 단위. WBS 트리 없음(전체 집계).
- 집계(`lib/server/mp/ut/stats.ts` `getUtStats`): 활성 케이스의 **최근 차수** 기준. 범위는 단위테스트 대상 Task의 케이스와 WBS 없는 케이스.
- 화면(`screens/mp/ut/UtStatsScreen.tsx`): KPI 카드 8개(대상 Task, 작성률, 케이스, 수행률, Pass율, PL 확인 완료, 미조치 결함, 확인 반려) → 수행결과 구성 막대(CSS 누적 막대) → "QC·PL 확인 진행" 표(단계·상태·건수·비율·합계) → "결함 현황" 표(상태 × 심각도 교차표·합계) → 구분별 표 3개(업무단위·케이스유형·수행자: 케이스·수행·미수행·Pass·Fail·Blocked·N/A·수행률·Pass율·구성 막대). 숫자 열은 우측 정렬(`data-numeric`).
- 사용자 요청으로 뺀 것: "작성자별" 표, "일자별 추이"(워킹데이 세로막대 그래프까지 만들었다가 제거). 일자별 추이를 다시 만들 경우 공휴일은 `holidays` 테이블(`loadHolidaySet`)에서 읽는데, 로컬 DB에는 2026-11~2027-02 공휴일이 0건이었다.
- 초안 상태다. 필터(기간·업무단위 등), 엑셀 출력은 없다.

### 2.12 화면 URL 항목
- DB: `ut_cases.screenUrl TEXT NOT NULL DEFAULT ''`(마이그레이션 `20261023150000_ut_case_screen_url`), 입력은 최대 500자(`cases.ts` zod), 형식 검사 없음.
- 화면: 케이스 정보에서 화면ID·화면명 줄 바로 아래에 "화면 URL" 입력란(한 줄 전체 폭). 목록·통계·엑셀에는 넣지 않았다.

### 2.13 운영 배포 호환 처리 (검토 폐지 전 상태)
- 운영 DB에는 검토 폐지 이전 상태(`DRAFT`, `REVIEW_REQUESTED`, `REJECTED`)의 케이스가 남아 있을 수 있고, 운영 데이터 변환은 승인받지 않아 수행하지 않았다.
- 그래서 코드가 그 상태를 `IN_EXECUTION`(수행 대기)과 똑같이 다룬다: `UT_LEGACY_PRE_EXECUTION_STATUSES`, `canEditCase`(수행 결과 0건이면 수정 가능), `canExecuteCase`(수행 가능), 내 수행 목록, 목록 "수행 대상" 필터(`lib/domain/ut.ts`, `grid.ts`, `executions.ts`). 단위테스트로 고정했다.
- 운영 DB의 작업자(`workerName`)는 비어 있다. 케이스 정보·목록에서 `–`로 보인다. 4장 3번 백필을 운영에서 승인 후 실행하면 채워진다.

## 4. DB 작업 — 승인 후에만 실행 (로컬 DB 기준 이력)

다른 PC의 DB 상태는 다를 수 있다. **실행 전에 건수를 확인하고 백업한 뒤, 사용자 승인을 받는다.**

로컬 DB: `postgresql://…@localhost:55432/mydb` (`.env`의 `DATABASE_URL`). 접속 정보는 문서에 적지 않았다. `.env.local`의 `SUPABASE_DATABASE_URL`은 운영 연결이므로 **건드리지 않는다.**

1. 마이그레이션: `npx prisma migrate deploy` (위 2.10, 2.12 — `ut_case_worker`, `ut_case_screen_url`). 이 PC에서는 적용 시 "DB에 있는데 로컬에 없는 마이그레이션 `20261022100000_wbs_app_tokens`" 경고가 있었으나 적용에는 문제가 없었다. 다른 브랜치/PC에서 만든 변경으로 보이며, 운영 배포 전 목록 정합성 확인이 필요하다.
2. 상태 변환 (검토 폐지 때문에 필요): 이 PC에서는 작성중 30건, 검토요청 3건, 반려 1건 = 34건.
   ```sql
   -- 먼저 대상 id·이전 상태를 JSON 등으로 백업
   UPDATE ut_cases SET status = 'IN_EXECUTION'
   WHERE status IN ('DRAFT','REVIEW_REQUESTED','REJECTED');
   ```
3. 작업자 백필 (이 PC에서는 WBS가 있는 44건 모두 이름 확보, 사용자 id는 전부 비어 있었음):
   ```sql
   UPDATE ut_cases c
   SET "workerUserId" = w."ownerUserId",
       "workerName"   = coalesce(u.name, nullif(w."ownerNameRaw", ''), '')
   FROM wbs_items w LEFT JOIN users u ON u.id = w."ownerUserId"
   WHERE w.id = c."wbsItemId" AND c."workerName" = '';
   ```
4. 이 PC의 백업 파일(`db_backups/`, 추적되지 않음): `ut_cases_status_before_20261023.json`, `ut_cases_worker_before_20261023.json`. 되돌리려면 파일의 이전 값으로 UPDATE.
5. **운영 DB(Vercel/Supabase)의 데이터 변환(2·3번)은 실행하지 않았다.** 운영 배포(`vercel-build`가 `prisma migrate deploy` 실행) 때 마이그레이션 2개는 자동 적용된다. 상태 변환(2번)은 2.13의 호환 처리 때문에 배포 직후에도 서비스가 막히지 않지만, 운영 데이터 정리를 위해 건수 확인 후 승인받아 실행한다. 작업자 백필(3번)도 같다.
