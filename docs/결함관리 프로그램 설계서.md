## 1. 개요

### 1.1 목적

외부 시스템 `defect_manage2`(Express + 바닐라 JS)의 핵심 기능을 **pmotools 구조(Next.js, Prisma, 프로젝트·사용자·공통코드·증적 저장소)에 맞게 새로 구현**한다. 구현 대상 기능은 세 가지다.

1. **테스트결과 수집** — 테스트 대상 화면에서 위젯·확장 프로그램으로 테스트 중 발견한 내용(화면 URL, 제목, UserAgent, 캡처 이미지)을 수집해 결함 등록으로 이어 준다. 단위테스트 케이스 화면에서 진입 정보를 가지고 등록하는 경로도 포함한다.
2. **결함관리** — 결함 등록, 담당자 배정, 조치, 상태 관리, 이력, 증적.
3. **결함 및 조치 통계** — 테스트별 결함 현황, 조치자 현황, 조치 재확인.

> **목표 정정(2026-10-24):** 이 문서의 이전 초안은 "로그인·사용자, WBS, 테스트, 진척 통계를 pmotools와 통합하는 것"을 목표로 적었으나, 목표는 통합이 아니라 위 세 기능의 구현이다. pmotools의 사용자·프로젝트·공통코드·증적 저장소는 **재사용**하고, 단위테스트·WBS와의 연결은 **부가 연동**으로 본다(1.3 비고).

### 1.3 확정된 결정 (이식검토 8.2, 8.11)

1. 결함관리는 **독립 모듈**이다. 새 결함 테이블·이력·화면·메뉴를 만든다.
2. ~~단위테스트의 결함 기능은 새 모듈로 전환한다(`ut_defects` 대체).~~ **철회(2026-10-24, 설계 규칙 1).** 단위테스트의 결함 기능(`ut_defects`)은 **그대로 둔다.** 새 결함관리는 이와 별개로 병존한다.
3. 케이스 없는 결함은 **별도 등록 경로**로 등록한다.
4. 단위테스트 외 단계는 **결함만** 관리한다.
5. 테스트 단계는 **프로젝트별 공통코드**다(고정 값 아님).
6. 진척 통합은 **통계 전용**이다. WBS 진척을 바꾸지 않는다.
7. 조치자 = 결함 **담당자**. 기본값은 케이스의 작업자이며 QC·PL·업무그룹리더 등이 확인 후 직접 지정한다.
8. 조회: 일반 사용자는 **본인이 등록했거나 담당인 결함만** 본다.
9. **단위테스트의 결함(`ut_defects`)은 새 결함 통계에 읽기 전용으로 합산한다**(R-01 확정, 7장).
10. **defect_manage2는 별도 시스템이다.** 연결·데이터 이관·동기화는 없고, 그 기능만 pmotools에 개발한다(규칙 2, 9장).
11. 단위테스트 화면에서의 진입은 **확장 프로그램·위젯 방식**으로 충분하다(F-02 확정, 5.1).
12. **결함 상태는 순서 제한 없이 권한 있는 사람이 바꾼다.** 변경은 모두 이력에 남긴다(D-01, 4.1).
13. **"미조치 중대 결함"의 기준 심각도는 Critical·Major**이며 설정에서 바꿀 수 있다(D-02, 3.2).
14. **결함 첨부 한도는 결함당 파일 3개, 파일당 20MB, 단위테스트와 같은 형식**이다(D-04, 6.3).
15. **화면경로는 세 가지 방식을 모두 제공**한다. ① 사용자 입력 ② 결함 수집 시 URL 정보를 획득해 전달·저장(`screenUrl`) ③ 화면 목록 일괄 등록(엑셀 포함)과 목록 선택·URL 자동 매칭(F-20, DM-11, 5.2). 화면경로는 필수값이 아니다.
16. **위젯·확장 프로그램의 허용 도메인은 "대상 도메인 관리" 기능으로 관리**한다(F-19, DM-10). 초기 대상은 cinetube와 secret album이다(6.2).
17. **조치 담당자의 기본값은 WBS Task의 작업자**이고, QC·PL·운영자·그룹리더·PMO(와 관리자)가 변경한다(4.2).
18. **현업 사용 시작 목표일, 운영 배포 실패 원인, 운영 환경 확인은 이 프로젝트에서 관리하지 않는다.** 배포는 **GitHub 반영까지**만 하고 **Vercel 배포는 별도로 진행하지 않는다**(사용자 결정).
19. **화면 목록 일괄 등록의 세부 규칙**(엑셀 양식, 검증, 반영, 권한, URL 매칭)은 5.2에서 확정한다.
20. **기본 코드 값**(단계·상태·심각도·우선순위·결함식별)과 **중대 결함 기준 설정**은 3.2·3.1에서 확정한다.
21. **위젯·확장 프로그램의 메시지 규격과 로그인 유지 방식**은 6.2에서 확정한다.
22. **저장 오류 로그(F-17)는 만들지 않는다.** 저장 실패는 서버 로그와 화면 오류 메시지로 처리한다.

> **비고(설계 규칙 반영):** 결정 2(단위테스트 결함 전환)는 설계 규칙 1(단위테스트 무변경)에 따라 철회되었다. WBS Task–테스트 단계 연결(F-14)은 결함관리 **자신의 신규 테이블**로만 구현하고 단위테스트의 대상 판정은 바꾸지 않는다. 케이스 화면에서의 진입은 단위테스트 화면을 고치지 않고 위젯·확장 프로그램과 결함 화면의 케이스 검색으로 해결한다(5.1).

### 1.4 설계 규칙 (불변, 2026-10-24)

구현과 전환의 모든 단계가 지켜야 하는 규칙이다. 작업계획서의 각 Phase 완료 기준에 준수 점검을 넣는다.

**규칙 1 — pmotools 단위테스트 프로그램과 데이터는 변경하지 않는다. 연계는 테이블 조인과 API로 구현한다.**
- 단위테스트의 화면·서버 코드·도메인 코드·테이블 구조·데이터를 바꾸지 않는다(`screens/mp/ut`, `lib/server/mp/ut`, `lib/domain/ut.ts`, `features/mp/ut`, `app/mp-ut`, `app/api/v1/mp/ut`, `ut_*` 테이블).
- 단위테스트 데이터가 필요하면 **읽기 전용 조인 또는 API 조회**로 가져온다(케이스 검색·정보, 작업자, QC·PL, 화면 URL, WBS Task). 결함관리는 단위테스트 데이터를 쓰지 않는다.
- 단위테스트 테이블에는 **외래 키와 Prisma 역관계를 추가하지 않는다.** 결함의 `caseId`·`executionId`는 외래 키 없는 **소프트 참조**(문자열 id)이고 조회 시 조인한다. 단위테스트 모델 정의(`UtCase` 등)를 바꾸지 않기 위함이다.
- 공유 자원(`users`, `projects`, `groups`, `wbs_items`, `common_code_*`)은 **읽기만** 한다. 새 공통코드 그룹과 코드는 결함관리 전용 **새 행**으로만 추가하고 기존 코드는 바꾸지 않는다. 공유 메뉴 파일에는 결함관리 메뉴 항목만 추가한다.
- 이미 반영된 단위테스트 변경(작업자·화면 URL 컬럼 등)은 이 규칙 이전의 작업이며 되돌리지 않는다. 결함관리는 그 값을 읽기만 한다.

**규칙 2 — defect_manage2는 별도 시스템이며 현재 기능·데이터를 변경하지 않는다. 연결·데이터 이관·동기화도 하지 않는다.**
- defect_manage2는 pmotools와 **별도 시스템**이다. 이 프로젝트의 목표는 그 시스템과 연결하는 것이 아니라 그 **기능을 pmotools에 개발**하는 것이다. defect_manage2는 기능 참고 자료이며, 그 코드·설정·위젯·확장 프로그램 파일·데이터베이스를 수정하지 않는다. 계속 기존대로 동작해야 한다.
- defect_manage2의 데이터를 읽거나 옮기지 않는다(이관·가져오기·동기화·API 연결 없음). 사용자·결함·공통코드는 pmotools에서 새로 관리한다.
- pmotools용 위젯·확장 프로그램은 **새로 제작**하며 defect_manage2의 파일을 쓰거나 고치지 않는다. defect_manage2의 위젯·확장은 기존 주소를 계속 가리킨다.
- 두 시스템 사이에 데이터 연결이 없으므로 중복·불일치 처리는 이 프로젝트의 범위 밖이다.

### 1.5 용어

| 용어 | 의미 |
|---|---|
| 테스트 단계 | 결함이 발견된 테스트 구분. 프로젝트별 공통코드(예: 단위, 통합1차, 3자내부, 파일럿오픈) |
| 진입 정보 | 결함 등록 화면을 열 때 함께 전달되는 컨텍스트(케이스, 화면 URL, WBS Task, 단계 등) |
| 독립 결함 | 케이스·수행과 연결되지 않은 결함 |
| 심각도 | **결함 자체**가 얼마나 중대한지(영향도). 결함을 등록할 때 정하며 조치가 어디까지 진행됐는지(조치 상태)와는 별개다. 예: Critical, Major, Minor |
| 조치 상태 | 결함 처리가 어디까지 진행됐는지(Open, In Progress, Resolved 등). 심각도와는 별개이며 상태 분류(미조치·조치완료·종결)로 묶는다 |
| 등록자 | 결함을 등록한 사람(보통 테스트를 한 사람) |
| 수행자 | 단위테스트 케이스의 테스트 수행 담당자(`ut_cases.executorId`). 결함의 조치 담당자와 다른 사람이다 |
| 조치 담당자(조치자) | 결함을 **고치는(조치하는) 사람**. 결함의 `assigneeUserId`. **이 문서의 "담당자"는 모두 조치 담당자를 뜻한다.** |
| 작업자 | 해당 기능을 만든 개발 담당자 — **WBS Task의 작업자**(`wbs_items`의 담당 사용자). **조치 담당자의 기본값** |
| 대상 도메인 | 위젯·확장 프로그램이 동작하도록 허용한 테스트 대상 사이트 주소. 설정 화면(DM-10)에서 관리 |
| 미조치 중대 결함 | 조치 상태가 미조치이면서 심각도가 설정한 기준(예: Critical·Major) 이상인 결함. 통계에서 따로 보여 준다 |
| 지정 권한자 | 조치 담당자를 지정·변경할 수 있는 주체: QC, PL, **운영자**(역할 `OPERATOR`), 업무그룹리더, PMO(PM/PMO 직무), 관리자·슈퍼관리자 |
| 상태 분류 | 상태 코드를 통계 기준으로 묶는 값: 미조치(OPEN), 조치완료(DONE), 종결(CLOSED) |

### 1.6 선행 조건

- 운영 배포 실패(커밋 `50e7077`)의 원인 해결, 운영 환경 확인, 현업 사용 시작 목표일은 **이 프로젝트에서 관리하지 않는다**(2026-10-24 사용자 결정). **배포는 GitHub 반영까지**이며 Vercel 배포는 별도로 진행하지 않는다.
- 구현 단계에서 DB 스키마 변경, 데이터 이전, 운영 배포는 각각 **리스크 보고 후 사용자 승인**을 받는다(`CLAUDE.md`).

**`defect_histories` — 이력(INSERT 전용)**: `defectId`, `action`(CREATE, UPDATE, ASSIGN, STATUS, LINK, DELETE), `statusBeforeCodeId`, `statusAfterCodeId`, `changedData`(JSON: 변경 필드 전/후, 증적 원문은 복사하지 않음), `actorId`, `actorName`, `createdAt`. 수정·삭제를 DB 트리거로 막는다(단위테스트 이력과 같은 방식).

**`defect_evidences` — 증적**: `defectId`, `fileName`, `mimeType`, `sizeBytes`, `sha256`, `storageKey`, `uploadedBy`, `createdAt`. 파일은 단위테스트 증적 저장소(`ut-evidence-storage`)를 일반화해 재사용한다.

**`defect_status_classes` — 상태 분류**: `projectId`, `statusCodeId`, `statusClass`(OPEN=미조치, DONE=조치완료, CLOSED=종결). 프로젝트당 상태 코드 하나에 분류 하나. 통계의 "미조치" 기준이 이 분류다.

**`defect_severity_settings` — 중대 결함 기준**: `projectId`, `severityCodeId`, `isMajorImpact`(중대 여부). 심각도 코드당 하나이고 유일 키는 `(projectId, severityCodeId)`다. 기본값은 Critical·Major = 중대, Minor·Trivial = 중대 아님이며 설정 화면에서 바꾼다. "미조치 중대 결함" 통계가 이 설정을 쓴다.

**`wbs_item_test_stages` — Task–단계 연결**: `projectId`, `wbsItemId`, `testStageCodeId`, 유일 키 `(wbsItemId, testStageCodeId)`. 한 Task가 여러 단계의 대상일 수 있다. 결함관리가 쓰는 **신규 테이블**이며 `wbs_items`·단위테스트 대상 판정(`isUnitTestTarget`, "개발" 단계 판정)은 **변경하지 않는다**(규칙 1). 연결 키(`wbsItemId`)는 읽기 전용 참조다(F-14).

**`defect_sequences` — 채번**: 단위테스트 `ut_sequences`와 같은 방식.

**`defect_target_sites` — 대상 도메인(F-19)**: `projectId`, `name`(사이트 이름), `origin`(허용할 주소, 예: `http://localhost:8080`), `isActive`, `createdBy`, `createdAt`, `updatedAt`. 프로젝트별 관리하며 유일 키 `(projectId, origin)`. 위젯·확장 프로그램의 허용 출처 검사는 **이 목록의 활성 도메인만** 통과시킨다.

**`defect_screens` — 화면 목록(F-20)**: `projectId`, `path`(화면경로, 필수, 500자), `url`(화면 주소 또는 패턴, 선택, 1000자), `name`(화면명, 선택, 255자), `isActive`(사용 여부), `createdBy`, `updatedBy`, `createdAt`, `updatedAt`. 유일 키는 `(projectId, path)`이며 비교할 때 앞뒤 공백을 지우고 대소문자를 구분하지 않는다. 삭제하지 않고 비활성만 한다. 엑셀로 일괄 등록·수정하고(5.2), 결함의 `screenPath`는 이 목록에서 선택하거나 수집 URL로 자동 매칭해 채운다. 목록이 비어 있어도 결함 등록은 항상 가능하다.

### 3.2 공통코드 그룹 (프로젝트별 시딩)

`defect_test_stage`, `defect_status`, `defect_severity`, `defect_priority`, `defect_identification` (5개). 코드의 이름·순서·사용 여부는 프로젝트 관리자가 화면에서 관리한다. 이미 쓰인 코드는 삭제하지 않고 비활성화만 한다(공통코드 기존 동작). 새 프로젝트용 기본 템플릿(예: 단위·통합·3자·오픈형)을 시드로 제공한다.

**기본 코드 값(새 프로젝트의 기본 시드, 확정).** 관리자가 설정 화면에서 이름 변경·추가·비활성할 수 있다.

| 그룹 | 코드값 → 표시 이름(상태는 분류) |
|---|---|
| 테스트 단계 `defect_test_stage` | `UNIT` 단위 · `INTEGRATION` 통합 · `THIRD_PARTY` 3자 · `OPEN_TEST` 오픈 (프로젝트에 맞게 통합1차·2차·3차, 3자내부·3자외부, 파일럿오픈 등으로 바꿔 쓴다) |
| 상태 `defect_status` | `OPEN` 접수(미조치) · `IN_PROGRESS` 조치중(미조치) · `REOPENED` 재오픈(미조치) · `RESOLVED` 조치완료(조치완료) · `STAGING` 반영대기(조치완료) · `CLOSED` 종결(종결) |
| 심각도 `defect_severity` | `CRITICAL` Critical · `MAJOR` Major · `MINOR` Minor · `TRIVIAL` Trivial |
| 우선순위 `defect_priority` | `P1` 긴급 · `P2` 높음 · `P3` 보통 · `P4` 낮음 |
| 결함식별 `defect_identification` | `EXISTING` 기존결함 · `DISCUSS` 협의필요 · `NEW_REQUIREMENT` 신규요구사항 · `NOT_DEFECT` 결함아님 |

기본 시드는 결함관리 설정 화면을 처음 열 때 해당 그룹이 비어 있으면 자동으로 만든다. `STAGING`(반영대기)은 조치완료 분류다.

**심각도**는 결함 자체의 영향도이며 결함을 등록할 때 정한다. 조치 상태와는 별개의 속성이다. 단위테스트 결함의 기준(Critical·Major·Minor·Trivial)과 맞추되 공통코드로 관리하고, 코드의 순서(`sortOrder`)를 심각도 순위로 쓴다. "미조치 중대 결함"(조치 상태가 미조치이고 심각도가 기준 이상인 결함) 통계를 위해 **중대 결함 기준 심각도**(예: Critical·Major)를 설정으로 둔다(확정: Critical·Major, 설정으로 변경 가능).

### 3.3 무결성 규칙

1. `(projectId, displayId)` 유일.
2. 이력은 INSERT 전용. 수정·삭제는 DB 트리거로 차단한다.
3. 낙관적 락(`version`)으로 동시 수정 충돌을 막는다.
4. 논리 삭제(`isActive`)만 허용한다. 물리 삭제는 하지 않는다.
5. 연결 키는 같은 프로젝트의 행만 가리킨다(서버 검증). `caseId`·`executionId`처럼 **단위테스트 테이블을 가리키는 키는 외래 키 없는 소프트 참조**이며, 조회 시 읽기 전용으로 조인한다(규칙 1).
6. 연결 키는 **선택**이다. 결함은 케이스·수행·Task 없이도 존재할 수 있다.
7. 결함의 존재 여부가 단위테스트 수행 결과 등록·QC/PL 확인의 선행 조건이 되어서는 안 된다(7장·8장). 단위테스트는 새 모듈과 무관하게 동작한다.

### 3.4 결함번호 체번 체계 (확정, 2026-10-24)

**모든 결함 번호는 이 체번 체계를 기준으로 한다.** 결함이 어느 테스트·어느 프로그램에서 등록되든 같은 체계를 따른다.

| 항목 | 규칙 |
|---|---|
| 형식 | `DF-{yyMMdd}-{순번 4자리}` (예: `DF-261024-0001`). 프로젝트 안에서 유일하다 |
| 날짜 | 결함 등록일(한국 시간) |
| **순번 범위 배정** | **0001~4999: 단위테스트 결함**(단위테스트 프로그램이 지금 방식 그대로 매긴다) · **5000: 예비** · **5001~9999: 결함관리 모듈의 결함** |
| 출처 판별 | 순번이 5001 이상이면 결함관리, 4999 이하이면 단위테스트. 번호만 보고 출처를 알 수 있다 |
| 발번 | 새 모듈은 그날의 결함관리 번호를 5001부터 1씩 올린다. 하루 4,999건을 넘기면 오류로 처리한다(현실적으로 발생하지 않는다) |
| 겹침 방지 | 범위가 서로 달라 같은 번호가 나올 수 없다. 단위테스트 프로그램은 바꾸지 않는다(설계 규칙 1) |
| 점검 | 합산 통계·검색 화면은 두 출처의 번호를 함께 다루므로, 번호 중복이 없는지 점검하는 쿼리를 테스트에 포함한다 |

**왜 범위로 나누는가:** 단위테스트 프로그램은 "오늘 몇 번까지 썼는지"를 혼자 기억하며 번호를 매기고, 이 기억을 새 모듈과 공유하려면 단위테스트를 바꿔야 한다(규칙 1로 불가). 그래서 한 체계 안에서 **출처별로 번호 범위를 나눠** 같은 번호가 두 곳에서 나오지 않게 한다. 단위테스트는 지금처럼 0001부터 매겨도 이 체계를 어기지 않는다. 이미 만들어진 단위테스트 결함 번호도 그대로 유효하다.

**한계:** 단위테스트 프로그램이 하루 4,999건을 넘겨 번호를 매기면 범위가 침범된다. 단위테스트 결함의 하루 건수로는 사실상 불가능한 수준이다.

## 4. 상태·담당자·권한 규칙

### 4.1 상태

- 상태는 공통코드이고 각 코드에 분류(미조치/조치완료/종결)가 붙는다. **상태 변경에는 순서 제한을 두지 않고 권한만 검사한다**(확정, D-01). 필요하면 이후에 전이 규칙을 추가한다.
- 상태·담당자·결함식별·조치 정보 변경은 모두 이력에 기록한다.

### 4.2 담당자 기본값과 지정

- **기본값:** 결함에 연결된 **WBS Task의 작업자**(해당 기능을 만든 개발 담당자, `wbs_items`의 담당 사용자)를 **읽기 전용 조인**으로 읽어 **조치 담당자**로 채운다. 케이스가 연결되어 있으면 그 케이스의 WBS Task를 쓴다. 케이스의 **수행자**(테스트를 한 사람)는 조치 담당자가 아니다. WBS Task가 없거나 작업자가 시스템 사용자와 연결되어 있지 않으면 **미지정**이다.
- **지정·변경:** QC, PL, **운영자**(`OPERATOR`), 업무그룹리더, PMO(PM/PMO 직무), 관리자·슈퍼관리자. 케이스에 연결된 결함은 그 케이스의 QC·PL이 판정 기준이다(`ut_cases.qcUserId`, `plUserId`). 업무그룹리더는 결함의 업무단위 그룹의 리더(`groups.leaderId`)다. 독립 결함은 업무단위 그룹의 리더와 PMO가 지정하고, 업무단위가 없으면 PMO·운영자·관리자가 지정한다.
- **미배정 결함:** 지정 권한자용 "미배정 결함" 목록(DM-04)에서 처리한다.

### 4.3 권한 매트릭스

| 동작 | 권한 |
|---|---|
| 조회 | 일반 사용자: 본인이 **등록했거나 담당**인 결함만. 업무그룹리더: 본인 그룹의 결함. QC·PL: 본인이 QC·PL인 케이스의 결함 + 본인 등록·담당 결함. 관리자·PM/PMO: 프로젝트 전체 |
| 등록 | 프로젝트 구성원 전체 |
| 조치 담당자 지정·변경 | QC, PL, 운영자, 업무그룹리더, PMO, 관리자·슈퍼관리자 |
| 조치 입력·상태 변경·결함식별 | 담당자 + 지정 권한자 |
| 심각도 변경 | 등록자 본인 + 지정 권한자 |
| 삭제(논리), 코드 관리 | 관리자·슈퍼관리자 |
| 조치 재확인 목록, 설정 | PM/PMO·관리자 |
| 관리자·슈퍼관리자 | 단위테스트와 같은 원칙: 모든 기능·상태 접근 |

조회 범위는 **서버 쿼리 조건**으로 강제한다(화면 숨김만으로 처리하지 않는다). 모든 목록·통계·내보내기·상세·증적 열람이 같은 조건을 공유한다.

### 5.1 등록 진입 경로

1. **단위테스트 화면에서 진입(F-02):** 단위테스트 화면은 **고치지 않는다.** 사용자가 단위테스트 케이스 화면(주소에 `?case={id}`가 있는 팝업)에서 pmotools 확장 프로그램·위젯을 실행하면 현재 페이지 URL과 캡처를 담아 `DM-02`가 열린다. 서버가 URL의 케이스 id를 **읽기 전용 조인**으로 해석해 진입 정보(케이스, 화면 URL·ID·명, WBS Task, 작업자, QC·PL)를 채운다. 클라이언트가 보낸 표시 값은 신뢰하지 않고 id만 쓴다. 사용자는 항목을 수정할 수 있다. 확장 프로그램 없이도 `DM-02`에서 케이스를 검색(`F-18`)해 연결할 수 있다.
2. **수동 등록(F-01):** 결함관리 메뉴의 `결함 등록`. 케이스 없이 단계·Task·화면 정보를 직접 입력한다. 이후 상세 화면에서 케이스·Task를 검색해 연결할 수 있다.
3. **위젯·확장 프로그램(F-03):** 6장.


### 5.2 화면 목록 일괄 등록 규칙 (F-20, 확정)

**화면경로를 채우는 세 방식:** ① 사용자가 결함 등록 화면에서 직접 입력 ② 위젯·확장이 수집한 URL을 전달·저장하고 이를 화면 목록과 맞춰 제안 ③ 화면 목록을 미리 등록해 두고 선택. 목록이 없어도 결함 등록은 항상 가능하다.

**엑셀 양식** (`.xlsx`, 첫 시트, 첫 행은 머리글)

| 열 | 머리글 | 필수 | 규칙 |
|---|---|---|---|
| A | 화면경로 | 필수 | 500자 이내, 앞뒤 공백 제거 |
| B | 화면 URL | 선택 | 1000자 이내. `http://` 또는 `https://`로 시작하는 주소이며 `*`를 와일드카드로 쓰는 패턴도 허용 |
| C | 화면명 | 선택 | 255자 이내 |
| D | 사용 여부 | 선택 | `Y` 또는 `N`, 비우면 `Y` |

한도: 파일 5MB, 최대 5,000행.

**검증과 반영**
1. 업로드하면 서버가 파일을 검증해 **미리보기**를 보여 준다(등록 n건, 수정 n건, 오류 n건, 행별 결과). 이 단계에서는 아무것도 저장하지 않는다.
2. 필수값·길이·URL 형식·사용 여부 값, 그리고 파일 안의 **화면경로 중복**(공백 제거·대소문자 무시)을 검사한다.
3. **오류가 하나라도 있으면 반영하지 않고** 오류 보고서(행 번호, 항목, 사유)를 내려받게 한다. 오류가 없을 때만 반영한다.
4. 같은 화면경로가 이미 있으면 **수정**, 없으면 **등록**한다. 엑셀에 없는 기존 항목은 **변경하지 않는다**(삭제 없음).
5. 반영은 한 번의 트랜잭션으로 처리하고 감사 로그에 남긴다. 반영 후 결과 건수를 보여 준다.
6. 일괄 등록 엔진은 WBS·요구사항 엑셀 일괄 등록의 스테이징 방식을 참고해 **새로 만든다**(기존 코드는 수정하지 않는다).

**권한:** 등록·수정·비활성·엑셀 업로드는 운영자·PMO·관리자·슈퍼관리자. 조회와 선택은 프로젝트 구성원 전체.

**수집 URL 자동 매칭**
- 비교 전에 URL을 정규화한다: 호스트는 소문자, 쿼리스트링과 `#` 뒷부분 제거, 끝의 `/` 제거.
- 목록의 URL이 패턴이면 `*`가 임의의 문자열(`/` 포함)과 일치한다.
- 일치하는 항목이 여러 개면 **더 구체적인 것**(와일드카드가 적고 길이가 긴 것)을 고르고, 같으면 먼저 등록된 것을 고른다.
- 일치하는 항목이 없으면 화면경로를 비워 둔다.
- 자동 채움은 **제안**이다. 사용자가 이미 입력한 화면경로는 덮어쓰지 않고 언제든 수정할 수 있다. 사용 여부가 `N`인 항목은 매칭·선택에서 제외한다.

**결함 등록 화면:** 화면경로 입력칸은 목록 검색 자동완성을 제공하되 **직접 입력도 허용**한다(목록에 없는 경로도 등록 가능).

## 6. 진입·연동 설계

### 6.1 API (`/api/v1/mp/defects/*`)

| 메서드·경로 | 설명 |

| `GET /defects` | 목록(필터·페이징). 조회 범위 조건 적용 |

| `GET /defect-lookup/cases/:id` | 케이스 정보(화면 URL·작업자·QC·PL·WBS Task) 조회(읽기 전용) |
| `GET /defects/export` | 엑셀 |
| `GET /defects/action-recheck` | 조치 재확인 |
| `GET /defect-evidences/:id` | 증적 열람(조회 범위 검사 후 파일 반환) |

### 6.2 위젯·확장 프로그램

- **구조:** 테스트 대상 사이트의 위젯 또는 Chrome 확장이 현재 페이지의 URL·제목·UserAgent와 캡처 이미지를 담아 `DM-02`를 팝업(전용 창, 사이드바 없음)으로 연다. defect_manage2의 `postMessage` 방식(준비·데이터·닫기 이벤트)을 참고하되 pmotools에 맞게 다시 만든다.
- **인증:** pmotools 로그인 세션을 쓴다. 로그인되어 있지 않으면 등록 팝업이 로그인 화면으로 이동하고 로그인 후 같은 팝업으로 돌아온다(`returnTo`). 위젯·확장이 보낸 수집 데이터(URL·제목·UserAgent·캡처)는 팝업 창의 `sessionStorage`에 임시로 보관해 로그인 이동 중에도 유지하고, 등록 또는 취소하면 삭제한다.
- **URL 수집(화면경로 방식 ②):** 위젯·확장은 결함을 수집할 때 현재 페이지의 URL을 획득해 등록 화면에 전달하고, 서버는 형식(http/https)을 검증한 뒤 `screenUrl`로 저장한다. 등록 화면은 이 URL을 화면 목록(5.2)과 맞춰 **화면경로를 제안**하며 사용자가 수정할 수 있다.
- **보안:** 허용 출처 검사는 **대상 도메인 관리(DM-10)에 등록된 활성 도메인만** 통과시킨다. 메시지 스키마 검증, 캡처 이미지 크기·형식 제한(증적 저장소 설정 재사용), 요청 위조 방지, 등록 팝업의 출처 확인을 함께 둔다. 테스트 대상으로 **cinetube**(로컬 정적 사이트 `localhost:8080`)와 **secret album**(설계 단계, 계획 웹 포트 `8090`, 코드 없음)을 대상 도메인 관리에 등록한다.
- **메시지 규격:** `PMO_DEFECT_READY`(등록 팝업이 준비됨, 팝업 → 위젯·확장), `PMO_DEFECT_DATA`(수집 데이터 전달, 위젯·확장 → 팝업) 본문 `{ pageUrl, pageTitle, userAgent, screenshot, testStage?, caseId? }`, `PMO_DEFECT_CLOSE`(등록·취소 후 닫기). `screenshot`은 이미지 data URL(PNG·JPEG·WEBP, 20MB 이하)이며 서버가 저장 전에 파일로 변환한다. 수신 측은 `event.origin`이 대상 도메인 목록에 있고 `type`과 필드 형식이 맞을 때만 처리하고 나머지는 버린다.
- **케이스 지정:** 선택 사항. 지정하지 않으면 독립 결함이다.
- **확장 프로그램:** `manifest.json`의 호스트·열기 주소를 pmotools 주소와 등록 경로로 바꾼다. 현재 defect_manage2의 확장은 `http://127.0.0.1:3000/?mode=standalone#register`를 연다.
- **저장 실패 로그:** 만들지 않는다(F-17 제외). 저장 실패는 서버 로그와 화면 오류 메시지로 처리한다.

### 6.3 증적

- 이미지는 base64 JSON이 아니라 **멀티파트 업로드**로 받아 파일로 저장한다. 파일 저장 위치·제한은 단위테스트 증적 설정(`UT_EVIDENCE_ROOT`, 파일 수 3개, 크기 20MB, 허용 형식)을 기본값으로 일반화한다.
- 증적 저장은 서버 디스크 전제다. 운영 환경에서 파일 저장이 가능한지는 이 프로젝트에서 확인·관리하지 않는다(사용자 결정). 첨부 한도는 **결함당 3개, 파일당 20MB, 단위테스트와 같은 형식**으로 확정했다(D-04).

## 7. 통계 설계 (진척 통합 = 통계)

WBS 진척·실적일·이정표를 **자동으로 바꾸지 않는다.** 결함과 테스트 데이터를 집계해 보여 주기만 한다.

**집계 축:** 테스트 단계 → WBS Task → 케이스(연결된 경우) → 업무단위 → 담당자 → 기간. 케이스 없는 결함은 단계·Task·업무단위 기준으로 집계한다.

**지표**
- 결함 총수, 상태 분류별 건수(미조치·조치완료·종결), 조치완료율(조치완료+종결 / 전체)
- 심각도별·우선순위별 건수, **미조치 중대 결함** 수(미조치이면서 심각도가 기준 이상)
- 미배정 결함 수, 조치 예정일 초과 건수
- 단계별 비교 표, Task별 결함 현황, 케이스당 결함 수(결함 밀도 = 결함 수 / 수행 케이스 수)
- 담당자별 현황(DM-06)

**기존 통계와의 관계:** 단위테스트의 통계보기·이정표·엑셀은 **변경하지 않는다**(규칙 1). 새 결함 통계는 새 결함 테이블을 집계하고, 단위테스트 결함(`ut_defects`)은 **읽기 전용 조인으로 합산**한다(R-01 확정).

**단위테스트 결함 합산 방식(확정)**
- 집계 화면에서 결함의 **출처**(결함관리 / 단위테스트)를 구분해 보여 주고 합계도 낸다. 단위테스트 결함의 테스트 단계는 고정 값 "단위테스트"로 본다(`ut_defects`에는 단계 코드가 없음).
- 상태 분류 매핑: `REGISTERED`·`REFIX` → 미조치, `FIXED` → 조치완료, `VERIFIED` → 종결. 심각도: `CRITICAL`→Critical, `MAJOR`→Major, `MINOR`→Minor, `TRIVIAL`→Trivial(코드값이 같아 이름으로 대응한다). 심각도 코드를 바꾼 프로젝트에서 이름이 맞는 코드가 없으면 "기타"로 묶어 표시한다.
- 업무단위·WBS Task·케이스·담당자는 `ut_defects` → `ut_cases` 조인으로 얻는다. 같은 프로젝트의 행만 대상으로 하고 `ut_*`에는 쓰지 않는다.
- 결함 상세·조치 같은 **작업은 합산 대상이 아니다**(조회·집계만). 단위테스트 결함은 단위테스트 화면에서 계속 관리한다.

**불변조건:** 결함이 0건이면 모든 계산은 "충족"·0으로 나온다. 새 모듈의 결함 조회 실패·지연이 수행 결과 등록을 막지 않는다. 결함 집계는 조회용에 머문다.

## 8. 단위테스트와의 관계 — 무변경·읽기 전용 연계 (F-18)

**결정 2(`ut_defects` 전환, F-15)는 설계 규칙 1에 따라 철회되었다.** 단위테스트의 결함 등록·조치·검증 기능과 데이터(`ut_defects`, `ut_defect_actions`)는 그대로 둔다. 새 결함관리는 이와 별개로 병존한다.

**연계 방식(읽기 전용)**
- 결함이 케이스에 연결되면 케이스 정보(화면 URL·ID·명, 작업자, QC·PL, WBS Task, 업무단위)를 **조인 또는 API로 읽어** 보여 준다. 쓰기는 하지 않는다.
- 결함은 케이스를 소프트 참조(`caseId`, 외래 키 없음)로 가리키므로 단위테스트 모델 정의를 바꾸지 않는다.
- 단위테스트 화면에서의 진입은 화면 변경 없이 확장 프로그램·위젯으로 한다(5.1). 단위테스트 케이스 화면에 새 모듈의 결함 건수·목록을 보여 주는 영역은 만들지 않는다.

**두 결함 기능의 병존**
- 단위 단계의 결함은 기존대로 단위테스트 화면에서 관리하고, 결함관리 모듈은 통합·3자 등 그 밖의 단계와 독립 결함을 관리한다. 같은 결함을 두 곳에 입력하지 않도록 사용 안내가 필요하다.
- 단위테스트 결함은 새 결함관리 통계에 읽기 전용으로 합산한다(확정, 7장).

**회귀 방지(규칙 준수 점검)**
- 구현 중 단위테스트 관련 경로(규칙 1에 열거한 파일·폴더·`ut_*` 테이블)에 diff가 없음을 매 Phase 종료 시 확인한다.
- 단위테스트 기존 테스트(`lib/domain/ut.test.ts` 등)가 모두 통과함을 확인한다.
- 단위테스트의 수행 결과 등록은 지금처럼 결함에 의존하지 않는다. 새 모듈은 이에 어떤 영향도 주지 않는다(새 모듈 장애가 단위테스트를 막지 않음).

## 9. defect_manage2와의 관계 — 별도 시스템 (이관 없음)

**defect_manage2와는 연결하지 않는다.** 데이터 이관, 가져오기, 동기화, API 연결이 모두 범위 밖이다. 이 프로젝트는 defect_manage2의 **기능**(테스트결과 수집, 결함관리, 결함 및 조치 통계)을 pmotools 구조에 맞게 개발하는 것이다. defect_manage2의 코드·설정·위젯·확장·DB는 변경하지 않는다(규칙 2).

**초기 데이터**
- 사용자: pmotools 사용자를 그대로 쓴다.
- 결함: 새로 쌓는다. 기존 번호 체계와도 무관하다.
- 공통코드(단계·상태·심각도·우선순위·결함식별): 기본 템플릿 시드로 만들고 프로젝트 관리자가 설정 화면에서 조정한다.
- 화면경로: defect_manage2의 163건 목록은 가져오지 않는다. **사용자 입력, 결함 수집 시 URL 획득·저장, 화면 목록 일괄 등록(엑셀 포함, 5.2)** 세 방식을 모두 제공한다.

**필드 대응(기능 이해용 참고, 이관용 아님)**

| defect_manage2 | 새 모듈 | 비고 |
|---|---|---|
| `title`, `steps_to_repro`, `env_info`, `menu_name`, `screen_name`, `screen_url` | 같은 의미 컬럼 | 제목 5자 이상, URL은 http/https |
| `test_type` | `testStageCodeId` | 프로젝트별 단계 공통코드 |
| `severity`, `priority`, `status`, `defect_identification` | 각 `...CodeId` | 공통코드, 상태는 분류 지정 |
| `creator`, `assignee`(이름) | `createdBy`, `assigneeUserId`(사용자 id) | 이름 문자열이 아니라 사용자 id |
| `action_comment`, `action_due_date`, `action_start`, `action_end` | `action*` | 그대로 |
| `screenshot`(base64 TEXT) | `defect_evidences`(파일) | 파일 저장으로 변경 |
| `is_deleted` | `isActive` | 논리 삭제 |
| `defect_history` | `defect_histories` | INSERT 전용으로 강화 |

## 10. 비기능·보안·운영

- **권한 검사는 서버에서** 한다. 목록·통계·내보내기·증적 열람이 같은 조회 범위 조건을 공유한다.
- **감사:** 모든 쓰기는 이력과 감사 로그(`writeAuditLog`)에 남긴다.
- **성능:** 목록은 서버 페이징(최대 200건), 통계는 집계 쿼리를 쓴다. defect_manage2처럼 전체를 내려받아 브라우저에서 계산하지 않는다.
- **위젯 보안:** 6.2. 특히 출처 허용 목록과 요청 위조 방지를 구현 전에 확정한다.
- **배포:** 증적 파일 저장을 위해 서버 디스크가 있는 환경이 필요하다. 마이그레이션 적용과 운영 배포는 승인 후 진행하고, 모든 배포 보고서에 롤백 절차를 적는다.
- **롤백:** 새 모듈은 신규 테이블 추가 중심이라 코드 `git revert`와 신규 테이블 DROP(승인 후)으로 되돌릴 수 있다. 단위테스트와 defect_manage2는 변경하지 않으므로 롤백 대상이 아니다.

## 11. 결정 현황

이 설계서에는 **미결·후속 사항이 없다.** 모든 항목이 이 문서에서 확정되었고, **2026-10-24에 사용자가 승인했다.** 구현 단계에는 **사용자가 착수를 지시할 때까지 진입하지 않는다.** 확정한 값을 바꿔야 할 때는 이 문서와 작업계획서의 변경 이력에 기록한다.
