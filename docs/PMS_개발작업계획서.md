## 1. 문서 목적

SI/IT 프로젝트 현장에서 PM·PMO와 참여 인력이 수행하는 주간보고, 공정율, 이슈, 인력변동, 사용자 및 공통코드 관리를 하나의 내부 업무 시스템으로 구현하기 위한 개발 범위와 순서, 데이터 구조, 검증 기준을 정의한다.

본 계획서는 제공된 Excel 원형 데이터와 16개 HTML/PNG 디자인 시안을 실제 개발 단위로 변환한 기준 문서다. 미확정 정책은 임의로 확정하지 않고 착수 전 결정사항으로 분리한다.

### 2.3 디자인 구현 시 보정사항

- 모든 사용자 화면은 한국어를 기본으로 한다.
- `New Task`, `Project Alpha`, `Dashboard`, `Weekly`, `Month`, `Week`, `COMPLETE`, `IN PROGRESS`, `DELAYED` 등 시안의 영문 UI는 각각 한국어 메뉴·상태로 변경한다.
- 브랜드명처럼 유지가 필요한 영문에는 한국어 기능명을 함께 표시한다.
- 예시 데이터는 한국 이름, 국내 전화번호·주소, KRW 금액과 실제 프로젝트 도메인에 맞는 업무명으로 구성한다.
- 화면별로 다르게 표현된 상단 내비게이션과 사이드바를 하나의 앱 셸 규격으로 통일한다.
- 시안의 정적 HTML과 CDN 의존 코드는 참고용으로만 사용하고 제품 코드는 재사용 가능한 컴포넌트로 구현한다.
- 상태는 색상만으로 구분하지 않고 한국어 텍스트와 아이콘을 함께 사용한다.

## 3. 개발 목표 및 범위

### 3.1 목표

1. 프로젝트별 주차 단위 보고 업무를 중앙화한다.
2. 계획·실적·공정율과 지연 현황을 같은 데이터 기준으로 관리한다.
3. 이슈와 대응방안, 처리 상태를 추적한다.
4. 인력 투입·철수 현황을 주차별로 집계한다.
5. 역할에 따라 조회·입력·관리 권한을 분리한다.
6. 모든 주요 변경을 감사 로그로 남긴다.
7. 대시보드, 캘린더, 출력 보고서가 원천 업무 데이터와 자동 연동되게 한다.

### 3.2 포함 범위

- 로그인, 로그아웃, 비밀번호 초기화, 사용자 가입 및 승인
- 프로젝트 선택 및 프로젝트별 사용자 배정
- 주차 생성·조회·마감
- 주간보고 CRUD 및 출력/PDF
- 주간실적 CRUD, 공정율 및 지연 자동 판정
- 이슈 CRUD, 상태 변경, 첨부파일, 활동 이력
- 인력변동 CRUD 및 합계 자동 집계
- 대시보드와 공정율 추이 차트
- 월간·주간 캘린더
- 사용자, 역할, 권한, 공통코드 관리
- 사용자 활동·감사 로그 조회
- 엑셀 내보내기와 초기 기준 데이터 가져오기
- 반응형 조회 화면, 접근성, 오류·빈 상태·로딩 상태

### 3.3 제외 또는 별도 승인 범위

- 외부 고객용 포털 및 공개 페이지
- 모바일 네이티브 앱
- 실시간 채팅·메신저
- 복잡한 결재선·전자결재
- ERP·그룹웨어·메일 연동
- 외부 SSO 연동의 실제 구현(인증 방식 확정 후 포함 여부 결정)
- Excel 양방향 동기화

## 4. 권한 모델

| 역할 | 주요 권한 |
|---|---|
| 관리자 | 전체 프로젝트·사용자·코드·활동로그 관리, 모든 데이터 조회·수정, 주차 마감 |
| PM/PMO | 담당 프로젝트 설정, 주간 데이터 전체 조회·입력·수정, 보고서 출력 |
| 사용자 | 배정된 프로젝트와 담당 영역의 데이터 조회·입력·수정 |
| 게스트 | 배정된 프로젝트의 승인된 데이터 조회 및 출력 |

권한은 화면 숨김만으로 처리하지 않고 API와 데이터베이스 접근 단계에서 검증한다. 사용자 상태는 `승인대기`, `사용`, `중지`, `미사용`으로 관리하며, 초기 가입 상태는 정책 확정 전까지 `승인대기`를 기본값으로 둔다.

## 5. 권장 기술 아키텍처

### 5.1 구성

| 계층 | 권장 기술 | 적용 원칙 |
|---|---|---|
| 웹 애플리케이션 | Next.js App Router + React + TypeScript | Vercel 배포, 화면·기능·공통 컴포넌트 분리, 접근성 준수 |
| UI | CSS 변수 기반 디자인 토큰 + 컴포넌트 스타일 계층 | 시안의 색상·타이포·간격 토큰 재사용 |
| 상태·조회 | Supabase JS + 필요 시 TanStack Query + 폼 검증 | 서버 상태 캐시와 입력 상태 분리 |
| 서버 계층 | Next.js Route Handlers·Server Actions | 관리자 작업, 보고서, 다중 테이블 업무 로직 분리 |
| 데이터베이스 | Supabase Hosted PostgreSQL | 관계형 업무 데이터, RLS, 트랜잭션, 이력 조회 |
| 스키마 관리 | Supabase CLI SQL migrations | 로컬·staging·production 스키마 재현과 버전 관리 |
| 인증 | Supabase Auth | 이메일·비밀번호 우선, SSO 확장 가능 구조 |
| 파일 | Supabase Storage | 비공개 버킷, Storage RLS, Signed URL |
| 보고서 | 인쇄 전용 HTML/CSS + PDF 변환 | A4 레이아웃, 한글 폰트 임베딩 검증 |
| 테스트 | Vitest, API 통합 테스트, Playwright | 단위→통합→E2E 순차 검증 |

환경별 상세 구성과 보안·배포 기준은 `docs/PMS_개발환경_아키텍처.md`를 단일 기준으로 사용한다. 브라우저 일반 CRUD는 사용자 JWT와 RLS를 유지하고 관리자·보고서·트랜잭션 작업만 Vercel 서버 계층으로 분리한다.

### 5.2 프론트엔드 모듈 구조

```text
apps/web/
  app/                 # Next.js 라우팅, 레이아웃, 서버 엔드포인트
  lib/                 # Supabase 클라이언트, 인증, 검증, 오류 처리
  components/          # 공통 입력, 테이블, 배지, 모달, 피드백
  features/
    auth/
    dashboard/
    calendar/
    weekly-report/
    weekly-progress/
    issue/
    staff-change/
    user-admin/
    code-admin/
    activity-log/
packages/
  ui/                  # 디자인 토큰과 공통 컴포넌트
  domain/              # 공통 업무 타입과 규칙
supabase/
  migrations/          # SQL 스키마 변경 이력
  seed.sql             # 비식별 로컬·개발 데이터
```

화면 파일에 API 호출, 권한 판정, 모달 관리, 데이터 변환을 누적하지 않는다. 기능별 서비스·훅·검증 스키마로 분리하고 화면은 표시와 사용자 입력 전달에 집중한다.

캘린더는 별도 중복 데이터를 만들기보다 주차, 목표일, 이슈, 인력변동 데이터를 통합 조회하는 API 또는 데이터베이스 뷰로 구성한다.

## 7. 주요 업무 규칙

### 7.1 주차

- 주차 기준은 프로젝트별 시작일·종료일과 함께 관리한다.
- ISO 주차 사용 여부, 주 시작 요일, 공휴일 반영 여부를 착수 전에 확정한다.
- 마감된 주차는 관리자 또는 PM/PMO만 재개할 수 있다.

### 7.2 공정율·지연

- 공정율 입력 범위는 0~100이며 소수점 허용 여부를 정책으로 정한다.
- 목표일이 지났고 공정율이 100 미만이면 지연 후보로 판정한다.
- 자동 판정과 사용자의 수동 상태를 구분해 저장한다.
- 영역별·프로젝트 전체 공정율의 가중치 방식은 별도 확정한다.

### 7.3 이슈

- 기본 상태는 `접수`, `진행중`, `완료`다.
- 완료 시 완료일과 완료자를 자동 기록한다.
- 상태 변경과 주요 필드 변경은 활동 로그에 남긴다.

### 7.4 인력변동

- 구분은 `투입`, `철수`로 관리한다.
- 영역별 합계와 전체 합계는 서버에서 재계산한다.
- 음수 인원과 합계 직접 입력은 허용하지 않는다.

| 인력변동 | 주차별 조회, 일괄 저장, 합계 조회 |
| 캘린더 | 기간·영역·유형별 통합 이벤트 조회 |
| 사용자 | 사용자 CRUD, 상태·역할 변경, 본인정보 조회·수정 |
| 공통코드 | 그룹·코드 CRUD, 사용 코드 조회 |
| 활동로그 | 사용자·기간·행위별 검색, 상세 조회 |
| 내보내기 | 주간보고 PDF, 업무별 Excel 내보내기 |

목록 API는 검색·필터·정렬·페이지네이션을 공통 규격으로 제공한다. 수정 API는 낙관적 잠금으로 동시 편집 충돌을 감지한다.

## 9. 화면별 개발 완료 기준

### 9.1 공통·인증

### 9.3 조회·분석·관리

- 대시보드: 주차·기간 필터가 모든 카드·차트에 동일 적용

- 공정율 추이: 계획·실적 비교, 영역 필터, 데이터 없음 상태

- 활동 로그: 기간·사용자·행위 필터, 시간순 조회, 원본 변경요약 확인

## 13. 보안·운영 계획

- 비밀번호는 단방향 강한 해시로 저장하고 평문 로그를 금지한다.
- 세션·토큰은 만료, 재발급, 철회 정책을 둔다.
- API는 서버 측 RBAC와 프로젝트 멤버십을 모두 검사한다.
- 입력값 검증, SQL Injection, XSS, CSRF, 파일 확장자·크기·MIME 검사를 적용한다.
- 활동 로그에는 비밀번호, 토큰, 개인정보 원문을 기록하지 않는다.
- 데이터베이스 계정은 최소 권한을 적용하고 개발·운영 계정을 분리한다.
- 운영 배포 전 백업·복구 리허설과 롤백 절차를 검증한다.
- 구조·데이터 이관 및 삭제 작업은 백업과 사용자 승인 없이 수행하지 않는다.

## 16. 개발 완료 정의(Definition of Done)

- 승인된 요구사항과 16개 화면의 기능 대응표가 최신 상태다.
- 사용자 대상 UI·검증·오류·상태·빈 화면이 모두 한국어다.
- 역할·프로젝트·영역 권한이 화면과 API에서 일치한다.
- 단위·통합·E2E·UAT 결과가 기록되고 미해결 중대 결함이 없다.
- 대시보드·차트·캘린더·출력 수치가 원천 데이터와 일치한다.
- 운영 환경에서 로그인, 핵심 CRUD, 출력, 백업·복구, 롤백을 검증했다.
- 환경변수·토큰·개인정보가 저장소와 로그에 노출되지 않는다.
- 사용자 메뉴얼, 운영자 메뉴얼, API·ERD·배포 문서가 최신 상태다.
- 사용자 승인 후에만 원격 배포한다.
