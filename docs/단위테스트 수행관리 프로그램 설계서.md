# 단위테스트 수행관리 프로그램 설계서

Oct 18, 2026 · @Bryan Jung

## 1. 개요

모든 단위테스트 시나리오·케이스·수행·결함을 WBS ID(Leaf 태스크)에 종속시켜, WBS 태스크의 '개발완료'를 단위테스트 결과로만 인정(0 또는 1)하는 수행관리 프로그램이다.

**목적**

- 개발 진척 보고의 근거를 '자가 신고'에서 '테스트 증적'으로 전환
- WBS ID 기준으로 테스트 누락·지연·결함 집중 구간을 즉시 식별
- 통합테스트 진입 품질게이트를 정량 기준으로 운영

**범위**: 단위테스트 계획 → 시나리오/케이스 작성 → 검토·승인 → 수행·증적 → 결함·재테스트 → WBS 완료 판정 → 진척·품질 보고. 통합/인수테스트는 확장 대상으로 데이터 구조만 열어둔다.

**참고자료 반영 사항**

| 참고 내용 | 설계 반영 |
| --- | --- |
| 기능을 작게 잘라 시나리오 작성 (회원가입 → 입력·조건·결과·예외로 분리) | 시나리오 = WBS Leaf 1개 이하의 기능 단위, 케이스 = 검증 규칙 1개 |
| 조건 · 행동 · 예상결과 3요소 | 케이스 필수 필드: 사전조건, 수행절차, 예상결과 |
| 정상만 쓰지 말고 실패 케이스를 반드시 붙일 것 | 시나리오당 정상 ≥ 1, 예외·경계 ≥ 2 미충족 시 검토요청 차단 |
| 예상결과는 한 문장으로 짧고 확인 가능하게 | 예상결과 200자 제한, '정상 처리' 류 모호어 입력 경고 |
| 테스트 항목을 WBS 일정표와 연결 | 케이스·수행·결함 모두 WBS ID 필수, 일정은 WBS 계획일 상속 |
| 상태값은 작성 / 확인중 / 통과 / 수정 필요 정도로 단순하게 | 케이스 상태 7단계로 표준화 (6장) |
| 항목이 많으면 결제·가입·권한·저장 등 영향 큰 흐름부터 | 케이스 우선순위 H/M/L, H 케이스 100% 수행을 게이트 조건으로 사용 |

> 첫 번째 참고 사이트(네이버 블로그)는 접근이 차단되어 반영하지 못했다. 본문을 받으면 양식 항목을 보완한다.

**설계 원칙**

1. 모든 데이터는 project\_id로 격리한다. 사용자는 배정된 프로젝트의 데이터만 조회·처리한다.
2. WBS ID 없는 테스트 데이터는 존재할 수 없다 (FK 필수, Leaf 레벨만 허용).
3. 진척은 0/1로만 인정한다. 부분 완료율은 보고 지표에서 제외한다.
4. 테스트 결과는 QC 확인 → PL 확인 2단계 승인을 거쳐야 진척으로 인정한다. 수행자, QC 확인자, PL 확인자는 서로 다른 사람이어야 한다.
5. Pass 판정 후 결과 수정 불가. 재수행은 신규 차수로만 기록한다.
6. 증적 없는 Pass는 Pass가 아니다.

## 2. 통제 관점 (PMO)

WBS 태스크의 개발완료(1)는 아래 4개 조건을 모두 충족한 날에만 시스템이 자동 확정하며, 개발자·PL의 수동 입력은 허용하지 않는다.

| # | 개발완료 인정 조건 | 시스템 검증 방식 |
| --- | --- | --- |
| 1 | 해당 WBS ID의 시나리오·케이스가 PL 승인 완료 | 승인 상태 케이스 ≥ 1, 예외·경계 비율 충족 |
| 2 | 승인된 케이스 전체 수행 (N/A는 PL 사유 승인 시만 제외) | 수행률 = 100% |
| 3 | 최종 차수 전 케이스 Pass, Open 결함 0건 (Minor는 조치계획 승인 시 허용) | 결함 상태 집계 |
| 4 | Pass 건 전체 증적 첨부 + QC 확인 + PL 확인 완료 | 증적 첨부율 = 100%, approval\_status = 승인완료 100%, 수행자·QC·PL 상이 |

**이해관계자 역할 (RACI)**

| 활동 | 개발자 | QC | PL/모듈리더 | 현업 | PMO | PM |
| --- | --- | --- | --- | --- | --- | --- |
| 시나리오·케이스 작성 | R | C | A | C | I | I |
| 케이스 검토·승인 | C | C | R/A | C (H등급) | I | I |
| 수행·증적 등록 | R | I | A | – | I | I |
| 테스트 결과 QC 확인 (1차 승인) | I | R/A | I | – | I | – |
| 테스트 결과 PL 확인 (최종 승인) | I | I | R/A | – | I | I |
| 결함 조치·재테스트 | R | C | A | – | I | I |
| 샘플링 감사 | C | C | C | – | R | A |
| 통합테스트 진입 게이트 | I | C | C | C | R | A |

QC는 증적·실제결과·예상결과 일치 여부와 케이스 수행의 적정성(형식적 수행 여부)을 확인하고, PL은 기능 완성도와 WBS 완료 관점에서 최종 승인한다. QC를 PL 앞에 두어, 진척 압박을 받는 PL이 단독으로 Pass를 확정하지 못하게 한다.

**권력 구조상 주의점**

- PL은 진척 압박의 당사자이자 승인자다. 자기 모듈 승인만으로 게이트가 열리지 않도록 PMO 샘플링(케이스 10%, H등급 우선)을 게이트 조건에 포함한다.
- 현업은 예외 케이스의 기준(무엇을 막아야 하는가)을 가진 유일한 주체다. H등급 시나리오는 현업 확인(C)을 필수로 둬, 통합·인수테스트 단계의 '요건 해석 차이' 결함을 앞당겨 걸러낸다.
- 다수 협력사가 참여하는 경우 결함 귀속(협력사별 결함 밀도)이 계약 정산·패널티 근거가 되므로, 결함에 담당 협력사 코드를 필수로 기록한다.

**핵심 리스크**

| 리스크 | 유형 | 발생확률(추정) | Trigger | 대응 |
| --- | --- | --- | --- | --- |
| 형식적 Pass (증적 없는 일괄 Pass) | 품질 | 40% | 마감 전 3일 내 Pass 급증 | 증적 필수 + 일 단위 Pass 급증 경보 + PMO 샘플링 |
| 케이스 사후 작성 (개발 후 끼워맞추기) | 품질 | 50% | 케이스 승인일 > 개발 착수일 | 설계완료 시점 케이스 승인을 WBS 착수 선행조건으로 설정 |
| WBS 변경 시 테스트 데이터 고아화 | 일정 | 30% | WBS 분할·병합·삭제 | WBS ID 이력 테이블 + 동기화 시 매핑 이관 화면 |
| 협력사 간 결함 책임 공방 | 계약/정치 | 25% | 인터페이스 결함 반복 | 결함 원인 모듈·협력사 코드 필수, 주간 결함 귀속 리뷰 |

## 3. 기능 구성

7개 모듈로 구성하며, M1(WBS 연계)이 모든 모듈의 기준 키를 공급한다.

| 모듈 | 주요 기능 | 주 사용자 | 우선순위 |
| --- | --- | --- | --- |
| M1 WBS 연계 | WBS 마스터 동기화(엑셀/API), Leaf 태스크 식별, WBS ↔ 프로그램 매핑, WBS ID 변경 이력·매핑 이관 | PMO | Phase 1 |
| M2 시나리오·케이스 관리 | 시나리오/케이스 작성, 엑셀 일괄 업로드·다운로드, 표준 템플릿, 검토요청·승인·반려, 버전 관리 | 개발자, PL | Phase 1 |
| M3 수행 관리 | 담당자·예정일 배정(WBS 계획일 상속), 결과 판정, 증적 첨부, QC 확인 → PL 확인 2단계 승인, 차수별 재수행 | 개발자, PL | Phase 1 |
| M4 결함 관리 | 결함 등록(수행 Fail 시 자동 생성), 조치·재테스트 연결, 심각도·원인·협력사 분류 | 개발자, PL, QA | Phase 1 |
| M5 진척·품질 대시보드 | WBS 트리별 UT 상태, 모듈·협력사·담당자별 지표, 지연·경보 목록 | PM, PMO | Phase 2 |
| M6 품질게이트·보고 | 게이트 체크리스트 자동 판정, 주간보고·경영진 요약 생성, 엑셀 산출물 출력 | PMO, PM | Phase 2 |
| M7 공통 관리 | 프로젝트(project\_id) 등록, 프로젝트별 사용자·역할(QC·PL) 배정, 협력사, 공통코드, 감사로그, 마감 잠금 | 관리자 | Phase 1 |

**권장 기술 구성**: Spring Boot(REST API) + Vue 3(SPA) + Oracle 또는 PostgreSQL, 증적 파일은 오브젝트 스토리지 또는 NAS(파일 해시 저장). 별도 시스템이 아닌 기존 프로젝트관리 플랫폼의 모듈로 편입하는 것을 권고한다(10장).

## 4. 데이터 모델

PROJECT가 데이터 격리 단위, WBS\_TASK가 테스트 귀속 기준이다. 전 테이블이 project\_id를 보유해 프로젝트별로 데이터·권한·집계를 분리하고, 케이스·수행·승인·결함 테이블은 wbs\_id도 함께 보유한다(집계 성능과 WBS 변경 추적을 위한 의도적 비정규화).

&#91;embedded content: 단위테스트 관리 ERD · 9개 테이블 (AUDIT\_LOG 제외)\]

UT\_CASE, UT\_EXECUTION, DEFECT는 그림의 부모 관계와 별도로 wbs\_id를 상속 보관해, WBS 단위 집계를 조인 없이 수행한다.

**엔터티 정의**

| 테이블 | 설명 | 주요 컬럼 | 관계 |
| --- | --- | --- | --- |
| PROJECT | 프로젝트 마스터 (데이터 격리 단위) | project\_id(PK, 프로젝트 코드), project\_name, customer\_cd, pm\_id, start\_dt, end\_dt, ut\_start\_dt, ut\_end\_dt, status, lock\_yn | 전 테이블 1:N |
| WBS\_TASK | WBS 마스터 동기화 사본 | project\_id(FK), wbs\_id, parent\_wbs\_id, wbs\_level, leaf\_yn, task\_name, owner\_id, vendor\_cd, plan\_start, plan\_end, actual\_end, dev\_complete\_yn, dev\_complete\_dt / PK(project\_id, wbs\_id) | PROJECT 1:N, 자기참조 트리 |
| WBS\_ID\_HIST | WBS ID 변경 이력 | hist\_id(PK), project\_id(FK), old\_wbs\_id, new\_wbs\_id, change\_type(분할/병합/변경/삭제), changed\_at | WBS\_TASK 1:N |
| PROGRAM | 개발 대상 프로그램 | project\_id(FK), program\_id, program\_name, program\_type(화면/API/배치/리포트), module\_cd, screen\_id / PK(project\_id, program\_id) | PROJECT 1:N |
| WBS\_PROGRAM\_MAP | WBS ↔ 프로그램 매핑 | project\_id, wbs\_id, program\_id / PK(3개 컬럼) | N:M |
| UT\_SCENARIO | 테스트 시나리오(기능 단위) | scenario\_id(PK), project\_id(FK), wbs\_id(FK 필수), program\_id, req\_id, scenario\_name, priority(H/M/L), writer\_id, reviewer\_id, status, approved\_at, version | WBS\_TASK 1:N |
| UT\_CASE | 테스트 케이스(검증 규칙 단위) | case\_id(PK), project\_id, scenario\_id(FK), wbs\_id, case\_type(정상/예외/경계), precondition, test\_steps, input\_data, expected\_result, priority, status, active\_yn | UT\_SCENARIO 1:N |
| UT\_EXECUTION | 케이스 수행 결과(차수별) | exec\_id(PK), project\_id, case\_id(FK), wbs\_id, round\_no, env\_cd, executor\_id, exec\_dt, actual\_result, verdict(Pass/Fail/Blocked/N/A), approval\_status(QC대기/PL대기/승인완료/반려), qc\_id, pl\_id | UT\_CASE 1:N |
| UT\_APPROVAL | 수행 결과 승인 이력 (QC 확인 → PL 확인) | approval\_id(PK), project\_id, exec\_id(FK), wbs\_id, approval\_step(QC/PL), approver\_id, decision(승인/반려), reject\_reason\_cd, comment, acted\_at | UT\_EXECUTION 1:N |
| UT\_EVIDENCE | 수행 증적 | evidence\_id(PK), project\_id, exec\_id(FK), file\_name, file\_path, file\_hash(SHA-256), uploaded\_at | UT\_EXECUTION 1:N |
| DEFECT | 결함 | defect\_id(PK), project\_id, exec\_id(FK), case\_id, wbs\_id, severity, defect\_type, cause\_module\_cd, vendor\_cd, assignee\_id, status, found\_dt, fixed\_dt, retest\_exec\_id | UT\_EXECUTION 1:N |
| AUDIT\_LOG | 변경 감사 | log\_id(PK), project\_id, table\_name, record\_id, action, before\_val, after\_val, actor\_id, acted\_at | 전 테이블 |

**공통코드 추가**: APPROVAL\_STEP(QC, PL), APPROVAL\_STATUS(QC대기, PL대기, 승인완료, 반려), REJECT\_REASON(증적 불충분, 예상결과 불일치, 케이스 부적정, 기타)

**무결성 규칙**

1. 모든 하위 테이블의 project\_id는 상위 레코드에서 자동 상속하며, 상위와 다른 project\_id 조합은 FK로 차단한다. 모든 조회·집계 API는 project\_id를 필수 조건으로 받는다.
2. UT\_SCENARIO의 (project\_id, wbs\_id)는 leaf\_yn = 'Y'이고 삭제되지 않은 WBS만 허용한다.
3. UT\_CASE, UT\_EXECUTION, UT\_APPROVAL, DEFECT의 wbs\_id는 상위 레코드에서 자동 상속하며 직접 수정할 수 없다.
4. UT\_APPROVAL은 QC 승인 행이 있어야 PL 행을 생성할 수 있다. 어느 단계든 반려 시 해당 수행 차수는 종료되고, 재수행은 round\_no + 1로 처음부터 다시 승인받는다.
5. executor\_id, QC approver\_id, PL approver\_id는 서로 달라야 한다.
6. WBS 분할·병합 시 WBS\_ID\_HIST 기록 후, PMO가 이관 화면에서 시나리오 단위로 신규 WBS ID에 재매핑한다. 미이관 시나리오는 '고아' 목록으로 대시보드에 노출한다.
7. UT\_EXECUTION, UT\_APPROVAL은 INSERT만 허용한다(approval\_status 갱신 제외).

**ID 채번 규칙**

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 시나리오 | UTS-{WBS ID}-{순번 2자리} | UTS-2.3.1.4-01 |
| 케이스 | {시나리오 ID}-{순번 3자리} | UTS-2.3.1.4-01-003 |
| 결함 | DF-{yyMMdd}-{순번 4자리} | DF-261020-0012 |

채번 순번은 project\_id별로 독립 관리하며, 유일성은 (project\_id, ID)로 보장한다. 프로젝트 간 산출물이 섞일 수 있는 엑셀 출력물에는 프로젝트 코드 열을 첫 열로 고정한다. 케이스 ID에 WBS ID를 포함해 엑셀 산출물만으로도 추적이 가능하게 하되, WBS ID 변경 시 기존 케이스 ID는 유지하고 wbs\_id 컬럼만 갱신한다(ID 재채번 금지).

## 5. 단위테스트 케이스 표준 양식

화면 입력과 엑셀 업로드 양식은 동일한 필드 순서를 사용하며, 필수 13개 필드가 비어 있으면 검토요청이 차단된다.

| 구분 | 필드 | 필수 | 작성 기준 |
| --- | --- | --- | --- |
| 식별 | 프로젝트 코드 (project\_id) | Y | 로그인 사용자의 현재 프로젝트로 자동 설정, 엑셀 업로드 시 불일치 행 거부 |
| 식별 | WBS ID | Y | 해당 프로젝트의 Leaf 태스크만 선택 가능 (드롭다운) |
| 식별 | 시나리오 ID / 케이스 ID | Y | 프로젝트별 자동 채번 |
| 대상 | 프로그램 ID · 화면 ID | Y | WBS\_PROGRAM\_MAP에 매핑된 항목만 선택 |

| 대상 | 테스트 대상 | Y | 검증 규칙 1개를 한 줄로 (예: 주문수량 입력값 검증) |

## 6. 수행 프로세스와 상태 전이

케이스는 설계 완료 시점에 승인되어야 하며, 수행 결과는 QC 확인 → PL 확인을 모두 통과해야 진척으로 인정된다. Fail 또는 반려는 신규 차수 재수행으로만 다시 승인 단계에 들어간다.

&#91;embedded content: 단위테스트 케이스 상태 전이 · 7개 상태, 반려·재수행 루프\]

QC 또는 PL이 반려하면 해당 차수는 종료되고, 보완 후 재수행한 신규 차수가 QC 확인부터 다시 거친다. 해당 WBS의 전 케이스가 PL확인완료되면 개발완료가 자동 확정된다.

**단계별 절차**

1. **WBS 동기화 (PMO)**: 프로젝트별로 WBS 기준선 확정 후 Leaf 태스크와 프로그램 매핑을 적재한다. 이후 변경은 일 1회 배치 + 수동 동기화.
2. **시나리오·케이스 작성 (개발자)**: 상세설계 완료 시점에 작성한다. WBS 착수일 이전 승인이 목표이며, 착수일 경과 후 미승인 WBS는 경보 대상이다.
3. **검토·승인 (PL, H등급은 현업 확인)**: 작성 검증 규칙 통과 후 검토요청. 반려 시 사유 필수.
4. **수행 (개발자)**: DEV 또는 STG 환경에서 수행하고 판정·증적을 등록한다. Pass 등록 즉시 approval\_status = QC대기.
5. **QC 확인 (QC, 1차 승인)**: 증적 존재·식별 가능 여부, 실제결과와 예상결과 일치, 수행절차 준수 여부를 확인한다. 승인 시 PL대기, 반려 시 사유코드와 함께 개발자에게 반송.
6. **PL 확인 (PL, 최종 승인)**: 기능 완성도와 WBS 완료 관점에서 확인한다. 승인 시 승인완료, 반려 시 개발자에게 반송.
7. **결함 조치·재수행**: Fail 시 결함 자동 생성 → 조치 완료 → 동일 케이스를 round\_no + 1로 재수행. QC·PL 반려도 보완 후 round\_no + 1로 재수행하며 QC 확인부터 다시 받는다.
8. **WBS 완료 판정 (시스템)**: 2장의 4개 조건 충족 시 dev\_complete\_yn = 'Y', dev\_complete\_dt 기록 후 WBS 진척에 반영.

**승인 SLA (권장)**: QC 확인 2영업일, PL 확인 1영업일. 초과 건은 대시보드 경보 및 승인자 일일 알림 대상이다.

**상태 정의**

| 대상 | 상태 | 진입 조건 |
| --- | --- | --- |
| 케이스 | 작성중 | 신규 등록 |
| 케이스 | 검토요청 | 필수 필드 + 작성 검증 규칙 충족 |
| 케이스 | 승인 | PL 승인 (반려 시 작성중 복귀) |
| 케이스 | 수행중 | 최초 수행 결과 등록, 또는 Fail·반려 후 재수행 대기 |
| 케이스 | Pass (QC대기) | 최종 차수 판정 Pass + 증적 첨부 |
| 케이스 | QC확인 (PL대기) | QC 승인 |
| 케이스 | PL확인완료 | PL 승인 (진척 인정 단위) |
| WBS 단위 UT | 미착수 → 케이스작성 → 수행중 → 결함조치중 → 승인대기 → 완료 | 하위 케이스 상태 집계로 자동 산출 |

참고자료의 4단계 상태(작성 / 확인중 / 통과 / 수정 필요)는 각각 작성중 / 검토요청·QC확인 / PL확인완료 / 수행중(Fail·반려)에 대응한다. 감사 대응을 위해 케이스 승인과 결과 확인을 분리하고, 결과 확인을 QC·PL 2단계로 나눴다.

## 7. 진척·품질 지표와 게이트 기준

진척은 'UT 완료 WBS 수'(0/1 합산) 하나로 보고하고, 나머지 지표는 그 원인을 설명하는 선행지표로 쓴다. 아래 임계값은 권장 초기값이며 프로젝트 착수 시 PMO 표준으로 확정한다.

| 지표 | 계산식 | Green | Yellow | Red |
| --- | --- | --- | --- | --- |
| UT 진척 SPI | 기준일까지 UT 완료 WBS 수 ÷ 기준일까지 계획 종료 WBS 수 | ≥ 0.95 | 0.85–0.94 | < 0.85 |
| 케이스 적시 승인율 | 착수일 이전 승인된 WBS 수 ÷ 착수한 WBS 수 | ≥ 90% | 70–89% | < 70% |
| 수행률 | 수행 케이스 ÷ 승인 케이스 (WBS 계획 종료일 도래분) | 100% | 90–99% | < 90% |
| 1차 Pass율 | 1차수 Pass ÷ 1차수 수행 | 80–95% | > 95% (형식 수행 의심) | < 70% |
| 최종 Pass율 | 최종 차수 Pass ÷ 수행 케이스 | ≥ 98% | 95–97% | < 95% |
| QC 반려율 | QC 반려 건 ÷ QC 처리 건 | 5–15% | < 5% (형식 확인 의심) | > 25% |
| PL 반려율 | PL 반려 건 ÷ PL 처리 건 | ≤ 5% | 6–10% | > 10% (QC 기준 불일치) |
| 승인 대기 리드타임 | 평균(PL 승인일 − Pass 등록일) | ≤ 3영업일 | 4–5영업일 | > 5영업일 |
| 예외·경계 비율 | (예외 + 경계) ÷ 전체 케이스 | ≥ 60% | 50–59% | < 50% |
| 결함 밀도 | 결함 수 ÷ 케이스 수 | 프로젝트 기준선 ±30% | 기준선 대비 −50% 이하 (누락 의심) | 기준선 대비 +50% 이상 |
| 결함 조치 리드타임 | 평균(조치일 − 발견일), Critical·Major | ≤ 2일 | 3–5일 | > 5일 |
| 증적 첨부율 | 증적 있는 Pass ÷ 전체 Pass | 100% | – | < 100% |

모든 지표는 project\_id 단위로 산출하며, 그룹·본부 보고 시에만 프로젝트 간 비교를 제공한다.

1차 Pass율이 지나치게 높거나, 결함 밀도·QC 반려율이 지나치게 낮은 것도 경보로 본다. 단위테스트에서 결함이 안 나온다는 것은 대개 품질이 아니라 테스트 강도의 문제다.

**통합테스트 진입 게이트 (모듈 단위)**

- [ ] 대상 Leaf WBS의 UT 완료율 ≥ 95%, 미완료 WBS는 PM 승인된 잔여계획 보유
- [ ] H등급 케이스 수행률 100%, 최종 Pass율 100%
- [ ] Open 결함 Critical·Major 0건
- [ ] 증적 첨부율 100%
- [ ] PMO 샘플링 감사(케이스 10%) 부적합률 ≤ 5%
- [ ] 고아 시나리오(WBS 미매핑) 0건

게이트 미충족 시 진입을 보류하거나, PM이 미충족 항목·잔여 리스크·완료 예정일을 명시한 조건부 진입을 승인한다. 조건부 진입은 본부장 보고 대상이다.

| UT-032 | PL 확인함 | PL대기 목록, QC 의견 확인 후 최종 승인·반려, WBS별 잔여 건수 표시 | PL |

QC·PL 확인함은 일괄 승인을 제공하지 않는다. 건별 증적 열람 기록이 있어야 승인 버튼이 활성화된다.

**UT-050 대시보드 경보 목록 (기본 규칙)**

- 착수일 경과 + 케이스 미승인 WBS
- 계획 종료일 경과 + UT 미완료 WBS (지연일수 내림차순)
- 3일 내 Pass 급증 WBS (평균 대비 3배 이상)
- Critical·Major 결함 48시간 이상 미조치
- QC 확인 2영업일, PL 확인 1영업일 SLA 초과 건
- 고아 시나리오

## 9. 연계 인터페이스와 권한·감사

WBS 마스터 연계(IF-01)만 Phase 1 필수이며, 나머지는 Phase 2 이후 선택 연계다.

**연계 인터페이스**

| IF ID | 대상 | 방향 | 방식 | 주기 | Phase |
| --- | --- | --- | --- | --- | --- |
| IF-01 | WBS 마스터 (PMS 또는 엑셀 WBS) | 수신 | REST API 또는 표준 엑셀 업로드 | 일 1회 배치 + 수동 | 1 |
| IF-02 | WBS 진척 반영 | 송신 | dev\_complete\_yn, dev\_complete\_dt 회신 | 실시간(이벤트) | 1 |
| IF-03 | 자동화 테스트 결과 (JUnit XML 등) | 수신 | CI 파이프라인에서 업로드, 케이스 ID 매핑 시 수행 자동 등록 | 빌드 시 | 2 |
| IF-04 | 형상관리 (Git) | 수신 | 커밋 메시지의 WBS ID 태그 수집 → 개발 착수 실적 근거 | 일 1회 | 2 |
| IF-05 | 결함관리 도구 (Jira 등) | 양방향 | 결함 동기화 (사내 표준 도구가 있을 때만) | 실시간 | 선택 |

**권한 매트릭스** (C 생성, R 조회, U 수정, A 승인·확인)

| 기능 | 개발자 | QC | PL | 현업 | PMO | PM | 관리자 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 프로젝트·사용자 배정 | – | – | – | – | CU | A | CU |
| WBS 동기화·이관 | R | R | R | – | CU | R | CU |
| 시나리오·케이스 | CRU (본인 WBS) | R | RU (담당 모듈) | R | R | R | R |
| 케이스 검토·승인 | – | C | A | A (H등급) | R | R | – |
| 수행 결과 등록 | CR (본인 배정) | R | R | – | R | R | – |
| 결과 QC 확인 | – | A | R | – | R | R | – |
| 결과 PL 확인 | – | R | A | – | R | R | – |
| 결함 | CRU | CRU | CRU | R | R | R | R |
| 대시보드·보고 | R (본인) | R | R (모듈) | R (업무) | R | R | R |
| 게이트 판정 | – | C | R | R | U | A | – |
| 마감 잠금·해제 | – | – | – | – | U | A | U |

모든 권한은 프로젝트 단위로 부여한다. 같은 사용자가 프로젝트 A에서는 QC, 프로젝트 B에서는 PL일 수 있으며, 한 프로젝트 안에서 QC와 PL 역할의 동시 보유는 차단한다.

**감사 통제**

- Pass 판정 수행 결과는 수정·삭제 불가. 오류 정정도 신규 차수로만 처리한다.
- 수행자 = QC 확인자, 수행자 = PL 확인자, QC = PL, 케이스 작성자 = 승인자 조합은 시스템에서 차단한다. QC·PL 반려 이력은 삭제할 수 없다.
- 증적 파일은 업로드 시 SHA-256 해시를 저장해 사후 교체를 탐지한다.
- 단계 마감(예: 단위테스트 종료일) 후 해당 범위는 잠금 처리하며, 해제는 PM 승인과 사유 기록을 요구한다.
- 판정·상태·WBS 매핑 변경은 전량 AUDIT\_LOG에 기록하고, 내부감사 요청 시 WBS ID 기준으로 추출한다.

## 10. 구축 시나리오와 권고안

권고: 시나리오 B(프로젝트관리 플랫폼 모듈 편입)를 2단계로 추진하되, 개발 착수 전까지는 시나리오 A(표준 엑셀)로 통제를 먼저 시작한다.

**시나리오 비교** (공수는 1인 풀타임 기준 추정치)

| 기준 | A. 표준 엑셀 + 업로드 | B. 프로젝트관리 플랫폼 모듈 편입 | C. 상용 테스트 도구 커스터마이징 |
| --- | --- | --- | --- |
| 구축 기간 | 1–2주 | 8–12주 (Phase 1: 6주) | 4–8주 + 구매 절차 |
| 투입 공수 | 0.5 M/M | 3–4 M/M | 1–2 M/M + 라이선스 |
| WBS 연계 통제력 | 낮음 (수작업 대조) | 높음 (FK·자동 판정) | 중간 (플러그인·커스텀 필드 의존) |
| 감사 대응 (수정 이력·증적) | 낮음 | 높음 | 높음 |
| 0/1 진척 자동 반영 | 불가 | 가능 | API 개발 필요 |
| 협력사 사용 편의 | 높음 | 중간 (교육 필요) | 중간 (계정·라이선스 배분) |
| 주요 리스크 | 버전 난립, 형식적 Pass 탐지 불가 | 일정 내 구축 실패 시 공백 | 그룹 보안심의·구매 지연, 데이터 외부 저장 |
| 재사용성 (다른 프로젝트) | 양식만 재사용 | 높음 | 계약 범위 내 |

**권고 근거**

1. 0/1 진척 자동 판정과 WBS ID 무결성은 B만 완전 충족한다. A는 통제가 아니라 기록이고, C는 WBS 연계에 별도 개발이 들어가 B와 공수 차이가 줄어든다.
2. 다수 회사·팀이 참여하는 프로젝트 관리 플랫폼을 이미 설계 중이므로, 단위테스트를 그 플랫폼의 모듈로 편입하면 WBS·사용자·권한 기반을 재사용해 Phase 1 공수를 줄일 수 있다.
3. A를 선행 적용하면 양식·채번·작성 규칙이 B의 엑셀 업로드 양식과 동일해, 이관 비용 없이 데이터를 그대로 적재할 수 있다.

**구축 단계**

| 단계 | 범위 | 기간 (추정) | 완료 기준 |
| --- | --- | --- | --- |
| Phase 0 | 표준 엑셀 양식·채번·작성 규칙 확정, 파일럿 1개 모듈 적용 | 2주 | 파일럿 모듈 케이스 승인율 100% |
| Phase 1 | M1·M2·M3·M4·M7 (WBS 연계, 케이스, 수행, 결함, 공통), IF-01·02 | 6주 | 엑셀 데이터 전량 적재, WBS 개발완료 자동 판정 가동 |
| Phase 2 | M5·M6 (대시보드, 게이트·보고), IF-03·04 | 4주 | 통합테스트 진입 게이트 자동 판정 1회 운영 |

**의사결정 지연 비용**: 케이스 사후 작성은 단위테스트 단계의 결함을 통합테스트로 이월시킨다. 통합테스트에서 발견된 결함은 원인 추적·재배포·회귀 확인이 추가되므로, 표준 확정이 개발 착수보다 늦어지는 주(週)만큼 이월 결함이 누적된다고 보고 Phase 0를 개발 착수 2주 전까지 완료한다.

**즉시 실행 Step**

- [ ] WBS Leaf 레벨과 WBS ID 체계 동결 (PMO, 이번 주)
- [ ] 5장 케이스 양식·7장 임계값을 PMO 표준안으로 PL 회의 상정 및 확정
- [ ] 'WBS 개발완료 = UT 4개 조건 충족' 기준을 PM 명의로 공지 (협력사 계약상 산출물 기준과 정합성 확인 포함)
- [ ] 파일럿 모듈 1개 선정, 엑셀 양식으로 2주 시범 운영
- [ ] 프로젝트관리 플랫폼 설계안에 단위테스트 모듈(M1–M7) 반영 범위 확정
- [ ] 첫 번째 참고자료(네이버 블로그) 본문 확보 후 양식 항목 보완
