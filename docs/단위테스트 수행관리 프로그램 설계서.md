## 1. 개요

모든 단위테스트 케이스·수행·결함을 WBS ID(Leaf 태스크)에 종속시켜 단위테스트 계획·수행·승인·결함 이력을 관리하는 수행관리 프로그램이다. WBS 태스크는 개발 → 단위테스트 → 통합테스트 단계로 보고, 개발완료·UT완료를 이정표로 기록한다(2.1). 1단계는 모든 판정·반영을 사람이 직접 입력하는 수기 관리로 운영한다.

**목적**

- 개발 진척 보고에 테스트 증적을 근거 자료로 제공 (WBS 진척 값은 담당자 직접 입력 유지)
- WBS ID 기준으로 테스트 누락·지연·결함 집중 구간을 즉시 식별
- 통합테스트 진입 품질게이트를 정량 기준으로 운영

**범위**: 단위테스트 계획 → 케이스 작성 → 검토·승인 → 수행·증적 → 결함·재테스트 → 개발완료·UT완료 기록 → 진척·품질 보고. 통합/인수테스트는 확장 대상으로 데이터 구조만 열어둔다.

**참고자료 반영 사항**

| 참고 내용 | 설계 반영 |
| --- | --- |
| 기능을 작게 잘라 케이스 작성 (회원가입 → 입력·조건·결과·예외로 분리) | WBS Leaf 1개 = 기능 단위, 케이스 = 검증 규칙 1개 (단위테스트 단계에는 시나리오를 두지 않음, 2026-10-21) |
| 조건 · 행동 · 예상결과 3요소 | 케이스 필수 필드: 사전조건, 수행절차, 예상결과 |
| 정상만 쓰지 말고 실패 케이스를 반드시 붙일 것 | PL 검토 시 정상·실패 흐름 포함 여부를 내용으로 확인(유형 구분은 2026-10-21 삭제) |
| 예상결과는 한 문장으로 짧고 확인 가능하게 | 예상결과 200자 제한, '정상 처리' 류 모호어 여부를 PL 검토 체크리스트로 확인 |
| 테스트 항목을 WBS 일정표와 연결 | 케이스·수행·결함 모두 WBS ID 필수, 예정일은 WBS 계획일을 참고해 수기 입력 |
| 상태값은 작성 / 확인중 / 통과 / 수정 필요 정도로 단순하게 | 케이스 상태 7단계로 표준화 (6장) |
| 항목이 많으면 결제·가입·권한·저장 등 영향 큰 흐름부터 | 케이스 우선순위(H/M/L)는 2026-10-21 삭제 — H등급 기준 게이트·샘플링·현업 확인 조건은 보류 |

> 첫 번째 참고 사이트(네이버 블로그)는 접근이 차단되어 반영하지 못했다. 본문을 받으면 양식 항목을 보완한다.

**설계 원칙**

1. 모든 데이터는 project\_id로 격리한다. 사용자는 배정된 프로젝트의 데이터만 조회·처리한다.
2. WBS ID 없는 테스트 데이터는 존재할 수 없다 (FK 필수, Leaf 레벨만 허용).
3. WBS 진척은 담당자가 기존 WBS 화면·엑셀로 직접 입력한다. UT 모듈은 WBS 진척을 바꾸지 않으며, UT 결과·이정표 기록을 진척 근거 자료로 제공한다(자동 반영은 11장 후보).
4. 테스트 결과는 QC 확인 → PL 확인 2단계 승인을 거쳐야 UT완료 근거로 인정한다. 수행자, QC 확인자, PL 확인자는 서로 다른 사람이어야 한다.
5. Pass 판정 후 결과 수정 불가. 재수행은 신규 차수로만 기록한다.
6. 증적 없는 Pass는 Pass가 아니다.

## 2. 통제 관점 (PMO)

WBS 태스크의 **UT완료**는 PL이 아래 4개 조건을 확인한 뒤 수기로 기록한다(2.1). 시스템은 조건별 현황을 조회로 보여 줄 뿐 판정하거나 WBS 진척을 바꾸지 않는다.

| # | UT완료 확인 조건 | 확인 근거 (조회) |
| --- | --- | --- |
| 1 | 해당 WBS ID의 케이스가 PL 승인 완료 | 승인 상태 케이스 ≥ 1, 예외·경계 비율 충족 |
| 2 | 승인된 케이스 전체 수행 (N/A는 PL 사유 승인 시만 제외) | 수행률 = 100% |
| 3 | 최종 차수 전 케이스 Pass, Open 결함 0건 (Minor는 조치계획 승인 시 허용) | 결함 상태 집계 |
| 4 | Pass 건 전체 증적 첨부 + QC 확인 + PL 확인 완료 | 증적 첨부율 = 100%, approval\_status = 승인완료 100%, 수행자·QC·PL 상이 |

### 2.1 WBS 이정표 — 개발완료·UT완료 수기 기록 (C8, 2026-10-19)

UT 대상 Leaf WBS는 같은 WBS 행 안에서 이정표 2개를 **사람이 직접 기록**한다(WBS 분할 없음). 이정표 기록은 `ut_wbs_milestones`에 저장하며, **WBS 진척률·실적종료일·역할 트랙은 바꾸지 않는다.** WBS 진척은 담당자가 기존 WBS 화면·엑셀로 직접 입력한다.

| 이정표 | 기록 방식 | 참고 근거(조회) |
| --- | --- | --- |
| 개발완료 | 개발자가 개발완료일을 입력(선언) → PL이 확인(승인/반려, 반려 시 사유 필수) | 케이스 승인 현황 |
| UT완료 | PL이 위 4개 조건을 확인한 뒤 UT완료일을 입력 | 4개 조건별 현황(수행률·Pass·Open 결함·증적·승인) 조회 |

- 선언자 ≠ 확인자. 리더가 공석이거나 본인이면 PM/PMO가 확인한다.
- 기록 취소·수정은 PM/PMO만 사유와 함께 할 수 있고 감사로그에 남긴다.
- UT 수행 등록 가능 시점, 이정표와 WBS 진척 연동, 조건 미충족 시 UT완료 입력 차단은 **자동화 후보(11장)** 로 보류한다.

**이해관계자 역할 (RACI)**

| 활동 | 개발자 | QC | PL/모듈리더 | 현업 | PMO | PM |
| --- | --- | --- | --- | --- | --- | --- |
| 케이스 작성 | R | C | A | C | I | I |
| 케이스 검토·승인 | C | C | R/A | C (H등급) | I | I |
| 수행·증적 등록 | R | I | A | – | I | I |
| 테스트 결과 QC 확인 (1차 승인) | I | R/A | I | – | I | – |
| 테스트 결과 PL 확인 (최종 승인) | I | I | R/A | – | I | I |
| 결함 조치·재테스트 | R | C | A | – | I | I |
| 샘플링 감사 | C | C | C | – | R | A |
| 통합테스트 진입 게이트 | I | C | C | C | R | A |

QC는 증적·실제결과·예상결과 일치 여부와 케이스 수행의 적정성(형식적 수행 여부)을 확인하고, PL은 기능 완성도와 WBS 완료 관점에서 최종 승인한다. QC를 PL 앞에 두어, 진척 압박을 받는 PL이 단독으로 Pass를 확정하지 못하게 한다.

**권력 구조상 주의점**

- PL은 진척 압박의 당사자이자 승인자다. 자기 모듈 승인만으로 게이트가 열리지 않도록 PMO 샘플링(케이스 10%, H등급 우선)을 게이트 조건에 포함한다.
- 현업은 예외 케이스의 기준(무엇을 막아야 하는가)을 가진 유일한 주체다. H등급 케이스는 현업 확인(C)을 필수로 둬, 통합·인수테스트 단계의 '요건 해석 차이' 결함을 앞당겨 걸러낸다.
- 다수 협력사가 참여하는 경우 결함 귀속(협력사별 결함 밀도)이 계약 정산·패널티 근거가 되므로, 결함에 담당 협력사 코드를 필수로 기록한다.

**핵심 리스크**

| 리스크 | 유형 | 발생확률(추정) | Trigger | 대응 |
| --- | --- | --- | --- | --- |
| 형식적 Pass (증적 없는 일괄 Pass) | 품질 | 40% | 마감 전 3일 내 Pass 급증 | 증적 필수 + PMO 주간 Pass 추이 점검(수기) + PMO 샘플링 |
| 케이스 사후 작성 (개발 후 끼워맞추기) | 품질 | 50% | 케이스 승인일 > 개발 착수일 | 설계완료 시점 케이스 승인을 원칙으로 공지, PMO가 케이스 승인일과 개발완료일을 대조 점검 |
| WBS 변경 시 테스트 데이터 고아화 | 일정 | 30% | WBS 분할·병합·삭제 | WBS 직접 참조(불변 `id`·`displayId`)로 이동 영향 제거 + 분할·병합·보관 시 PMO 수기 이관(`ut_wbs_migrations`) |
| WBS 진척과 UT 결과 불일치 (진척 자가 신고 지속) | 보고 | 60% | WBS 진척 100% + UT완료 미기록 | PMO 주간 대조표 점검, 불일치 비율을 자동화(11장 AU-01·03) 결정 근거로 사용 |
| 협력사 간 결함 책임 공방 | 계약/정치 | 25% | 인터페이스 결함 반복 | 결함 원인 모듈·협력사 코드 필수, 주간 결함 귀속 리뷰 |

## 3. 기능 구성

7개 모듈로 구성하며, M1(WBS 연계)이 모든 모듈의 기준 키를 공급한다.

| 모듈 | 주요 기능 | 주 사용자 | 우선순위 |
| --- | --- | --- | --- |
| M1 WBS 연계 | pmotools WBS(`wbs_items`) 직접 참조(동기화 없음, 읽기 전용), Leaf 태스크 식별, WBS ↔ 프로그램 매핑(선택), 분할·병합 시 케이스 수기 이관, 개발완료·UT완료 이정표 기록 | PMO | Phase 1 |
| M2 케이스 관리 | 케이스 작성, 엑셀 일괄 업로드·다운로드, 표준 템플릿, 검토요청·승인·반려, 버전 관리 | 개발자, PL | Phase 1 |
| M3 수행 관리 | 담당자·예정일 배정(수기 입력), 결과 판정, 증적 첨부, QC 확인 → PL 확인 2단계 승인, 차수별 재수행 | 개발자, PL | Phase 1 |
| M4 결함 관리 | 결함 등록(Fail 시 수기 등록), 조치·재테스트 수기 연결, 심각도·원인·협력사 분류 | 개발자, PL, QA | Phase 1 |
| M5 진척·품질 대시보드 | WBS 트리별 UT 상태, 모듈·협력사·담당자별 지표, 점검 목록(조회), WBS 진척 대조표 | PM, PMO | Phase 2 |
| M6 품질게이트·보고 | 게이트 체크리스트(PMO 수기 판정), 엑셀 산출물 출력 | PMO, PM | Phase 2 |
| M7 공통 관리 | 프로젝트·사용자·업무그룹·협력사·공통코드·감사로그는 pmotools 기존 기능 사용. 신규는 UT 역할(QC·테스터·현업) 배정과 마감 잠금만 | 관리자 | Phase 1 (역할 배정은 후속) |

**기술 구성 (2026-10-19 확정, C1)**: 별도 시스템을 만들지 않고 **pmotools 모듈로 편입**한다. 기술 스택은 pmotools와 동일하게 Next.js(App Router, API Routes) + TypeScript + Prisma ORM + PostgreSQL로 고정한다.

| 구분 | 구성 | 재사용 대상 |
| --- | --- | --- |
| 화면 | Next.js App Router, 다중 프로젝트(MP) 계열 경로 `/mp-ut/*` | `MpLayout`(대상 프로젝트 선택 상자), `PersonPicker`, `ImportStagingPanel` |
| 서버 | API Routes `app/api/v1/mp/ut/**`, 순수 규칙 `lib/domain/ut.ts`, 트랜잭션 `lib/server/mp/ut*.ts` | `getMpScope`, `writeAuditLog`, `version` 낙관적 잠금 |
| DB | 기존 pmotools PostgreSQL, Prisma 스키마에 모델 추가(추가 전용), 마이그레이션 SQL 수기 작성 | 4장 재사용 표 |
| 증적 파일 | 내부 서버 로컬 디스크 증적 저장소 + SHA-256 해시(9장 증적 저장소) | — (신규, C6) |
| 테스트 | Vitest(순수 함수·서버 로직 모의 객체) | 기존 테스트 패턴 |

M1(WBS 연계)·M7(공통 관리)은 대부분 기존 자산으로 대체되며, 신규 구현 범위는 4장 "신규 테이블"로 한정한다.

## 4. 데이터 모델

> 2026-10-19 재작성(C3): 기존 pmotools 테이블·리소스를 최대한 재사용하고, 신규 테이블은 단위테스트 고유 데이터로 한정한다. 신규 테이블은 모두 `ut_` 접두어를 쓰며, 기존 테이블의 컬럼·제약은 변경하지 않는다(추가 전용). **1단계는 수기 관리 기준이며, UT 데이터가 기존 WBS 데이터(진척률·실적종료일·역할 트랙)를 변경하지 않는다.**

### 4.1 재사용 테이블 (변경 없음)

### 4.3 무결성 규칙

1. 하위 행의 `projectId`·`wbsItemId`는 상위 행 값을 저장 시 복사하며 API 입력으로 받지 않는다. 모든 조회·집계 API는 `projectId`(MP 대상 프로젝트)를 필수 조건으로 받는다.
2. `ut_cases.wbsItemId`는 같은 프로젝트의, 보관되지 않은 **개발 단계(최상위 WBS 이름 "개발") 하위** Leaf WBS 중 **WBS에서 "단위테스트 대상"이 체크된(`wbs_items.isUnitTestTarget = true`)** Task만 허용한다(2026-10-20 단계 규칙, 2026-10-21 체크 규칙 사용자 확정).
   - 대상 여부는 **WBS 항목에만 저장**하며(WBS·WBS2 등록/수정 화면의 체크박스), 단위테스트 관리는 이를 읽기만 한다. 별도 대상 테이블(`ut_wbs_targets`)은 두지 않는다.
   - **WBS 없는 테스트(2026-10-21 사용자 확정, B안):** WBS ID 없이도 케이스를 등록할 수 있다(`wbsItemId` NULL). 케이스 ID는 수기 입력한다. 목록에는 대상 Task 행 뒤에 붙고, 좌측 트리의 "WBS 없음"으로 따로 조회한다. WBS 마일스톤(개발완료·UT완료) 집계에는 포함하지 않는다. 등록 경로: 대상 Task 행의 "+ 케이스 등록"(WBS 고정) 또는 상단 "+ 신규 등록"(WBS 선택 또는 WBS 없음).
   - WBS 변경 시: 신규 Task는 체크 전까지 대상 아님 / 보관·다른 단계 이동·하위 Task 생성 시 자동 제외(체크 값은 유지되어 복원 시 다시 대상) / 수정·엑셀 U 행은 체크 값 유지. 대상에서 빠진 Task에 걸린 케이스는 이관(UT-012) 대상이다.
3. `ut_cases`·`ut_executions`·`ut_approvals`·`ut_defects`의 `wbsItemId`는 직접 수정할 수 없다. PMO의 케이스 이관(`ut_wbs_migrations`) 처리에서만 바뀐다.
4. `ut_approvals`는 같은 수행 차수에 QC 승인 행이 있어야 PL 행을 만들 수 있다. 어느 단계든 반려하면 해당 차수는 종료되고, 재수행은 `roundNo + 1`로 처음부터 다시 승인받는다.
5. 수행자 ≠ QC 확인자 ≠ PL 확인자, 케이스 작성자 ≠ 케이스 승인자(PL), 결함 조치자 ≠ 결함 검증자. 입력 시 검증한다.
6. `ut_executions`·`ut_approvals`·`ut_evidences`·`ut_defect_actions`는 INSERT 전용이다(`ut_executions.approvalStatus` 갱신만 예외). 수기 마이그레이션 SQL에 UPDATE(허용 컬럼 외)·DELETE 차단 트리거를 함께 만든다.
7. WBS가 보관되거나 하위 항목이 생겨 Leaf가 아니게 된 케이스는 "고아" 목록(조회 화면)에 나타나며, PMO가 이관 화면에서 새 WBS로 재매핑한다. WBS 이동은 `id`가 그대로이므로 영향이 없다.
8. `ut_project_settings.lockedAt`이 기록된 프로젝트는 UT 데이터 쓰기를 차단한다. 잠금·해제는 PMO가 수기로 하며 해제는 PM 승인 + 사유 + 감사로그.
9. 프로젝트 삭제 시 증적 이력이 연쇄 삭제되지 않도록, `ut_executions`·`ut_approvals`·`ut_evidences`·`ut_defects`·`ut_defect_actions`의 FK는 `onDelete: Restrict`로 둔다.

### 4.4 PL 지정 (C4, 수기)

- PL은 케이스마다 **사람이 직접 지정**한다(작성자 또는 PM/PMO).
- 지정 화면은 참고 정보로 **작성자의 소속 그룹**(`user_group_map` ∩ 대상 프로젝트의 활성 `WORK_MODULE` 그룹)과 각 그룹의 리더를 보여 준다. 소속 그룹이 여러 개이면 모두 보여 주고, 선택은 사람이 한다.
- 업무그룹(`groupId`)도 케이스마다 직접 선택한다(참고 목록은 위와 같음).
- 리더가 공석이거나 리더가 작성자·수행자 본인이면 PM/PMO가 다른 PL을 지정한다(감사로그).
- 그룹 리더가 바뀌어도 기존 케이스의 PL은 바뀌지 않는다. 필요하면 PM/PMO가 직접 변경한다(감사로그, 이미 PL 승인된 차수는 그대로).

### 4.7 ID 채번

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 케이스 | **작성자 수기 입력**(2026-10-21 사용자 확정) — 프로젝트 안에서 유일(대소문자 무시), 공백 불가, 50자 이내. 시나리오 ID 없음 | `UTC-2026-000123-003`(권장 예시) |

- 순번은 저장 시 `ut_sequences`에서 발급한다(산출물관리 `deliverable_sequences`와 같은 방식). 유일성은 (`projectId`, `displayId`)로 보장한다. 채번은 수기 관리 범위에서도 유지하는 시스템 처리다(11장).

| 단계 | 상태(`ut_defects.status`) | 기록 |
| --- | --- | --- |

## 6. 수행 프로세스와 상태 전이

케이스는 설계 완료 시점에 승인되어야 하며, 수행 결과는 QC 확인 → PL 확인을 모두 통과해야 UT완료 근거로 인정된다. Fail 또는 반려는 신규 차수 재수행으로만 다시 승인 단계에 들어간다.

&#91;embedded content: 단위테스트 케이스 상태 전이 · 7개 상태, 반려·재수행 루프\]

QC 또는 PL이 반려하면 해당 차수는 종료되고, 보완 후 재수행한 신규 차수가 QC 확인부터 다시 거친다. 해당 WBS의 전 케이스가 PL확인완료되면 PL이 UT완료를 기록한다(2.1).

**단계별 절차**

1. **UT 대상 확인 (PMO)**: pmotools WBS 기준선 확정 후 Leaf 태스크를 확인한다. WBS는 동기화 없이 직접 참조하며, 프로그램 매핑은 선택이다.
2. **케이스 작성 (개발자)**: 상세설계 완료 시점에 작성한다. WBS 착수일 이전 승인이 목표이며, 착수일 경과 후 미승인 WBS는 PMO 점검 대상이다(점검 목록 조회).
3. **검토·승인 (PL, H등급은 현업 확인)**: 작성 검토 체크리스트를 확인해 승인 또는 반려. 반려 시 사유 필수.
3-1. **개발완료 기록 (개발자 → PL)**: 개발자가 개발완료일을 입력하고 PL이 확인한다(2.1). WBS 개발 진척은 담당자가 별도로 직접 입력한다.
4. **수행 (개발자)**: DEV 또는 STG 환경에서 수행하고 판정·증적을 등록한다. Pass 등록 즉시 approval\_status = QC대기.
5. **QC 확인 (QC, 1차 승인)**: 증적 존재·식별 가능 여부, 실제결과와 예상결과 일치, 수행절차 준수 여부를 확인한다. 승인 시 PL대기, 반려 시 사유코드와 함께 개발자에게 반송.
6. **PL 확인 (PL, 최종 승인)**: 기능 완성도와 WBS 완료 관점에서 확인한다. 승인 시 승인완료, 반려 시 개발자에게 반송.
7. **결함 조치·검증·재수행**: Fail 시 결함 수기 등록(결함내용) → 조치(조치일·조치자) → 검증(검증결과·검증일자·검증자, 부적합이면 재조치, 5.1) → 조치 완료 → 동일 케이스를 round\_no + 1로 재수행. QC·PL 반려도 보완 후 round\_no + 1로 재수행하며 QC 확인부터 다시 받는다.
8. **UT완료 기록 (PL)**: PL이 2장의 4개 조건 현황을 조회해 확인한 뒤 UT완료일을 기록한다(2.1). WBS 진척률·실적종료일은 담당자가 기존 방식으로 직접 입력한다.

**승인 SLA (권장)**: QC 확인 2영업일, PL 확인 1영업일. 초과 건은 SLA 경과 목록(조회)으로 PMO가 확인한다(알림 자동화는 11장 AU-10).

**상태 정의**

| 대상 | 상태 | 진입 조건 |
| --- | --- | --- |
| 케이스 | 작성중 | 신규 등록 |
| 케이스 | 검토요청 | 필수 필드 + 작성 검증 규칙 충족 |
| 케이스 | 승인 | PL 승인 (반려 시 작성중 복귀) |
| 케이스 | 수행중 | 최초 수행 결과 등록, 또는 Fail·반려 후 재수행 대기 |
| 케이스 | Pass (QC대기) | 최종 차수 판정 Pass + 증적 첨부 |
| 케이스 | QC확인 (PL대기) | QC 승인 |
| 케이스 | PL확인완료 | PL 승인 (UT완료 확인 단위) |
| WBS 단위 UT | 미착수 → 케이스작성 → 수행중 → 결함조치중 → 승인대기 → 완료 | 하위 케이스 상태 집계로 조회 표시(WBS 데이터는 변경하지 않음). 이정표(개발완료·UT완료)는 2.1 수기 기록 |

참고자료의 4단계 상태(작성 / 확인중 / 통과 / 수정 필요)는 각각 작성중 / 검토요청·QC확인 / PL확인완료 / 수행중(Fail·반려)에 대응한다. 감사 대응을 위해 케이스 승인과 결과 확인을 분리하고, 결과 확인을 QC·PL 2단계로 나눴다.

## 7. 진척·품질 지표와 게이트 기준

UT 진척은 'UT완료가 기록된 WBS 수'로 보고하고(WBS 진척률은 담당자 입력값으로 별도), 나머지 지표는 그 원인을 설명하는 선행지표로 쓴다. 지표는 조회 집계이며 판정·경보는 PMO가 수기로 한다. 아래 임계값은 권장 초기값이며 프로젝트 착수 시 PMO 표준으로 확정한다.

| 지표 | 계산식 | Green | Yellow | Red |
| --- | --- | --- | --- | --- |
| UT 진척 SPI | 기준일까지 UT 완료 WBS 수 ÷ 기준일까지 계획 종료 WBS 수 | ≥ 0.95 | 0.85–0.94 | < 0.85 |
| 케이스 적시 승인율 | 착수일 이전 승인된 WBS 수 ÷ 착수한 WBS 수 | ≥ 90% | 70–89% | < 70% |
| 수행률 | 수행 케이스 ÷ 승인 케이스 (WBS 계획 종료일 도래분) | 100% | 90–99% | < 90% |
| 1차 Pass율 | 1차수 Pass ÷ 1차수 수행 | 80–95% | > 95% (형식 수행 의심) | < 70% |
| 최종 Pass율 | 최종 차수 Pass ÷ 수행 케이스 | ≥ 98% | 95–97% | < 95% |
| QC 반려율 | QC 반려 건 ÷ QC 처리 건 | 5–15% | < 5% (형식 확인 의심) | > 25% |
| PL 반려율 | PL 반려 건 ÷ PL 처리 건 | ≤ 5% | 6–10% | > 10% (QC 기준 불일치) |
| 승인 대기 리드타임 | 평균(PL 승인일 − Pass 등록일) | ≤ 3영업일 | 4–5영업일 | > 5영업일 |
| 예외·경계 비율 | (예외 + 경계) ÷ 전체 케이스 | ≥ 60% | 50–59% | < 50% |
| 결함 밀도 | 결함 수 ÷ 케이스 수 | 프로젝트 기준선 ±30% | 기준선 대비 −50% 이하 (누락 의심) | 기준선 대비 +50% 이상 |
| 결함 조치 리드타임 | 평균(조치일 − 발견일), Critical·Major | ≤ 2일 | 3–5일 | > 5일 |
| 증적 첨부율 | 증적 있는 Pass ÷ 전체 Pass | 100% | – | < 100% |

모든 지표는 project\_id 단위로 산출하며, 그룹·본부 보고 시에만 프로젝트 간 비교를 제공한다.

1차 Pass율이 지나치게 높거나, 결함 밀도·QC 반려율이 지나치게 낮은 것도 PMO 점검 대상으로 본다. 단위테스트에서 결함이 안 나온다는 것은 대개 품질이 아니라 테스트 강도의 문제다.

**통합테스트 진입 게이트 (모듈 단위, PMO 수기 판정)**

- [ ] 대상 Leaf WBS의 UT 완료율 ≥ 95%, 미완료 WBS는 PM 승인된 잔여계획 보유
- [ ] H등급 케이스 수행률 100%, 최종 Pass율 100%
- [ ] Open 결함 Critical·Major 0건
- [ ] 증적 첨부율 100%
- [ ] PMO 샘플링 감사(케이스 10%) 부적합률 ≤ 5%
- [ ] 고아 케이스(WBS 미매핑) 0건

게이트 미충족 시 진입을 보류하거나, PM이 미충족 항목·잔여 리스크·완료 예정일을 명시한 조건부 진입을 승인한다. 조건부 진입은 본부장 보고 대상이다.

## 8. 화면 설계

15개 화면으로 구성하며, 상단에 프로젝트 선택기를, 모든 목록 화면의 좌측에 해당 프로젝트의 WBS 트리(단위테스트 대상 Task와 그 상위만)를 고정해 WBS ID 기준 탐색을 기본 동선으로 한다.

**UT-050 대시보드 점검 목록 (조회 조건 — PMO 수기 확인, 경보·알림 자동화는 11장 AU-10)**

- 착수일 경과 + 케이스 미승인 WBS
- 계획 종료일 경과 + UT 미완료 WBS (지연일수 내림차순)
- 3일 내 Pass 급증 WBS (평균 대비 3배 이상)
- Critical·Major 결함 48시간 이상 미조치
- QC 확인 2영업일, PL 확인 1영업일 SLA 초과 건
- 고아 케이스

**감사 통제**

- 판정·상태·WBS 매핑 변경은 전량 AUDIT\_LOG에 기록하고, 내부감사 요청 시 WBS ID 기준으로 추출한다.

- [ ] '개발완료 = PL 확인, UT완료 = UT 4개 조건 충족(PL 확인)' 기준을 PM 명의로 공지 (WBS 진척은 기존 수기 입력 유지, 협력사 계약상 산출물 기준과 정합성 확인 포함)

- [ ] 첫 번째 참고자료(네이버 블로그) 본문 확보 후 양식 항목 보완
