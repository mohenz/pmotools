## 2. 기존 자산 조사 결과

| 자산 | 현황 | 설계 반영 |
|------|------|-----------|
| 산출물 관리 기능 | 없음. `WbsDeliverable`(WBS 항목당 1건, 검수자 1명)과 업무일지의 `deliverableName`만 있음 | 신규 모듈. 기존 두 구조는 변경하지 않음 |
| 프로젝트 (`Project`) | `code`, 계층(`parentId`) 보유 | 프로젝트코드 = `projectId` 참조(코드는 조인으로 표시) |
| 업무그룹 (`Groups`, `WORK_MODULE`) | 프로젝트별 그룹, **리더 1명(`leaderId`)**, 사용자 소속(`UserGroupMap`) | 업무그룹코드 = `groupId` 참조. 1차 검수자 자동 지정에 `leaderId` 사용 |
| 사용자 기본 업무그룹 | 업무일지 `getWorkLogIdentity()`가 로그인 사용자의 소속 그룹을 조회 | 동일 방식으로 등록 화면 기본값 설정 |

| 사용자 검색 (`PersonPicker`) | 이름·아이디 검색, 다중 선택 | 검수자 선택용 단일 선택 래퍼로 재사용 (`allowGuests=false`) |
| 다중 프로젝트 틀 (`MpLayout`, `getMpScope`) | 대상 프로젝트 선택, 최상위 프로젝트 쓰기 차단 | 요구사항 2(프로젝트 변경 가능) 충족 |
| 엑셀 업로드 스테이징 (`ImportBatch`, `lib/server/mp/import-staging.ts`) | 종류별 엔진(`ENGINES`)에 검증·반영 함수만 꽂는 구조 | 엔진 1개 추가로 요구사항 14 충족 |
| 표시 ID 발번 | 회의록은 프로젝트 내 유일(`MM-0001`), 나머지 7종은 전역 순번 구간 | 회의록 방식 채택 — 전역 순번 7종(`numbering.ts`)·백오피스 코드 무수정 |
| 감사로그·낙관적 잠금 | 전 모듈 공통 (`writeAuditLog`, `version`) | 동일 적용 |

## 3. 데이터 설계

### 3.1 설계 원칙
1. **추가만 한다.** 기존 테이블의 컬럼·제약은 변경하지 않는다.
2. **검수자는 차수별 행으로 정규화한다.** 요구사항 표의 `1차~3차 검수자/결과` 컬럼을 그대로 두면 5차 확장(요구사항 9) 때 스키마 변경이 필요하다. `deliverable_reviewers` 1행 = 1차수로 두고, 목록·엑셀에서는 1~5차 컬럼으로 펼쳐 보여 준다.
3. **이력은 스냅샷이다.** 검수이력에는 문서번호·산출물명·검수자명을 기록 시점 값으로 보존한다(이후 산출물이 수정돼도 이력은 그대로).
4. **최종검수결과는 저장한다.** 차수 결과로 계산 가능하지만 목록 필터·통계 성능을 위해 같은 트랜잭션에서 갱신해 저장한다.

### 3.3 Prisma 모델 (안)

```prisma

  projectId String @id

}

model Deliverable {
  id                  String                   @id @default(uuid())

  finalResult         DeliverableReviewResult  @default(PENDING)
  finalizedAt         DateTime? // 최종 적격/부적격 확정 시각

  updatedBy           String?

  updatedAt           DateTime                 @updatedAt

  round         Int // 1~5

  WBS
  REQUIREMENT
```

- `Project`, `Groups`, `User`, `CommonCode`에는 Prisma 역관계 필드만 추가된다(DB 컬럼 변경 없음).
- **번호 발급 동시성:** 산출물 번호는 회의록과 같은 방식으로 `tx.deliverableSequence.upsert({ where: { projectId }, create: { projectId, value: 1 }, update: { value: { increment: 1 } } })`로 발급한다. 첫 행 생성 경합과 동시 증가를 DB가 원자적으로 처리한다. 이력번호(`historyNo`)는 검수 처리 트랜잭션 안에서 산출물 행을 먼저 잠근 뒤(`version` 조건부 갱신) `max(historyNo)+1`로 발급하고, 경합이 생기면 `@@unique([deliverableId, historyNo])` 위반으로 실패하므로 재시도 안내를 표시한다 (10장 P4).
- 첨부파일 원본은 저장하지 않는다. 문서 실물은 SharePoint에 두고 링크만 관리한다(요구사항 6).

### 3.4 공통코드

| 그룹 코드 | 이름 | 코드 (안) | 비고 |
|-----------|------|-----------|------|
| `deliverable_stage` (신규) | 산출물 단계 | `UNCLASSIFIED` 미분류(기본, 시스템), `ANALYSIS` 분석, `DESIGN` 설계, `BUILD` 구현, `TEST` 테스트, `TRANSITION` 이행 | 프로젝트별 시딩. "미분류"는 비활성화·삭제·코드 변경 불가 — 공통코드 서버 로직(`lib/server/common-codes.ts`)에 `deliverable_stage`/`UNCLASSIFIED` 차단 검사 추가(10장 P1). 나머지는 공통코드 설정 화면에서 조정 |
| `deliverable_extension` (기존) | 산출물 확장자 | PPTX, XLSX, DOCX, PDF, MD, TXT | HWP·XLSM·VSDX·ZIP 등은 공통코드 설정에서 추가(9장 결정 #6) |

**파일타입 자동 선택 (요구사항 5):** 파일명 입력 시 마지막 `.` 뒤 확장자를 대문자로 바꿔 `deliverable_extension` 코드와 비교한다. 일치하면 자동 선택하고, 일치하는 코드가 없으면 빈칸으로 두고 "등록되지 않은 확장자" 안내를 표시한다(사용자가 직접 선택할 수 있음). 엑셀 업로드에서도 같은 함수를 쓴다(`lib/domain/deliverables.ts`의 순수 함수, 단위 테스트 대상).

## 4. 검수 흐름 설계

### 4.1 검수결과 상태 전이 (차수 단위)

```
            검수요청(작성자)            검수 시작(해당 차수 검수자)
  대기 ─────────────────▶ 요청 ─────────────────────────▶ 진행
 (PENDING)    또는 이전 차수 적격   (REQUESTED)                    (IN_REVIEW)
                                                                    │
                          ┌─────────────────┬───────────────────────┤ 검수 완료(의견 입력)
                          ▼                 ▼                       ▼
                       적격(PASSED)   보완요청(REVISION_REQUESTED)  부적격(FAILED)
                          │                 │                       │
             다음 차수 → 요청      작성자 보완 후 재요청        검수 종료
             마지막 차수 → 최종 적격   → 같은 차수 다시 요청      → 최종 부적격
```

### 4.2 업무 규칙

| # | 규칙 | 근거 |
|---|------|------|
| R1 | 등록 시 검수자 입력란은 1~3차를 기본으로 보여 주고, "차수 추가"로 5차까지 늘린다. 저장된 차수는 1차부터 빈칸 없이 연속이어야 한다 | 요구 9 |
| R2 | 1차 검수자는 선택한 업무그룹의 리더로 자동 지정한다(`isAutoAssigned=true`). 작성자 = 리더이면 빈칸으로 둔다. 업무그룹을 바꾸면 1차가 자동 지정 상태이고 아직 `대기`일 때만 새 리더로 다시 지정한다. 새 리더가 이미 다른 차수의 검수자이면 자동 지정하지 않고 "검수자 중복" 안내를 표시한다. 이때 사용자가 검수자를 직접 변경해 해소한다 | 요구 7, 10장 S3 |
| R3 | 검수자는 사용자 검색으로 지정한다. 대상 프로젝트의 활성 멤버만 검색되며, 작성자 본인은 지정할 수 없다 | 요구 8 |
| R4 | **검수요청**(작성자): 검수자 1명 이상 + 작성현황 `작성완료`일 때 가능. 1차를 `요청`, `reviewRequestedAt` 기록, 최종결과 `요청`. 첫 검수요청이면 `submittedAt`(실제 제출일)도 기록한다 | 요구 1, 10장 P2 |
| R5 | **검수 시작**(해당 차수 검수자): `요청` → `진행`. 검수 화면은 이전 차수가 전부 `적격`이고 자기 차수가 `요청`/`진행`일 때만 열린다 | 요구 12 |
| R6 | **검수 완료**(해당 차수 검수자): `적격`/`보완요청`/`부적격` 중 선택. 보완요청·부적격은 의견 필수. **완료 시 이력 1건을 기록하며, 문서링크·파일명·문서버전을 함께 스냅샷으로 저장한다** | 요구 10, 13, 10장 A1 |
| R7 | 적격이면 다음 차수를 자동으로 `요청`으로 바꾼다. 마지막 차수가 적격이면 최종 `적격`, `finalizedAt` 기록 | 요구 11 |
| R8 | 보완요청이면 `revisionRequired=true`. 작성자가 수정 후 재요청하면 **같은 차수**를 다시 `요청`으로 바꾼다(앞 차수의 적격은 유지) | 9장 결정 #3 |
| R9 | 부적격이면 검수를 종료한다(최종 `부적격`). 작성자는 "재검수 요청"으로 전 차수를 `대기`로 되돌린 뒤 1차부터 다시 요청할 수 있다. 이전 이력은 그대로 남는다 | 9장 결정 #3 |
| R10 | 검수자는 다음 차수가 시작되기 전까지 자기 결과를 정정할 수 있다. 정정하면 새 이력을 남기고 이전 이력은 `정정됨`으로 표시한다. **이미 `요청`으로 열린 다음 차수 이후는 모두 `대기`로 되돌리고 `finalResult`를 다시 계산한다.** 정정 결과가 다시 `적격`이면 R7에 따라 다음 차수를 다시 `요청`으로 연다 | 요구 13, 9장 결정 #4, 10장 S1 |
| R10-1 | **최종결과가 확정된 뒤(`finalizedAt` 기록 후)에는 검수자가 정정할 수 없다.** 정정이 필요하면 PM/PMO가 사유를 입력하고 **확정 해제**한다. 확정 해제는 `finalizedAt`을 비우고 마지막으로 판정한 차수(최종 적격이면 마지막 차수, 부적격이면 부적격 차수)를 `진행`으로 되돌린다. 해당 차수의 기존 이력은 `정정됨`으로 표시하고, 해제 사유·처리자를 감사로그와 이력 비고에 남긴다. 이후 검수자가 다시 판정하면 R6~R9를 그대로 따른다 | 10장 S2→P3 |
| R11 | 차수 추가·삭제는 `대기`/`요청` 차수만 가능하다. **검수자 변경은 `대기`/`요청`/`진행` 차수에서 가능하다**(중복 해소, 검수자 프로젝트 이탈 대응). `진행` 차수의 검수자를 바꾸면 그 차수를 `요청`으로 되돌린다. 결과가 확정된 차수(`적격`/`보완요청`/`부적격`)는 잠근다. 변경 내역은 감사로그에 기록한다 | 정합성, 10장 S3·S4 |
| R12 | 검수요청 이후에는 산출물 기본정보(산출물명·문서번호·파일·링크)를 잠근다. 보완요청 상태이거나 PM/PMO일 때만 수정할 수 있다. PM/PMO가 수정해도 검수는 초기화하지 않으며, 변경 전후 값을 감사로그에 남긴다 | 검수 대상 고정, 10장 A2 |

### 4.3 최종검수결과 계산 (요구 11)

| 조건 (위에서부터 우선) | 최종검수결과 |
|------------------------|--------------|
| 어느 차수든 `부적격` | 부적격 |
| 지정된 차수 전부 `적격` | **적격** |
| 어느 차수든 `보완요청` | 보완요청 |
| 어느 차수든 `진행` | 진행 |
| 어느 차수든 `요청` | 요청 |
| 그 외(미요청) | 대기 |

계산 함수 `computeFinalResult(rounds)`는 `lib/domain/deliverables.ts`에 순수 함수로 두고, 차수 결과가 바뀌는 모든 트랜잭션에서 호출해 `finalResult`를 저장한다.

### 4.4 권한

| 행위 | 권한 |
|------|------|
| 조회 | 대상 프로젝트 멤버 전원 |
| 등록 | 대상 프로젝트 멤버 전원 (최상위 프로젝트에서는 불가 — MP 공통 규칙) |

| 보관(삭제) | 작성자(검수요청 전만), PM/PMO |

- 모든 수정은 `version` 낙관적 잠금으로 동시 수정 충돌을 막는다.

## 6. 엑셀 대량 등록·수정 (요구 14)

### 6.1 양식 (시트명 `산출물`)

| 열 | 헤더 | 입력 | 규칙 |
|----|------|------|------|
| A | 번호 | 선택 | 빈칸 = 신규 등록, `DLV-0001` = 해당 건 수정 |
| B | 프로젝트코드 | 필수 | 화면에서 선택한 대상 프로젝트 코드와 같아야 함 |
| C | 업무그룹코드 | 필수 | 활성 `WORK_MODULE` 그룹 코드 |
| D | 단계 | 선택 | 단계 코드 이름, 빈칸 = 미분류 |
| E | 문서번호 | 선택 | 중복 허용 |
| F | 산출물명 | 필수 | |
| G | 필수구분 | 필수 | 필수 / 선택 |
| H | 작성자ID | 선택 | 로그인 ID, 빈칸 = 업로드한 사람 |
| I | 작성현황 | 선택 | 미작성 / 작성중 / 작성완료 |
| J | 파일명 | 선택 | 파일타입 자동 판별 |
| K | 문서링크 | 선택 | https URL |
| L | 계획제출일 | 선택 | YYYY-MM-DD (10장 P2) |
| M~Q | 1차~5차 검수자ID | 선택 | 로그인 ID. 1차 빈칸이면 업무그룹 리더 자동(R2). 연속성·중복·작성자 제외 검증 |
| R~ | 파일타입, 실제제출일, 1~5차 검수결과, 최종검수결과, 등록일, 수정일 | 읽기 전용 | 내보내기에만 채움, 업로드 시 무시 |

### 6.2 반영 규칙
- 엑셀로는 **기본정보와 `대기` 상태 차수의 검수자만** 바꿀 수 있다. 검수결과·검수요청은 엑셀로 바꿀 수 없다(검수 증적 보호).
- 검수가 진행 중인 건(R12 잠금 대상)의 기본정보를 바꾸는 행은 오류로 처리한다.
- 엑셀로는 삭제하지 않는다(보관은 화면에서 1건씩).
- 빈칸 처리는 WBS 업로드와 같은 방식이다. 업로드 시 검증해 필수값 누락·형식 오류는 오류 행으로 표시하고, 스테이징 화면에서 사용자가 직접 정정한 뒤 반영한다. 선택 항목의 빈칸은 6.1의 기본값을 미리 채워 보여 주고, 사용자가 정정할 수 있다 (10장 S5)
- 오류 행이 하나라도 있으면 반영하지 않는다(기존 스테이징 규칙 `canApplyStaging`과 같음). 반영은 한 트랜잭션으로 처리한다.

## 8. 운영 리스크

| 리스크 | 내용 | 대응 |
|--------|------|------|
| DB 마이그레이션 | 신규 테이블 4개 + enum 값 1개 추가 | 추가만 하므로 기존 데이터 영향 없음. 롤백은 신규 테이블 DROP. enum 값 추가(`ALTER TYPE … ADD VALUE`)는 되돌리기 어렵지만 미사용 값으로 남아도 무해. 적용 전 승인 필수 |
| 마이그레이션 작성 방식 | `prisma migrate diff`가 백오피스 전용 테이블(`main_menus`/`sub_menus`) DROP을 끼워 넣음 | **SQL을 수기로 작성**한다(번호시작점 마이그레이션과 같은 방식) |
| 백오피스 스키마 불일치 | 같은 DB를 쓰는 백오피스(`pmotools_admin`)의 schema에는 신규 테이블이 없음. 백오피스에서 diff로 마이그레이션을 만들면 신규 테이블 DROP이 끼어들 수 있음 | 백오피스 스키마는 변경하지 않고, **백오피스 마이그레이션도 수기 작성 원칙을 유지**한다(10장 P4). 잔여 리스크: 백오피스에서 `prisma migrate diff`/`db push`를 실행하면 산출물 테이블 DROP이 생성될 수 있음 → 백오피스 작업 시 생성 SQL에 `deliverable` 테이블 DROP이 없는지 반드시 확인 |
| 배포 경로 | 배포 hook은 마이그레이션을 실행하지 않음. 현재 사내 Gitea fetch 장애(2026-10-13 확인, 서버 측 upload-pack 응답 비정상) | 서버 DB에 마이그레이션을 수동 적용하는 절차를 배포 계획에 포함. Gitea 복구가 배포의 선행 조건 |
| 검수 증적 무결성 | 결과 정정·엑셀 수정으로 증적이 훼손될 수 있음 | 이력은 추가만(정정 시 이전 이력 `정정됨` 표시), 엑셀로 검수결과 변경 불가, 감사로그 기록 |
| 업무그룹 리더 공석 | `leaderId`가 비어 있는 그룹 | 1차 자동 지정 생략, 등록 화면에 "리더 미지정" 안내 |
