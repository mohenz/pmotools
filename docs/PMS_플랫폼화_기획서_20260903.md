# PMOTOOLS 플랫폼화 기획서

작성일: 2026-09-03
버전: v0.1 (초안 — 목표 아키텍처 + 단계별 로드맵)

## 1. 배경 및 목적

현재 PMOTOOLS는 사실상 **단일 프로젝트 전용 도구**로 운영되고 있다. 데이터 모델(`Project`, `ProjectMember`)은 한 사용자가 여러 프로젝트에 속할 수 있는 다대다(N:M) 구조를 이미 갖추고 있지만, 실제 로그인·화면 로직은 `DEFAULT_PROJECT_ID` 상수 하나에 하드코딩되어 있어 이 구조를 전혀 활용하지 못하고 있다.

이번 플랫폼화의 목적은 PMOTOOLS를 **여러 프로젝트(및 프로젝트 그룹)를 동시에 운영할 수 있는 플랫폼**으로 전환하는 것이다. 요구사항 원문 기준 핵심 목표는 다음과 같다.

- 1개 이상의 프로젝트를 동시에 운영
- 슈퍼관리자가 프로젝트를 생성하고 PM/PMO를 지정
- 프로젝트 PM이 자신의 프로젝트 정보를 관리하고, 사용할 기능(기본/추가)을 선택
- 사용자는 가입 시 프로젝트를 검색해서 가입 신청
- 슈퍼관리자가 상위-하위 프로젝트를 지정하는 2단계 계층 구조
- 하위 프로젝트는 개별적으로 WBS·요구사항관리를 하면서, 상위 프로젝트에서는 하위 전체를 모은 **통합 현황(집계/롤업 보고)**도 볼 수 있음
- 로그인 시 프로젝트를 선택하고, "기억하기"로 다음 로그인부터 자동 선택

## 2. 현재 상태 진단 (코드 기준)

| 영역 | 현재 상태 | 시사점 |
|---|---|---|
| `User` | 전역 계정 1개, 전역 `role`(SUPER_ADMIN/ADMIN/OPERATOR/MEMBER) 보유. 프로젝트에 종속되지 않음 | 계정 자체는 이미 여러 프로젝트에 걸쳐 재사용 가능한 구조 |
| `ProjectMember` | `(projectId, userId)` 유니크, **프로젝트별 role**을 별도로 가짐 | 한 사용자가 프로젝트마다 다른 역할(관리자/운영자/일반)을 가지는 구조가 **이미 존재** — 활용만 안 되고 있음 |
| `Project` | 단일 평면 엔티티. 상하위 관계·기능 On/Off 필드 없음 | 계층·기능선택은 신규 스키마 확장 필요 |
| 로그인 (`lib/server/auth.ts`) | `authorize()`가 항상 `DEFAULT_PROJECT_ID`로만 멤버십을 조회. 세션의 `projectId`도 항상 이 값 고정 | **가장 큰 변경 지점.** 실제 멤버십 기반 로그인으로 전면 재작성 필요 |
| 회원가입 (`app/signup`, `/api/auth/signup`) | `User`만 생성, 프로젝트 연결 없음 → 가입 후 관리자가 수작업으로 `ProjectMember` 추가해야 로그인 가능 | 가입 흐름에 "프로젝트 검색·선택" 단계 자체가 없음 |
| PM/PMO | `jobTitle`(자유 텍스트)이 `"PM"`/`"PMO"`인지로 판별(`lib/domain/job-access.ts`)하는 **설명적 속성**이지 프로젝트별 권한이 아님 | PM 지정은 "그 프로젝트의 `ProjectMember.role`을 관리자급으로 부여"로 구현하는 것이 기존 구조와 가장 잘 맞음 |
| 요구사항관리·WBS·이슈관리 등 | 이미 모든 도메인 함수(`lib/server/*.ts`)가 `projectId`를 명시적으로 받아 Prisma 쿼리를 필터링 | **재사용 가능한 자산.** 멀티 프로젝트 자체를 위한 데이터 격리는 이미 되어 있음 — 문제는 "어떤 projectId를 쓸지 결정하는 상위 로직"이 없다는 것 |
| 공통코드 설정 화면 | `app/settings/common-codes` → `screens/CommonCodeSettingsScreen.tsx` → API route → `lib/server/common-codes.ts` → Prisma | 신규 관리 화면들이 그대로 따라야 할 **표준 스택 패턴** |

**결론:** 데이터 격리·권한 체크의 하부 배관(plumbing)은 이미 갖춰져 있다. 이번 작업의 본질은 (1) 로그인/세션이 "프로젝트 하나 고정"을 벗어나게 하는 것, (2) 그 위에 슈퍼관리자·PM 전용 관리 화면들을 새로 얹는 것이다.

## 3. 목표 아키텍처

### 3.1 데이터 모델 확장

```
Project
  + parentProjectId  String?  (자기참조, 상위 프로젝트)
  + 검증: parentProjectId가 있는 프로젝트는 다시 자식을 가질 수 없음 (2단계 강제, 앱 레이어에서 검증)

ProjectFeature (신규 테이블)
  projectId   String
  featureKey  String   (예: "wbs", "requirements", "meetrooms", "pmo_daily", ...)
  enabled     Boolean  @default(true)
  @@unique([projectId, featureKey])

ProjectMember.role (기존 필드 재해석, 신규 컬럼 없음)
  ADMIN     → 그 프로젝트의 PM (프로젝트 정보 수정, 기능 선택, 가입 승인 권한)
  OPERATOR  → 그 프로젝트의 PMO (관리 보조 권한, 기존 "운영자"와 동일 위계 재사용)
  MEMBER    → 일반 참여자
  isActive  → 가입 승인 대기(false) / 승인 완료(true) 상태로 재사용

User
  + lastProjectId  String?  (마지막으로 로그인한 프로젝트 — "기억하기" 서버측 저장)
```

- `jobTitle`(PM/PMO 자유 텍스트)은 그대로 유지하되, 프로젝트 생성 시 슈퍼관리자가 "PM/PMO 지정"하는 행위는 **해당 사용자의 `ProjectMember.role`을 ADMIN/OPERATOR로 설정**하는 것으로 구현한다. `jobTitle`은 설명용, `ProjectMember.role`이 실질 권한이라는 기존 원칙을 유지.
- `ProjectFeature`를 별도 테이블로 둔 이유: 공통코드 테이블(`CommonCodeGroup`/`CommonCode`)과 동일한 "정규화된 설정 테이블" 패턴을 따라 감사·확장(기능별 세부옵션 추가 등)이 쉽도록 함. 켜지지 않은 `featureKey`는 "기본 OFF"로 취급.
- **기본기능 vs 추가기능**: 코드 레벨의 `FEATURE_CATALOG` 상수로 각 `featureKey`에 `tier: "base" | "addon"`을 부여. base는 모든 프로젝트에 항상 `enabled=true`로 강제(토글 UI 비활성)하고, addon만 PM이 켜고 끌 수 있게 한다. (기본기능 후보: 요구사항관리, WBS, 캘린더/회의실, 공지사항 / 추가기능 후보: PMO Daily, 이슈관리, 업무일지, 위클리리포트, 주간실적, 인력변동 — 실제 분류는 3.6절에서 확정 필요)

### 3.2 권한 모델

| 레벨 | 역할 | 권한 범위 |
|---|---|---|
| 플랫폼 | `SUPER_ADMIN` (User.role) | 모든 프로젝트 생성/조회, PM·PMO 지정, 상하위 프로젝트 지정, 모든 프로젝트 데이터 접근 |
| 프로젝트 | `ProjectMember.role = ADMIN` (PM) | 자기 프로젝트 정보 수정, 기능 On/Off, 가입 승인/반려, 프로젝트 멤버 관리 |
| 프로젝트 | `ProjectMember.role = OPERATOR` (PMO) | PM 보조 — 기존 매니저 권한(`isManagerRole`)과 동일 위계 |
| 프로젝트 | `ProjectMember.role = MEMBER` | 일반 참여자, 승인된 기능 내에서 활동 |

기존 `assertManager`/`assertAdmin`/`isManagerRole`(lib/server/permissions.ts) 등은 모두 "현재 세션의 projectId 컨텍스트 안에서" 이미 이렇게 동작하고 있으므로 **그대로 재사용**한다. 신규로 필요한 것은 "플랫폼 레벨(SUPER_ADMIN, 프로젝트 컨텍스트 없이)" 게이트 하나뿐이다 (`requireSuperAdminContext`는 이미 존재 — 그대로 활용).

### 3.3 로그인 흐름 재설계

1. `authorize()`가 더 이상 `DEFAULT_PROJECT_ID`를 쓰지 않는다. 대신:
   - ID/비밀번호 검증 후, 해당 유저의 `isActive=true` `ProjectMember` 목록을 조회
   - **0개**: 로그인 거부("소속된 프로젝트가 없습니다. 가입 승인을 기다려 주세요.")
   - **1개**: 자동으로 그 프로젝트로 로그인 (선택 UI 노출 안 함)
   - **2개 이상**: 클라이언트가 프로젝트를 지정하지 않고 요청했다면 "PROJECT_REQUIRED" 오류를 반환 → 로그인 화면이 프로젝트 선택 UI를 노출 → 사용자가 고르면 `projectId`를 포함해 재요청
2. 로그인 화면: "프로젝트 저장(기억하기)" 체크 시 `User.lastProjectId`를 서버에 저장. 다음 로그인 때 후보가 2개 이상이면 `lastProjectId`를 기본 선택값으로 미리 채워준다(기기가 바뀌어도 유지되도록 로컬스토리지가 아닌 서버 저장을 권장).
3. 세션(JWT)의 `projectId`는 이렇게 확정된 프로젝트로 채워지며, 이후 로직(요구사항관리·WBS 등 모든 화면)은 **한 줄도 바꿀 필요 없이 지금처럼 `session.user.projectId`를 그대로 쓴다.**
4. (로드맵 3단계) 로그인 이후에도 프로젝트를 바꿀 수 있는 "프로젝트 전환" UI를 상단 메뉴에 추가 — 여러 프로젝트 소속 사용자를 위한 자연스러운 보완 기능.

### 3.4 회원가입 흐름 재설계

1. 가입 폼에 "프로젝트 검색" 입력을 추가 (프로젝트명/코드로 검색 → 자동완성 목록, 공개된 프로젝트만 노출).
2. 가입 제출 시 `User` 생성과 함께 해당 프로젝트에 `ProjectMember(role=MEMBER, isActive=false)`를 함께 생성 — **가입 승인 대기 상태**로 시작.
3. 프로젝트 PM/PMO에게 "가입 승인 관리" 화면(신규)에서 대기 목록을 보여주고 승인/반려 처리. 승인 시 `isActive=true`로 전환, 이 시점부터 로그인 가능.
   - 기존 "정기예약 승인"(`/settings/recurring-meetings`) 화면과 동일한 UX 패턴(대기 목록 → 승인/반려 버튼)을 재사용.
4. 한 사용자가 여러 프로젝트에 가입 신청하는 것은 제한하지 않는다(멀티 소속을 지원하는 것이 이번 플랫폼화의 취지이므로).

### 3.5 슈퍼관리자: 프로젝트 생성/관리 (신규 화면)

- 경로 제안: `/platform/projects` (슈퍼관리자 전용, 기존 `/settings/*`와 구분되는 플랫폼 레벨 네임스페이스)
- 프로젝트 생성 마법사:
  1. 기본정보 입력(기존 `Project` 필드: 코드/이름/고객사/벤더/오픈방식/일정 등 — 지금의 "프로젝트정보 설정" 폼과 동일 필드 재사용)
  2. PM 지정: 사용자 검색(이름/아이디) → 선택 → `ProjectMember(role=ADMIN)` 생성
  3. PMO 지정(복수 가능): 사용자 검색 → 선택 → `ProjectMember(role=OPERATOR)` 생성
  4. 상위 프로젝트 지정(선택): 기존 프로젝트 중 상위 프로젝트가 없는 것만 후보로 노출 → `parentProjectId` 설정
- 전체 프로젝트 목록 화면: 계층 구조(상위 프로젝트 아래 하위 목록 들여쓰기)로 표시, 프로젝트별 상태(멤버 수, 활성 기능 수) 요약.

### 3.6 프로젝트 PM: 정보 수정 및 기능 선택 (신규 화면)

- 기존 `/project-settings` 화면(PM/관리자 전용, 이미 존재)에 **"기능 선택" 탭**을 추가.
- `FEATURE_CATALOG`를 순회하며 각 항목을 토글 스위치로 표시. `tier: "base"`는 항상 켜진 상태로 비활성 표시(끌 수 없음), `tier: "addon"`만 실제 토글 가능.
- 기능을 끄면 해당 모듈은 `AppNavigation.tsx`의 메뉴 목록에서 제외되고, 관련 API 라우트도 `assertFeatureEnabled(projectId, key)` 가드로 차단(URL 직접 접근 방어).
- **확정 필요 사항**: 기본기능/추가기능 분류 기준(3.1절 후보안)은 실제 구현 착수 전 사용자 확인 필요.

### 3.7 상하위 프로젝트 및 통합 현황 (집계/롤업 보고)

- 슈퍼관리자만 `parentProjectId`를 지정/해제할 수 있다 (3.5절 화면에서 처리).
- 하위 프로젝트는 지금처럼 자신의 WBS·요구사항을 완전히 독립적으로 CRUD한다 — **데이터 소유권은 항상 개별 프로젝트에 남는다.**
- 상위 프로젝트 컨텍스트에서 신규 "통합 현황" 화면 진입 시:
  - 자기 자신 + 모든 하위 프로젝트의 WBS/요구사항 데이터를 프로젝트별로 묶어 집계
  - 기존 `RequirementStatisticsScreen`/`WBS 통계` 화면 패턴을 확장해 "프로젝트별 breakdown" 축을 추가(현재도 `요구사항분류×수용여부`, `업무 대분류별 분포` 같은 다차원 집계를 이미 하고 있어 동일한 패턴으로 자연스럽게 확장 가능)
  - **읽기 전용**이며, 항목을 클릭하면 해당 하위 프로젝트의 실제 상세 화면으로 드릴다운
- 접근 권한: 상위 프로젝트의 PM/PMO(또는 SUPER_ADMIN)만 통합 현황에 접근 가능. 하위 프로젝트 멤버가 상위 프로젝트 멤버가 아니라면 통합 뷰에는 접근할 수 없다(하위 프로젝트 데이터를 상위로 "승격"시키는 것이 아니라, 상위 프로젝트 담당자에게 "조회 권한"만 부여하는 개념).

## 4. 단계별 로드맵

### Phase 1 — 멀티 프로젝트 로그인/가입 기반 구축
데이터 모델과 인증 흐름을 다중 프로젝트 대응으로 전환. 이 단계가 끝나야 이후 모든 관리 화면이 의미를 가진다.

- [ ] `Project.parentProjectId`, `ProjectFeature`, `User.lastProjectId` 마이그레이션 추가
- [ ] `lib/server/auth.ts` 재작성 — `DEFAULT_PROJECT_ID` 하드코딩 제거, 멤버십 기반 로그인 + "PROJECT_REQUIRED" 흐름
- [ ] 로그인 화면: 프로젝트 선택 UI(2개 이상일 때만 노출) + "프로젝트 기억하기"
- [ ] 회원가입 화면: 프로젝트 검색·선택 UI 추가, `ProjectMember(isActive:false)` 동반 생성
- [ ] 가입 승인 관리 화면(PM/PMO용) 신규 추가
- [ ] 기존 `DEFAULT_PROJECT_ID` 참조 코드 전수 점검(스크립트, 시드, 문서) 및 정리

### Phase 2 — 플랫폼 관리 기능
슈퍼관리자와 PM에게 실제 운영 도구를 제공.

## 5. 리스크 및 미해결 이슈

- **기존 운영 데이터 이관**: 지금의 `DEFAULT_PROJECT_ID` 프로젝트를 플랫폼 전환 후 "1번 프로젝트"로 그대로 유지해야 하며, 그 프로젝트에 속한 기존 사용자 전원의 `ProjectMember.isActive`가 `true`로 남아 있는지 마이그레이션 스크립트로 검증 필요.
- **기능 OFF 시 기존 데이터 처리 정책**: 어떤 프로젝트가 나중에 특정 기능(예: 이슈관리)을 끄면, 이미 쌓인 데이터를 숨기기만 할지(재활성화 시 복구), 접근 자체를 차단할지 정책 확정 필요.
- **PM 권한과 `ProjectMember.role=ADMIN` 재사용의 부작용**: 기존에 "관리자"라는 표현이 쓰이는 화면 문구들이 이제는 "PM"을 의미하게 되므로, 사용자 대상 UI 라벨을 프로젝트 컨텍스트에서는 "PM"으로 바꿔줄지 검토 필요.
- **통합 현황 성능**: 하위 프로젝트 수가 많아지면 집계 쿼리 비용이 커질 수 있음 — 초기엔 단순 집계로 시작하고, 필요 시 캐싱(기존에 쓰이는 `unstable_cache`/`revalidateTag` 패턴) 적용.
- **가입 승인 알림**: 승인 대기/승인 완료를 사용자에게 알릴 방법(기존 쪽지/초청함 기능 재사용 가능) 결정 필요.
- **기본기능/추가기능 분류표(3.6절)는 아직 확정안이 아님** — 실제 구현 착수 전 사용자 확인 필수.
