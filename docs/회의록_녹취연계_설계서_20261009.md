### 1.2 설계에 영향을 주는 현행 제약 (중요)

1. **회의록 수정 시 `attendees`·`entries`는 매번 전체 삭제 후 재생성**된다 (`updateMeetingMinute`의 `deleteMany` + `createMany`).
   → 다른 테이블이 `MeetingMinuteEntry.id`나 `MeetingMinuteAttendee.id`를 FK로 참조하면 **저장할 때마다 링크가 끊긴다.**
   → 결정사항의 주제·근거 링크는 **Entry 행 자체의 컬럼**으로 두고, 화자 매핑은 Attendee id가 아니라 **userId/이름**으로 연결한다.
2. Action Item은 id를 유지하며 갱신된다 → FK 참조 가능.
3. `MeetingMinute.category`는 자유 입력 문자열이며 "이후 공통코드로 전환 예정" 주석이 있다 → 카테고리 체계는 공통코드로 정리한다.
4. 권한: 등록자 또는 운영자 이상만 수정, Action Item 상태는 프로젝트 멤버 누구나 변경.

## 3. 전체 구조

### 3.1 처리 흐름

```
 [입력 파일]                [저장/정규화]                     [회의록 본문]                  [조회/분석]
 ┌───────────────┐      ┌────────────────────┐          ┌──────────────────────┐      ┌────────────────────┐
 │ 녹취 스크립트   │─────▶│ MeetingMinuteSource │──파싱──▶│ MeetingUtterance       │──┬──▶│ 발언자별 조회 (R6)   │
 │ (.txt/.vtt/.srt)│      │  (원문 텍스트 보존)   │          │  (발언 단위 + 화자 매핑)  │  │   └────────────────────┘
 │ 녹취 요약       │─────▶│                     │          └──────────────────────┘  │
 │ 회의 정리       │─────▶│                     │                    │               │   ┌────────────────────┐
 └───────────────┘      └────────────────────┘                    ▼               ├──▶│ 의사결정 대장 (R5)   │
                                  │                    ┌──────────────────────┐    │   └────────────────────┘
                                  └──── AI 추출 ───────▶│ MeetingExtraction      │    │
                                        (Gemini)        │ (후보: 내용/결정/AI/주제)│    │   ┌────────────────────┐
                                                        └──────────┬───────────┘    ├──▶│ Action Item 보드     │
                                                                   │ 사람 검토·선택      │   └────────────────────┘
                                                                   ▼                 │
                                                        ┌──────────────────────┐    │   ┌────────────────────┐
                                                        │ 기존 회의록 본문         │────┴──▶│ 주제·카테고리 조회 (R7)│
                                                        │ Entry(CONTENT/DECISION/ │        └────────────────────┘
                                                        │ NOTE) + ActionItem      │
                                                        └──────────────────────┘
```

### 3.2 설계 원칙

1. **AI는 제안만, 확정은 사람** — AI 결과는 `MeetingExtraction`에 후보로만 저장하고, 사용자가 선택한 항목만 기존 회의록 본문(Entry/ActionItem)에 반영한다. AI 결과가 회의록에 자동 기록되는 경로는 없다.
2. **AI 없이도 전 기능 동작** — AI 비활성(키 미설정·정책상 금지) 상태에서도 업로드·파싱·화자 매핑·수기 작성·조회가 모두 동작한다.
3. **원문 불변 보존** — 업로드 원문은 수정하지 않는다(재업로드 = 신규 Source). 결정·Action Item은 근거 발언(seq)으로 원문에 역추적 가능.
4. **기존 저장 방식 존중** — Entry/Attendee 전체 재작성 방식을 바꾸지 않고, 링크 정보를 행 내부 컬럼으로 둔다(§1.2).

## 5. 입력 파일 파싱 설계

### 5.1 지원 포맷 (P1)

| format | 판별 규칙 | 예시 |
| --- | --- | --- |
| `CLOVA_TXT` | `^(.+?)\s+(\d{1,2}:\d{2}(:\d{2})?)$` 헤더 줄 다음 본문 | `참석자 1 00:03`<br>`네 시작하겠습니다.` |
| `VTT` | 첫 줄 `WEBVTT`, `<v 화자>` 태그 (MS Teams) | `00:00:03.000 --> 00:00:05.000`<br>`<v 홍길동>안녕하세요</v>` |
| `SRT` | 숫자 인덱스 + `-->` 타임코드 (Zoom 등) | |
| `SPEAKER_COLON` | `^[가-힣A-Za-z0-9 ()]{1,20}\s*:\s*.+` 비율 ≥ 60% | `김PM: 일정 확정합니다` |
| `PLAIN` | 그 외 | 화자 "미상", 문단 단위 분리 |

- 인코딩: UTF-8(BOM 제거) 우선, 실패 시 EUC-KR(CP949) 재시도 — 사내 Windows 메모장 산출물 대응.
- 연속된 동일 화자 발언은 병합하지 않는다(시각 정보 보존).
- `.docx`/`.hwp`는 P1 비지원(§12 의사결정). `.md`는 SUMMARY/NOTES 용으로 텍스트 그대로 저장.
- 파서는 `lib/domain/meeting-transcripts.ts`의 순수 함수로 구현하고 포맷별 픽스처로 vitest 단위 테스트.

```ts
// lib/domain/meeting-transcripts.ts (시그니처)
export type TranscriptFormat = "CLOVA_TXT" | "VTT" | "SRT" | "SPEAKER_COLON" | "PLAIN";
export type ParsedUtterance = { seq: number; speakerLabel: string; startMs: number | null; text: string };
export function detectTranscriptFormat(text: string): TranscriptFormat;
export function parseTranscript(text: string, format: TranscriptFormat): ParsedUtterance[];
export function decodeTranscriptBuffer(buffer: ArrayBuffer): string; // UTF-8 → CP949 fallback
export function speakerLabelsOf(rows: ParsedUtterance[]): { label: string; count: number }[];
```

### 5.2 화자 자동 매핑 제안

1. 라벨이 참석자 이름과 정확히 일치 → 자동 매핑
2. 라벨이 프로젝트 멤버 이름과 일치 → 자동 매핑(참석자 추가 제안)
3. "참석자 N"/"Speaker N" → 미매핑, 화면에서 수동 선택(발언 샘플 3건 표시)

## 6. AI 추출 설계 (P2)

### 6.1 처리

- 기존 `weekly-report-summary.ts`의 Gemini 클라이언트·감사로그 패턴을 재사용(`lib/server/meeting-extraction.ts`).
- 입력: 회의 기본정보 + 참석자 + SUMMARY/NOTES 원문 + TRANSCRIPT 발언(`[seq] 화자: 내용` 형태).
- 출력: `responseMimeType: "application/json"` + `responseSchema`로 구조화 JSON 강제, zod로 재검증.
- 각 후보는 **근거 seq 필수** — 근거 없는 결정·Action Item 후보는 서버에서 "근거 없음" 경고 표시.
- 입력이 모델 한도를 넘으면(장시간 회의) 발언을 구간 분할 → 구간별 추출 → 병합(중복 제목 dedupe). 단, P2 1차는 단일 호출 + 길이 초과 시 안내 메시지로 시작.

```json
{
  "contents":   [{ "content": "...", "remark": "...", "topics": ["상품전시"], "evidence": [12, 13] }],
  "decisions":  [{ "content": "...", "plannedSchedule": "10월 중", "importance": "KEY", "topics": [], "evidence": [40] }],
  "actionItems":[{ "title": "...", "content": "...", "assigneeName": "홍길동", "dueDate": "2026-10-20", "topics": [], "evidence": [41, 42] }],
  "topics":     [{ "name": "상품전시", "isNew": false }]
}
```

### 6.2 반영(Apply) 규칙

- 사용자가 후보별 체크·수정 후 "회의록에 반영" → 기존 `updateMeetingMinute` 경로를 그대로 호출(낙관적 잠금·권한·감사로그 일원화).
- 담당자명은 프로젝트 멤버 이름과 매칭해 `assigneeId` 자동 연결, 실패 시 `assigneeName`만 저장(기존 외부인 허용 규칙과 동일).
- 신규 주제(`isNew`)는 자동 생성하지 않고 "주제 추가" 확인을 거친다.
- 원문 변경 후 기존 추출 결과는 `stale` 표시(기존 위클리 요약과 동일한 sourceHash 방식).

### 6.3 권한·통제

- 실행: 회의록 수정 권한자(등록자·운영자 이상).
- 감사로그: `MEETING_SOURCE_UPLOAD`, `MEETING_SOURCE_DELETE`, `MEETING_SPEAKER_MAP`, `MEETING_EXTRACTION_RUN`, `MEETING_EXTRACTION_APPLY`.
- 환경변수 `MEETING_AI_ENABLED`(기본 false) — 미설정 시 AI 버튼 비노출. 외부 전송 정책 승인 전까지 꺼둔다(§12).

### 9.3 성능 기준

- 규모 가정: 프로젝트당 회의 300건 × 평균 발언 800건 ≈ 24만 행.
- P1~P2: `(projectId, speakerUserId)` 인덱스 + 회의 단위 페이지네이션이면 발언자 조회는 인덱스 범위 스캔으로 충분.
- 키워드 검색(ILIKE `%q%`)이 24만 행 Full Scan → 200ms 초과 시 P3에서 `pg_trgm` GIN 인덱스 도입. **DB 확장(extension) 설치이므로 운영 DB 권한·Supabase 지원 여부 사전 확인 필요.**
