- 문서버전: v1.1 (이슈사항 상태값 반영)
- 작성일: 2026-07-31
- 근거자료: `PMS/PMS Design.xlsx` (시트 6종: 주간보고, 주간실적, 이슈사항, 인력변동, 사용자, 코드)

## 1. 개요

### 1.1 목적
SI/IT 프로젝트 현장에서 PM(프로젝트 매니저)이 주간 단위로 관리하는 업무 — 주간보고, 진행률(공정율) 관리, 이슈 트래킹, 인력 투입/철수 현황 — 를 웹 기반 시스템으로 전산화하여, 보고서 작성 시간을 줄이고 프로젝트 이력을 데이터로 축적·조회할 수 있도록 한다.

### 1.2 대상 사용자
- **관리자(PM/PMO)**: 전체 데이터 등록·수정·삭제, 사용자 및 공통코드 관리
- **사용자(참여 인력)**: 담당 영역(기획/디자인/개발 등)의 주간 실적·이슈 입력
- **게스트**: 조회 전용 (설계 시트의 `코드` 테이블에 권한값으로 정의되어 있으나 현재 사용자 데이터에는 미배정 상태)

### 1.3 설계 자료 요약
원본 엑셀은 완성된 데이터가 아니라 **화면/테이블 골격(헤더 + 예시 1~2행)** 수준으로, 실질적으로는 데이터 모델 설계서에 가깝다. 이번 개발계획서는 이 골격을 소프트웨어 요구사항으로 해석·구체화한 것이다.

## 2. 기능 요구사항 (엑셀 시트 → 기능 매핑)

| # | 시트명 | 기능 모듈 | 핵심 컬럼 |
|---|--------|-----------|-----------|
| 1 | 주간보고 | 주간보고 관리 | 영역, 금주실적, 차주계획, 이슈사항, 의사결정필요사항, 비고 |
| 2 | 주간실적 | 진행률(공정율) 관리 | 영역, 금주계획/목표일, 실적/목표일, 공정율, 차주계획/목표일, 비고 |
| 3 | 이슈사항 | 이슈/요청 트래킹 | 영역, 이슈 및 요청항목, 대응방안, **상태(접수/진행중/완료)**, 비고 |
| 4 | 인력변동 | 인력 투입/철수 관리 | 구분(투입/철수), 영역, 금주 인원수, 차주 인원수, 비고 |
| 5 | 사용자 | 사용자 관리 | ID, 소속사, 직책, 직급, 이름, 사용여부, 등록일, 권한, 비고 |
| 6 | 코드 | 공통코드 관리 | 영역, 직책, 직급, 사용여부, 권한 (각 드롭다운의 마스터 값) |

### 2.1 모듈별 상세 기능

**① 주간보고**
- 영역(기획/디자인/개발)별로 금주실적·차주계획·이슈사항·의사결정필요사항을 입력
- 주차(회차) 단위로 이력 관리, 과거 주차 조회/비교
- 보고서 형태(인쇄/PDF/화면) 출력 지원

**② 주간실적(공정율)**
- 영역별 세부 항목 단위로 "계획 vs 실적" 대비 진행률(%) 관리
- 계획일·목표일과 실제 완료일 차이를 통한 지연 여부 자동 표시
- 공정율 추이를 시각화(주차별 라인/바 차트)

**③ 이슈사항**
- 영역별 이슈/요청 항목과 대응방안을 등록
- 상태값(접수 → 진행중 → 완료) 관리: 원본 시트에는 없던 컬럼이나, 이슈 트래킹의 핵심 요소로 판단하여 신규 추가 확정(2026-07-31 확정)
  - 기본값은 "접수"로 등록, 담당자가 진행중/완료로 변경
  - 목록 화면에서 상태별 필터링 및 완료율(전체 이슈 대비 완료 건수) 표시
- 주간보고와 연계하여 "이슈사항" 컬럼에 자동 요약 가능(상태가 "완료"가 아닌 이슈만 노출)

**④ 인력변동**
- 구분(투입/철수) × 영역별로 금주/차주 인원수 입력, 합계 자동 집계
- 인력 투입/철수 추이를 프로젝트 기간 전체로 누적 조회

**⑤ 사용자 관리**
- ID, 소속사, 직책, 직급, 이름, 사용여부, 등록일, 권한(관리자/사용자/게스트), 비고 CRUD
- 로그인 인증 및 권한별 메뉴/기능 접근 제어(§5 참고)

**⑥ 코드(공통코드) 관리**
- 영역/직책/직급/사용여부/권한의 마스터 값을 관리자가 등록·수정
- 타 화면의 드롭다운(콤보박스)이 이 코드 테이블을 참조하도록 구성

## 3. 데이터 모델 설계(초안)

> 실제 DDL 작성 및 반영은 사용자 승인 후 진행(워크스페이스 공용 거버넌스 원칙에 따름). 아래는 논리 모델 초안이다.

| 테이블(안) | 원본 시트 | 주요 컬럼(안) | 비고 |
|---|---|---|---|
| `TB_WEEKLY_REPORT` | 주간보고 | 주차ID, 영역코드, 금주실적, 차주계획, 이슈사항, 의사결정필요사항, 비고, 등록자, 등록일 | 영역코드는 `TB_CODE` 참조 |
| `TB_WEEKLY_PROGRESS` | 주간실적 | 주차ID, 영역코드, 계획내용, 계획목표일, 실적내용, 실적목표일, 공정율, 차주계획, 차주목표일, 비고 | 공정율은 0~100 |
| `TB_ISSUE` | 이슈사항 | 이슈ID, 주차ID, 영역코드, 이슈요청항목, 대응방안, **상태코드**, 비고, 등록자, 등록일, 완료일 | 상태코드는 `TB_CODE`(코드유형=이슈상태: 접수/진행중/완료) 참조, 완료일은 상태를 "완료"로 변경 시 자동 기록 |
| `TB_STAFF_CHANGE` | 인력변동 | 변동ID, 주차ID, 구분(투입/철수), 영역코드, 금주인원수, 차주인원수, 비고 | 합계는 조회 시 SUM |
| `TB_USER` | 사용자 | 사용자ID(PK), 소속사, 직책코드, 직급코드, 이름, 사용여부, 등록일, 권한코드, 비고 | 로그인 계정 겸용 |
| `TB_CODE` | 코드 | 코드유형(영역/직책/직급/사용여부/권한/**이슈상태**), 코드값, 코드명, 정렬순서, 사용여부 | 공통코드 마스터. **이슈상태**(접수/진행중/완료)는 이슈사항 상태값 추가에 따른 신규 코드유형 |

- `주차ID`(WEEK_ID)는 모든 실적성 테이블(주간보고/주간실적/이슈사항/인력변동)의 공통 키로 두어, 특정 주차 기준 일괄 조회·보고서 생성이 가능하도록 설계한다.
- 영역/직책/직급/권한/사용여부는 모두 `TB_CODE` 공통코드를 참조하는 정규화 구조로 설계하여, 향후 값 추가(예: 새로운 직책 도입) 시 코드 관리 화면에서만 수정되도록 한다.

## 4. 화면 설계(메뉴 구조안)

```
PMS
├── 대시보드           # 현재 주차 공정율/이슈/인력 현황 요약
├── 주간보고
│   ├── 주간보고 입력/조회
│   └── 주간보고서 출력(인쇄/PDF)
├── 주간실적(공정율)
│   ├── 실적 입력/조회
│   └── 공정율 추이 차트
├── 이슈사항 관리
├── 인력변동 관리
├── 시스템 관리 (관리자 전용)
│   ├── 사용자 관리
│   └── 공통코드 관리
```

- 화면 단위/기능 단위 소스 분리 원칙에 따라, 실제 구현 시에는 메뉴별로 화면 컴포넌트 및 API를 분리한다(예: `weekly-report`, `weekly-progress`, `issue`, `staff-change`, `user`, `code` 각 도메인 폴더 분리).

## 6. 개발 범위 및 일정(안)

### 6.1 개발 착수 전 확정 필요 사항 (사용자 확인 요청)

**확정된 사항**
- ~~이슈사항 상태값~~ → **확정(2026-07-31): 접수/진행중/완료 3단계 상태값을 `TB_ISSUE.상태코드`로 추가하여 진행** (§2.1 ③, §3 `TB_ISSUE`/`TB_CODE` 반영 완료)

**미확정 사항**
1. **주차 기준**: 매주 월요일 자동 신규 주차 생성 여부, 또는 수동 등록
2. **기술 스택**: 프론트엔드/백엔드/DB 선호 기술이 있는지 (예: React+Node+PostgreSQL, 또는 사내 표준 스택)
3. **인증 방식**: 자체 로그인 vs 사내 SSO 연동 여부
4. **배포 환경**: 온프레미스/사내망 vs 클라우드

### 6.2 WBS(안)

| 단계 | 주요 작업 | 기간(안) |
|---|---|---|
| 1. 요구사항 확정 | §6.1 항목 확정, 화면정의서/DB설계서 확정 | 1주 |
| 2. 설계 | ERD, API 명세, 화면 UI 설계(와이어프레임) | 1~2주 |
| 3. 개발 - 공통 | 로그인/인증, 사용자관리, 공통코드관리 | 1~2주 |
| 4. 개발 - 핵심기능 | 주간보고, 주간실적(공정율), 이슈사항, 인력변동 | 3~4주 |
| 5. 개발 - 대시보드/리포트 | 대시보드, 보고서 출력(PDF) | 1~2주 |
| 6. 테스트 | 단위(Vitest) → 통합(Jest) → E2E(Playwright) 3단계 검증 | 1~2주 |
| 7. 배포/안정화 | 사용자 승인 후 배포, 초기 운영 지원 | 1주 |

> 테스트 단계는 워크스페이스 공용 거버넌스(Vitest → Jest → Playwright)를 따른다.

## 7. 리스크 및 고려사항

- **데이터 정규화**: 현재 엑셀은 각 시트가 독립적이라 영역/직책/직급 값이 시트마다 자유 텍스트로 들어갈 위험이 있음 → 반드시 공통코드 참조 구조로 구현 필요
- **권한 세분화**: "사용자"가 본인 담당 영역 외 데이터를 수정하지 못하도록 하는 규칙이 원본 설계에 명시되어 있지 않음 → §6.1에서 확정 필요
- **이력 관리**: 주차별 스냅샷을 남길지, 최신값만 유지할지에 따라 테이블 구조(이력 테이블 별도 여부)가 달라짐
