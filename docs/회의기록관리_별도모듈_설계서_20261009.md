## 3. 처리 흐름

```
 [입력 파일]                [원문 저장]                 [발언]                     [회의기록 본문]                [조회]
 녹취 스크립트 ─┐       ┌────────────────────┐    ┌────────────────────┐    ┌──────────────────────┐    ┌──────────────┐
 녹취 요약    ─┼─업로드▶│ meeting_record_     │파싱▶│ meeting_record_     │근거▶│ items (내용/특이사항)   │──▶│ 발언자 조회     │
 회의 정리    ─┘       │ sources            │    │ utterances         │    │ decisions (의사결정)   │──▶│ 의사결정 대장   │
                       └─────────┬──────────┘    └─────────┬──────────┘    │ action_items         │──▶│ Action Item 보드│
                                 │                         │화자 매핑     └──────────▲───────────┘    │ 주제·카테고리 조회│
                                 └──────── AI 추출(Gemini) ─┴──▶ extractions(후보) ──사람 검토·선택──┘    └──────────────┘
```

설계 원칙
1. **AI는 제안만, 확정은 사람** — AI 결과는 `extractions`에 후보로만 저장, 선택된 항목만 본문에 반영.
2. **AI 없이도 전 기능 동작** — 업로드·파싱·매핑·수기 작성·조회는 AI와 무관.
3. **원문 불변** — 업로드 원문은 수정하지 않음(재업로드 = 신규 Source). 본문 항목은 근거 발언으로 원문 역추적.
4. **자식 행 id 유지 저장** — 기존 회의록처럼 저장 시 전체 삭제·재생성하지 않고 id 기준 upsert. 그래야 주제 태그·근거 링크·Action Item 이력이 FK로 안전하게 유지된다.

## 4. 데이터 모델

### 4.1 기존 테이블 참조 방식

- `projectId`, `userId` 류는 **일반 문자열(uuid) 컬럼**으로 저장하고 Prisma relation·DB FK를 기존 테이블로 걸지 않는다.
  - 이유: Prisma relation은 상대 model(`Project`, `User`)에 back-reference 필드 추가를 강제 → 기존 model 블록 수정이 발생.
  - 보완: 서버에서 저장 시 `project_members` 조회로 프로젝트 멤버 여부 검증(기존 회의록 `validatePeople`과 동일 수준), 표시용 이름은 행에 비정규화 저장(`*Name` 컬럼) → 사용자 비활성·삭제 시에도 기록 보존.
- 신규 테이블끼리는 정상 relation/FK 사용.

### 4.2 ERD

```
meeting_record_sequences (projectId PK)
meeting_record_categories ─1:*─ meeting_record_topics
meeting_records ─┬─* meeting_record_participants
                 ├─* meeting_record_sources ─┬─* meeting_record_utterances
                 │                           └─* meeting_record_speakers
                 ├─* meeting_record_items            (회의 내용 / 특이사항)
                 ├─* meeting_record_decisions ──(supersededById: self)
                 ├─* meeting_record_action_items ─* meeting_record_action_logs
                 ├─* meeting_record_extractions
                 └─* meeting_record_topic_links *─1 meeting_record_topics
                     (targetType: RECORD / ITEM / DECISION / ACTION_ITEM)
```

| errorMessage | text | |
| requestedBy | uuid | |

#### `meeting_record_categories` / `meeting_record_topics` / `meeting_record_topic_links` — 분류 체계

| 테이블 | 주요 컬럼 |
| --- | --- |
| categories | id, projectId, code(예: DES), name(예: 설계), sortOrder, isActive — unique `(projectId, code)` |

## 5. 입력 파일 파싱

| format | 판별 규칙 | 대상 |
| --- | --- | --- |
| `CLOVA_TXT` | `화자명 00:00(:00)` 헤더 줄 + 본문 | 클로바노트 텍스트 내보내기 |
| `VTT` | 첫 줄 `WEBVTT`, `<v 화자>` | MS Teams 기록 |
| `SRT` | 인덱스 + `-->` 타임코드 | Zoom 등 |
| `SPEAKER_COLON` | `화자: 내용` 줄 비율 ≥ 60% | 수기 정리본 |
| `PLAIN` | 그 외 | 화자 미상, 문단 단위 |

- 인코딩: UTF-8(BOM 제거) → 실패 시 CP949 재시도.
- 허용 확장자: `.txt .vtt .srt .md` (P1). `.docx`는 §12 D4.
- 화자 자동 매핑: ① 참석자 이름 일치 ② 프로젝트 멤버 이름 일치(참석자 추가 제안) ③ "참석자 N" 류는 수동 선택(발언 샘플 3건 제시).
- 파서는 `lib/domain/meeting-records/transcripts.ts` 순수 함수 + 포맷별 픽스처 vitest.

```ts
export type TranscriptFormat = "CLOVA_TXT" | "VTT" | "SRT" | "SPEAKER_COLON" | "PLAIN";
export type ParsedUtterance = { seq: number; speakerLabel: string; startMs: number | null; text: string };
export function decodeTranscript(buffer: ArrayBuffer): string;
export function detectTranscriptFormat(text: string): TranscriptFormat;
export function parseTranscript(text: string, format: TranscriptFormat): ParsedUtterance[];
export function speakerLabelsOf(rows: ParsedUtterance[]): { label: string; count: number; samples: string[] }[];
```

## 6. AI 추출 (P2)

- 모듈 내부 `lib/server/meeting-records/extraction.ts`에서 Gemini 클라이언트를 별도 생성(기존 위클리 요약 코드 무수정, 같은 `GEMINI_API_KEY` 사용).
- 입력: 회의 기본정보 + 참석자 + 허용된 Source(§12 D1에 따라 SUMMARY/NOTES만 또는 TRANSCRIPT 포함) — 발언은 `[seq] 화자: 내용` 형식.
- 출력: `responseMimeType: application/json` + `responseSchema`, 서버에서 zod 재검증.
- 모든 의사결정·Action Item 후보는 근거 seq 필수, 근거 없으면 검토 화면에 경고.
- 반영: 사용자가 후보별 선택·수정 → 같은 트랜잭션으로 items/decisions/action_items 생성(`origin=AI`), 주제 링크 생성, extraction `APPLIED` 기록, 헤더 `version` 증가.
- 담당자명은 프로젝트 멤버 이름 매칭으로 `assigneeUserId` 연결, 실패 시 이름만 저장.
- 신규 주제 후보는 자동 생성하지 않고 확인 후 생성.
- 원문 변경 시 기존 추출은 `stale` 표시(sourceHash 비교).
- 환경변수 `MEETING_RECORD_AI_ENABLED`(기본 false) — 꺼져 있으면 AI 버튼 미노출.

### 9.3 독립성 검증 기준 (각 단계 완료 시)

1. `git diff main -- prisma/schema.prisma` 결과가 **추가 행만** 포함(기존 model/enum 행 변경 0).
2. `git diff main --stat`에서 신규 경로 외 변경 파일은 메뉴 2개 파일뿐(§2.3, 옵션 A 선택 시).
3. 기존 회의록 테스트(`lib/domain/meeting-minutes*.test.ts`, `meeting-action-items.test.ts`) 전부 통과.
4. 신규 마이그레이션 SQL에 `ALTER TABLE` 대상이 신규 테이블뿐임을 리뷰로 확인.

### 9.4 성능 기준

- 가정: 프로젝트당 회의 300건 × 발언 800건 ≈ 24만 행.
- 발언자 조회는 `(projectId, speakerUserId)` 인덱스로 처리. 키워드 ILIKE가 200ms 초과 시 P3에서 신규 테이블 `meeting_record_utterances.text`에 pg_trgm GIN 인덱스(확장 설치는 DB 권한 확인 필요 — 신규 테이블 대상이므로 기존 구조 무영향).
